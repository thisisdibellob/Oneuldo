# 생활 시뮬레이션 게임 행동 로그 수집표

> 출처: `정리본.md`의 10장과 19장 내용을 통합한 표  
> 상태 구분: **공통 필수**는 모든 생활과제에서 같은 이름과 의미로 수집하도록 문서에 명시된 항목이고, **조건부 필수**는 해당 화면·이벤트·종료 조건이 발생했을 때 반드시 수집할 항목이며, **권장/초안**은 문서가 예시 또는 권장 이벤트로 제시한 항목이다. 필드명과 JSON 구조는 구현 과정에서 확정해야 한다.
> JSON 요청과 응답의 필드 이름은 프로젝트 전체에서 **camelCase**를 사용한다. Java record 필드도 같은 이름을 사용하며 별도 naming strategy로 변환하지 않는다.

## 1. 로그 적용 범위

| 값 | 수집 상황 | 판단 시 사용 원칙 |
|---|---|---|
| `ASSESSMENT_TASK` | 평가 목적과 조건이 통제된 과제 | 핵심 평가 증거로 사용 가능 |
| `TRAINING_TASK` | 생활기술 훈련 중 발생한 행동 | 학습·향상·힌트 감소 확인에 사용 |
| `PASSIVE_PLAY` | 자유 이동, NPC 상호작용, 일반 UI 사용 | 단독 점수화 금지, 반복 신호를 추가 평가 추천에만 사용 |
| `ACCESSIBILITY` | 조작과 접근성 확인 행동 | 능력점수와 분리하여 평가 유효성 판단에 사용 |

각 이벤트에는 위 구분을 나타내는 `evidenceContext`를 기록한다.

## 2. 모든 게임의 공통 로그

| 상태 | 데이터 범주 | 필드 | Java 권장 타입 | 수집 내용 | 판단 시 주의사항 |
|---|---|---|---|---|---|
| 공통 필수 | 식별 | `sessionId` | `UUID` | 플레이 회기 식별 | `userId`는 요청으로 받지 않고 서버가 JWT subject에서 확정 |
| 공통 필수 | 이벤트 식별 | `clientEventId`, `eventSequence` | `UUID`, `Long` | 프론트에서 생성한 이벤트 고유 ID와 세션 내 발생 순서 | 재전송에 따른 중복 저장 방지와 오프라인 이벤트 순서 복원에 사용 |
| 공통 필수 | 스키마·앱 버전 | `eventSchemaVersion`, `appVersion`, `contentVersion` | `String` | 이벤트 계약, 앱, 화면·퀘스트 콘텐츠 버전 | 서로 다른 수집 로직과 콘텐츠 결과를 무조건 동일 비교하지 않음 |
| 공통 필수 | 과제정보 | `gameId`, `taskId`, `taskVersion` | `String`, `UUID`, `String` | 게임·과제·버전 | 버전이 다른 결과를 무조건 동일 비교하지 않음 |
| 공통 필수 | 난이도·변형 | `difficulty`, `scenarioVariant` | `Integer`, `String` | 난이도와 시나리오 조건 | 난이도 차이를 점수 해석에 반영 |
| 조건부 필수 | 제공 콘텐츠 | `questInstanceId`, `contentSource` | `UUID`, `ContentSource` enum | 퀘스트·시뮬레이션에서 실제 제공된 실행본과 정적·생성·대체 콘텐츠 구분 | 같은 원본 퀘스트라도 실행본이 다르면 구분하여 분석 |
| 공통 필수 | 행동정보 | `eventCode`, `microActionId`, `occurredAt` | `String`, `String`, `Instant` | 이벤트 종류, 세부행동 ID와 발생 시각 | 최종 성공이 아닌 세부행동 단위로 기록 |
| 공통 필수 | 증거 맥락 | `evidenceContext` | `EvidenceContext` enum | 평가·훈련·상시·접근성 구분 | `PASSIVE_PLAY`만으로 점수 확정 금지 |
| 공통 필수 | 접근성 조건 | `instructionMode`, `textLevel`, `audioEnabled`, `symbolSupport`, `controllerMode` | `InstructionMode` enum, `TextLevel` enum, `Boolean`, `Boolean`, `ControllerMode` enum | 글·그림·음성·상징·조작 방식 | 접근성 조건이 다르면 동일 조건 결과와 구분 |
| 공통 필수 | 과제 결과 | `taskCompleted`, `completionQuality`, `completionTimeMs` | `Boolean`, `Double`, `Long` | 완료 여부·품질·총 시간 | 시간만으로 능력을 판단하지 않음 |
| 공통 필수 | 시작 | `startLatencyMs`, `firstAction` | `Long`, `String` | 지시 후 첫 행동까지 시간과 첫 선택 | 피로·이해·조작 등 다른 원인 확인 |
| 공통 필수 | 단계 수행 | `stepId`, `stepOutcome`, `stepOrder` | `UUID`, `StepOutcome` enum, `Integer` | 단계별 성공·실패와 실제 수행 순서 | 세부행동별 능력 매핑 후 사용 |
| 공통 필수 | 오류 | `omissionCount`, `repetitionCount`, `wrongActionCount`, `sequenceErrorCount` | `Integer` | 생략·반복·오행동·순서 오류 | 오류 원인이 조작·접근성인지 확인 |
| 공통 필수 | 재시도 | `retryCount` | `Integer` | 같은 행동을 다시 시도한 횟수 | 반복 시도와 동일 오류 반복을 구분 |
| 공통 필수 | 자기수정 | `selfCorrected`, `selfCorrectionLatencyMs` | `Boolean`, `Long` | 외부 단서 없이 오류를 수정했는지와 시간 | 오류 횟수와 별도로 긍정적 증거로 관리 |
| 공통 필수 | 지원 | `promptLevel`, `supportType`, `supportCount` | `Integer`, `SupportType` enum, `Integer` | 필요했던 지원 단계·종류·횟수 | 독립수행과 지원 후 수행을 분리 |
| 공통 필수 | 도움요청 | `helpRequested`, `helpRequestTarget`, `helpRequestLatencyMs` | `Boolean`, `String`, `Long` | 도움 요청 여부·대상·요청까지 시간 | 도움 사용 자체를 낮은 능력으로 처리하지 않음 |
| 공통 필수 | 비활동 | `idleCount`, `idleTimeMs` | `Integer`, `Long` | 멈춘 횟수와 누적 시간 | 불안·의욕·집중력으로 추론하지 않음 |
| 공통 필수 | 안전 | `safetyEventCode`, `safetySeverity`, `nearMiss` | `String`, `SafetySeverity` enum, `Boolean` | 위험행동·심각도·위험 직전 사건 | 일반 능력점수와 평균 내지 않음 |
| 공통 필수 | 유효성 | `invalidReason`, `technicalError`, `assistantIntervention` | `InvalidReason` enum, `Boolean`, `Boolean` | 평가 제외 사유·기술오류·조력자 개입 | 평가 불가 행동은 `X`로 제외 |
| 조건부 필수 | 세션 종료 | `sessionEndReason`, `interruptionCount`, `interruptionTimeMs` | `SessionEndReason` enum, `Integer`, `Long` | 세션 종료 시 정상 완료·사용자 중단·앱 백그라운드·네트워크·기술 오류와 중단 횟수·시간 | 사용자 의도 중단과 기술적 이탈을 구분 |
| 공통 필수 | 사용자 경험 | `perceivedDifficulty`, `comfortReport`, `preferredSupport` | `Integer`, `String`, `SupportType` enum | 체감 난이도·불편함·선호 지원 | 관찰 로그와 분리된 자기보고 자료로 저장 |

### 지원 단계

| `promptLevel` | 지원 수준 |
|---:|---|
| 0 | 도움 없음 |
| 1 | 그림 또는 짧은 힌트 |
| 2 | 구체적인 단계 지시 |
| 3 | 시범·정답 위치 표시·대리 수행 |

지원 이벤트가 발생하면 `지원 직전 결과`, `지원 직후 결과`, `다음 시도의 필요 지원 수준`, `일정 시간 후 독립수행 여부`를 함께 비교할 수 있어야 한다.

### 2.1 이벤트 전달·중복 방지 메타데이터

아래 값은 사용자의 능력을 판단하기 위한 데이터가 아니라, 프론트에서 발생한 이벤트를 서버가 누락·중복·순서 변경 없이 저장하기 위한 데이터다. `occurredAt`은 프론트에서 행동이 실제 발생한 시각으로 사용하고, 서버 수신 시각인 `receivedAt`은 서버가 별도로 기록한다.

| 상태 | 필드 | 수집 시점 | 설명 |
|---|---|---|---|
| 필수 | `clientEventId` | 이벤트 생성 시 | UUID 등 프론트가 한 번만 생성하는 고유값. 재전송해도 같은 값을 유지 |
| 필수 | `eventSequence` | 이벤트 생성 시 | 한 세션에서 1부터 증가하는 순번 |
| 필수 | `eventSchemaVersion` | 이벤트 생성 시 | 예: `behavior-event-v1` |
| 필수 | `appVersion` | 세션 시작 시 스냅샷 | 수집 로직이 포함된 앱 버전 |
| 필수 | `contentVersion` | 퀘스트 로드 시 스냅샷 | 화면·퀘스트·선택지 구성 버전 |
| 권장 | `batchId` | 이벤트 묶음 전송 시 | 배치 요청 최상위에 한 번만 포함하는 묶음 UUID |
| 권장 | `offlineQueued` | 로컬 큐 적재 시 | 네트워크 문제로 즉시 전송하지 못했는지 여부 |
| 권장 | `devicePerformanceClass` | 세션 시작 시 스냅샷 | `LOW`, `MEDIUM`, `HIGH`처럼 앱이 계산한 성능 등급. 상세 기기 식별값은 보내지 않음 |

서버는 사용자별 `clientEventId`와 `(sessionId, eventSequence)`를 고유하게 처리하고, 동일 이벤트가 다시 도착하면 새 행을 추가하지 않는다. `eventSequence`에 빈 번호가 있으면 누락 가능성을 표시하되, 늦게 도착한 이벤트를 임의로 폐기하지 않는다.

### 2.2 실제 화면 제시 조건

사용자의 선택을 해석하려면 서버가 내려준 원본뿐 아니라 프론트가 실제로 무엇을 어떤 순서로 보여 주었는지 확인할 수 있어야 한다. 아래 값은 단계 진입, 선택지 노출, 힌트 노출 시점에 수집한다.

| 상태 | 필드 | Java 권장 타입 | 수집 내용 | 판단 시 주의사항 |
|---|---|---|---|---|
| 필수 | `screenId` | `String` | 행동이 발생한 실제 화면 | 같은 행동 코드가 서로 다른 화면에서 발생하는 경우 구분 |
| 해당 시 필수 | `instructionContentId` | `String` | 지시가 있는 화면에서 실제 노출한 지시문·음성·그림 콘텐츠 ID | 지시문 원문을 이벤트마다 중복 저장하지 않고 버전 있는 콘텐츠를 참조 |
| 해당 시 필수 | `presentedChoiceIds` | `List<String>` | 선택지가 있는 화면에서 실제 표시 순서대로 나열한 선택지 ID | 선택지 위치 편향과 누락·셔플 오류 확인에 사용 |
| 권장 | `hintContentId` | `String` | 실제 표시하거나 재생한 힌트 콘텐츠 ID | `promptLevel`, `supportType`과 함께 기록 |
| 권장 | `foregroundDurationMs` | `Long` | 화면이 실제 포그라운드였던 누적 시간 | 앱이 백그라운드였던 시간을 응답 시간에서 분리 |
| 권장 | `appBackgrounded` | `Boolean` | 행동 또는 응답 대기 중 앱이 백그라운드로 이동했는지 여부 | 긴 응답 시간을 수행 지연으로 잘못 해석하지 않도록 사용 |
| 권장 | `renderErrorCode` | `String` | 이미지·음성·선택지 등 콘텐츠 표시 실패 코드 | 해당 단계의 평가 유효성 판단에 사용 |

### 2.3 생성 시뮬레이션 제공·사용자 피드백

생성형 또는 정적 변형 시뮬레이션을 제공할 때 프론트는 서버에서 받은 실행본 식별자를 모든 관련 이벤트에 포함한다. 모델명·프롬프트 원문·프로파일 데이터는 프론트 행동 이벤트에 넣지 않고 서버의 생성 이력에서 관리한다.

| 상태 | 필드 | Java 권장 타입 | 수집 시점·내용 | 사용 원칙 |
|---|---|---|---|---|
| 제공 시 필수 | `questInstanceId` | `String` | 사용자에게 제공된 실행본의 서버 발급 ID | 행동 로그와 정확한 생성 결과를 연결 |
| 제공 시 필수 | `contentSource` | `ContentSource` enum | `STATIC`, `GENERATED`, `REVIEWED_VARIANT`, `FALLBACK` 구분 | 생성 콘텐츠와 대체 콘텐츠 결과를 분리 비교 |
| 권장 | `simulationStarted` | `Boolean` | 콘텐츠 로드가 아니라 실제 첫 화면 노출 여부 | 생성만 되고 제공되지 않은 실행본을 수행 표본에서 제외 |
| 권장 | `simulationFeedbackCode` | `SimulationFeedbackCode` enum | 종료 화면에서 선택한 이해·난이도·불편·기술 문제 코드 | 자유서술보다 선택형 코드를 우선 사용 |
| 권장 | `instructionUnderstood` | `Boolean` | 사용자가 지시를 이해했다고 응답했는지 여부 | 실제 행동 결과와 분리된 자기보고로 저장 |
| 권장 | `satisfactionRating` | `Integer` | 1~5 만족도 | 능력점수에 포함하지 않음 |
| 권장 | `confusingStepIds` | `List<String>` | 이해하기 어려웠다고 선택한 단계 ID | 생성 문장·화면 품질 개선에만 사용 |
| 권장 | `wouldRetry` | `Boolean` | 같은 기술의 다른 상황을 다시 연습할 의향 | 동기나 성격을 추론하지 않음 |
| 선택 | `feedbackNote` | `String` | 사용자가 직접 입력한 짧은 의견 | 길이 제한, 개인정보 안내와 필터 적용 |

`perceivedDifficulty`, `comfortReport`, `preferredSupport`는 기존 공통 사용자 경험 필드를 그대로 사용한다. `simulationFeedbackCode`는 그 응답이 어려움·불편·기술 문제 중 어느 종류인지 구조적으로 구분하는 보조 코드다.

## 3. 퀘스트 밖 상시 행동 로그

| 영역 | 수집 행동 | 권장 필드·코드 | 보조 연결 영역 | 사용 제한 |
|---|---|---|---|---|
| 이동 | 불필요한 왕복·되돌아감 | `backtrackCount`, `backtrackDistance` | 시공간·탐색, 목표 유지 | 목표가 명확했는지 먼저 확인 |
| 이동 | 실제 경로와 최단경로 차이 | `travelDistance`, `routeEfficiency` | 시공간·탐색 | 최단경로가 요구되는 상황인지 확인 |
| 이동 | 지도·랜드마크·웨이포인트 사용 | `landmarkPause`, `mapOpenCount`, `waypointUsed` | 시공간·탐색, 생활 독립 | 지도 사용 빈도만으로 길찾기 어려움 판정 금지 |
| 이동 | 새로운 장소 진입과 탐색 | `newAreaEntryCount`, `explorationRatio` | 탐색 행동 양상 | 능력점수로 사용하지 않음 |
| 이동 | 길을 잃은 뒤 도움 요청 | `lostStateDetected`, `helpRequestLatencyMs` | 인지·집행, 의사소통, 생활 독립 | 실제 길 잃음 판정 조건 필요 |
| NPC·사물 | 이미 본 설명·대화 다시 보기 | `contentReopenCount`, `dialogueRepeatCount` | 작업기억, 의사소통 | 제시방식과 UI 접근성 확인 |
| NPC·사물 | 상호작용 후 다음 행동까지 시간 | `postInteractionLatencyMs` | 인지·집행 보조 | 시간만으로 능력 판단 금지 |

## 6. 수집·판단 운영 원칙

| 원칙 | 적용 방법 |
|---|---|
| 세부행동 우선 | 전체 성공 여부보다 `microActionId`별 행동을 기록하고 채점한다. |
| 독립·지원 분리 | 같은 행동의 지원 전과 후를 같은 대상끼리 비교한다. |
| 상시 로그 제한 | 지도 열기·메뉴 반복 같은 상시 행동 하나만으로 능력을 판정하지 않는다. |
| 반복 증거 | 동일 신호가 여러 상황과 통제된 과제에서도 반복될 때만 판단 근거로 사용한다. |
| 유효성 우선 | 조작·감각·언어접근·기술 오류가 있으면 능력점수에서 제외한다. |
| 안전 분리 | 안전사건은 평균점수에 섞지 않고 별도 상태와 사건 수로 관리한다. |
| 속도 분리 | 정확하지만 느린 사용자를 낮게 평가하지 않도록 시간과 정확도를 분리한다. |
| 관찰 표현 | 불안·고집·충동성 같은 성격을 추론하지 않고 관찰된 행동만 기록한다. |
| 초기 상태 | 권장 이벤트와 파생지표는 확정 스키마가 아닌 MVP 설계 초안이므로 구현 전에 명칭·타입·발생조건·중복처리를 확정한다. |
| 전달 신뢰성 | `clientEventId`로 중복을 제거하고 `eventSequence`로 누락과 순서 변경을 확인한다. |
| 실제 제시 조건 | 서버 원본이 아니라 프론트에서 실제 노출된 지시·선택지 순서·힌트·포그라운드 시간을 행동과 연결한다. |
| 콘텐츠 출처 분리 | 정적·생성·검토된 변형·fallback 결과를 `contentSource`와 `questInstanceId`로 구분한다. |
| 자기보고 분리 | 만족도·이해 여부·재시도 의향은 행동 기반 능력점수와 분리하고 콘텐츠 품질 개선에 사용한다. |
| 최소 수집 | 상세 기기 ID, 모델 프롬프트, 프로파일, 직접식별정보는 프론트 행동 이벤트에 포함하지 않는다. |

## 7. Java 데이터 타입 사전

JSON 요청 DTO는 값이 누락되었는지 검증할 수 있도록 primitive 타입인 `int`, `long`, `double`, `boolean`보다 nullable wrapper 타입인 `Integer`, `Long`, `Double`, `Boolean`을 권장한다. 검증을 통과한 내부 계산 객체에서는 primitive 타입으로 변환해도 된다.

### 7.1 필드 이름별 기본 타입 규칙

| 필드 형태·예시 | Java 권장 타입 | 단위·범위 | 비고 |
|---|---|---|---|
| `*Id`, `*Code`, `*Variant`, `firstAction` | `String` 또는 `UUID` | 식별자·코드 문자열 | UUID로 확정된 식별자는 Java `UUID` 사용 |
| `occurredAt`, `receivedAt` | `Instant` | ISO-8601 UTC | 예: `2026-08-26T13:10:24Z` |
| `eventSequence` | `Long` | 세션별 1 이상의 정수 | 프론트에서 증가시키고 재전송 시 기존 값 유지 |
| `*Count`, `stepOrder`, `difficulty`, `promptLevel`, `satisfactionRating` | `Integer` | 원칙적으로 0 이상의 정수 | `satisfactionRating`은 1~5로 제한 |
| `*TimeMs`, `*LatencyMs`, `*DurationMs` | `Long` | 밀리초 | 긴 세션을 고려해 `Long` 사용 |
| `*Seconds` | `Long` 또는 `Double` | 초 | 소수 초가 필요하면 `Double` |
| `*Distance`, `pointerDistance` | `Double` | 게임 거리 단위 또는 m | 프로젝트 전체에서 단위 통일 |
| `*Rate`, `*Ratio`, `*Accuracy`, `*Efficiency` | `Double` | 원칙적으로 0.0~1.0 | 0~100과 혼용하지 않도록 계약에 명시 |
| `*Score`, `completionQuality` | `Double` | 권장 0.0~100.0 | 점수 범위를 스키마에 고정 |
| `*Amount`, `budget`, `balance`, `price` | `Long` | 대한민국 원(KRW) | 원 단위 정수 저장, 부동소수점 금지 |
| `*Selected`, `*Checked`, `*Used`, `*Requested`, `*Completed`, `*Enabled`, `nearMiss` | `Boolean` | `true`/`false` | 미수집 상태와 `false`를 구분하려면 wrapper 사용 |
| 여러 선택값 | `List<String>` 또는 `List<Enum>` | 배열 | 예: 공개한 개인정보 종류, 선택한 지원 종류 |
| 자유서술 | `String` | UTF-8 | 길이 제한과 개인정보 필터 필요 |

### 7.5 Java 수신 DTO 예시

```java
public record BehaviorLogRequest(
    EventMetadata metadata,
    IdentityContext identity,
    TaskContext task,
    ActionContext action,
    AccessibilityContext accessibility,
    PresentationContext presentation,
    TaskResultContext taskResult,
    ErrorContext error,
    SupportContext support,
    SafetyContext safety,
    ValidityContext validity,
    SimulationContext simulation,
    SessionEndContext sessionEnd,
    UserExperienceContext userExperience,
    BehaviorPayload payload
) {}

public record EventMetadata(
    UUID clientEventId,
    Long eventSequence,
    String eventSchemaVersion,
    String appVersion,
    String contentVersion,
    Boolean offlineQueued,
    DevicePerformanceClass devicePerformanceClass,
    Instant occurredAt
) {}

public record IdentityContext(UUID sessionId) {}

public record BehaviorLogBatchRequest(
    UUID batchId,
    List<BehaviorLogRequest> events
) {}
```

모든 이벤트에 모든 문맥을 보내지 않는다. 공통 필수 문맥만 항상 전송하고, 지원·안전·종료·사용자 경험·게임별 payload는 해당 이벤트에서만 포함한다. `userId`는 요청 DTO에 포함하지 않으며 Controller가 JWT subject에서 회원 ID를 추출한다.

## 8. 백엔드 저장 계약

| 항목 | 구현 기준 |
|---|---|
| 단건 수집 | `POST /api/behavior-logs` |
| 배치 수집 | `POST /api/behavior-logs/batches`, 요청당 최대 100건 |
| 인증 | 두 API 모두 JWT 인증 필수, 로그의 `memberId`는 JWT subject로 확정 |
| 멱등성 | 사용자별 `clientEventId` 유일성 보장 |
| 순서 충돌 방지 | 사용자별 `(sessionId, eventSequence)` 유일성 보장 |
| 원본 저장 | `behavior_logs`에 append-only로 저장하며 JPA 엔티티는 `@Immutable` 사용 |
| 주요 조회 컬럼 | 사용자, 세션, 발생 시각, 과제, 이벤트 코드, 단계 결과, 콘텐츠 출처, payload 종류 |
| 가변 문맥 | 접근성·화면·결과·오류·지원·안전·유효성·종료·사용자 경험·게임별 payload는 JSONB 저장 |
| 서버 시각 | 프론트의 `occurredAt`과 별도로 서버가 `receivedAt` 기록 |

단건 및 배치 응답은 이벤트별로 `ACCEPTED` 또는 `DUPLICATE` 상태와 서버 저장 ID, `clientEventId`, `eventSequence`, `receivedAt`을 반환한다.

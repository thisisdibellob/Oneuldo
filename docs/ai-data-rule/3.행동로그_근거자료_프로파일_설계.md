# 정규화 행동 로그 기반 프로파일 설계

## 1. 목적

이 문서는 현재 백엔드의 정규화 결과를 사용해 생성할 사용자 프로파일의 입력 범위, 계산 규칙, Java 타입과 저장 구조를 정의한다.

프로파일은 다음 의미로만 사용한다.

> 현재 게임 조건에서 관찰된 과제 수행 결과, 필요한 지원 수준, 안전행동, 훈련 변화와 데이터 신뢰도를 설명하는 프로파일

IQ, 발달연령, 장애 정도, 임상 진단, 성격 또는 실제 생활능력 전체를 의미하지 않는다.

프로파일 계산은 백엔드의 결정적 규칙으로 수행한다. LLM은 점수나 비율을 계산하지 않으며, 완성된 프로파일을 입력받아 시뮬레이션을 생성하는 역할만 담당한다.

---

## 2. 현재 프로젝트 기준과 버전

개발 중인 현재 단계에서는 모든 규칙을 v1으로 유지한다.

```text
eventSchemaVersion: behavior-event-v1
normalizerVersion: behavior-normalizer-v1
registryVersion: behavior-event-registry-v1
measurementRuleVersion: behavior-measurement-rules-v1
profileVersion: behavior-profile-v1
profilePolicyVersion: behavior-profile-policy-v1
```

v1 규칙을 변경하면 기존 정규화 결과 및 프로파일 스냅샷을 개발 데이터에서 다시 생성한다. 서비스 운영 및 외부 배포를 시작한 뒤에는 기존 버전을 변경하지 않고 v2를 추가한다.

---

## 3. 기존 `MemberQuestProfile`과의 구분

현재 `MemberQuestProfile`은 다음과 같은 사용자 설정과 퀘스트 선호를 저장한다.

- 선호 난이도
- 기본 지원 수준
- 선호 수행 시간
- 하루 퀘스트 제한
- 선호 퀘스트 세부 카테고리

행동 로그에서 계산하는 프로파일과 목적이 다르므로 기존 `MemberQuestProfile`에 행동 평가값을 추가하지 않는다.

```text
MemberQuestProfile
└── 사용자 설정과 퀘스트 선호

BehaviorProfileSnapshot
└── 정규화 행동 로그에서 계산한 관찰 프로파일
```

시뮬레이션 생성 단계에서는 두 데이터를 별도로 읽어 하나의 LLM 입력 DTO로 조합한다.

---

## 4. 프로파일 입력 데이터

프로파일은 다음 테이블을 입력으로 사용한다.

| 입력 | 사용 목적 |
|---|---|
| `normalized_behavior_events` | 정규화 상태, 행동 결과, 독립·지원 수준, 유효성, 안전 상태, 근거 사용 범위 |
| `normalized_behavior_evidence` | `skillCode`, 긍정·부정·중립 방향, 주·보조 근거 구분 |
| `normalized_behavior_measurements` | 횟수, 시간, 비율, 관찰값과 누적값 |
| `behavior_session_integrity` | 완료된 세션과 순번 누락 세션 구분 |
| `behavior_logs` | 정규화 이벤트에 연결된 사용자, 세션, 과제 식별자와 버전만 사용 |

`behavior_logs`에서는 다음 그룹화 메타데이터만 읽는다.

```text
memberId
sessionId
taskId
taskVersion
gameId
difficulty
scenarioVariant
evidenceContext
```

프로파일이 원본 payload를 다시 해석하거나 원본 `eventCode`를 새로운 의미로 추론하지 않는다. 행동 결과와 측정값은 정규화된 값만 사용한다.

## 5. 프로파일 대상 이벤트 선택 규칙

### 5.1 공통 포함 조건

다음 조건을 모두 만족하는 이벤트만 수행률 계산에 포함한다.

```text
normalizationStatus == NORMALIZED
validityStatus == VALID
sessionIntegrity.status == COMPLETE
normalizerVersion == behavior-normalizer-v1
registryVersion == behavior-event-registry-v1
measurementRuleVersion == behavior-measurement-rules-v1
```

세션 무결성 상태별 처리는 다음과 같다.

| 상태 | 수행률 | 데이터량·해석 제한 |
|---|---|---|
| `COMPLETE` | 포함 | 정상 포함 |
| `OPEN` | 제외 | 진행 중 세션으로 기록 |
| `OPEN_WITH_GAPS` | 제외 | 진행 중이며 순번 누락 가능성 기록 |
| `GAPPED` | 제외 | 무결성 문제로 제외하고 유효성 프로파일에 반영 |
| 세션 무결성 없음 | 제외 | `MISSING_SESSION_INTEGRITY` 제한 사유 기록 |

### 5.2 `EvidenceUse`별 사용 범위

| `EvidenceUse` | 사용 위치 |
|---|---|
| `ASSESSMENT_PRIMARY` | 독립·지원 수행률, 신뢰도, 강점·어려움 |
| `TRAINING_PROGRESS` | 훈련 회기 변화, 지원 수준 변화 |
| `CONTEXT_ONLY` | 행동 패턴과 추가 평가 필요 상태 |
| `ACCESSIBILITY_ONLY` | 유효성·접근성 요약 |
| `SAFETY_ONLY` | 안전 프로파일 |
| `EXCLUDED` | 수행률에서 제외하고 전체 제외 건수에만 반영 |

`QUARANTINED` 이벤트는 점수와 비율에서 제외하고 격리 건수와 `normalizationIssues`만 집계한다.

## 6. measurement 집계 규칙

`normalized_behavior_measurements.valueSemantics`에 따라 집계 방법을 고정한다.

| `ValueSemantics` | 집계 방법 |
|---|---|
| `DELTA` | 선택한 기간 안에서 합계 |
| `SNAPSHOT` | 같은 세션·같은 `metricCode`의 가장 높은 `eventSequence` 값 사용 |
| `DURATION` | 기본값은 중앙값, 총시간이 필요한 지표만 합계 |
| `TARGET` | 관찰값과 같은 이벤트의 목표값으로만 사용하고 단독 합계하지 않음 |
| `OBSERVATION` | 비율은 평균, 금액·수량은 지표 정의에 따라 평균 또는 중앙값 |

동일 이벤트에 같은 `metricCode`가 여러 번 존재하면 `(normalizedEventId, metricCode, valueSemantics)` 기준으로 한 번만 사용한다.

값이 없으면 `0`으로 대체하지 않는다. 계산 가능한 분모나 관찰값이 없으면 결과는 `null`이다.

## 7. 프로파일 데이터

### 7.1 기술 근거별 수행 프로파일

현재 정규화 결과에는 고정된 6개 능력영역이 아니라 이벤트 레지스트리의 세부 `skillCode`가 저장된다. 따라서 v1 프로파일은 `skillCode`별로 생성한다.

예시:

```text
EXECUTIVE_FUNCTION
FUNCTIONAL_COMMUNICATION
SPATIAL_NAVIGATION
NUMERACY
MONEY_MANAGEMENT
SAFETY_AWARENESS
DAILY_LIVING
HELP_SEEKING
```

`BehaviorDomain`은 장보기·요리·안전 같은 시뮬레이션 영역이며 `skillCode`와 다른 축이다. 프로파일은 두 값을 서로 대체하지 않는다.

| 프로파일 데이터 | 계산 |
|---|---|
| `skillCode` | `normalized_behavior_evidence.skillCode` |
| `independentSuccessRate` | 독립 평가 근거의 긍정 수 / 독립 평가 가능 근거 수 × 100 |
| `supportedSuccessRate` | 지원 평가 근거의 긍정 수 / 지원 평가 가능 근거 수 × 100 |
| `independentEvaluableEvidenceCount` | 독립 근거 중 `POSITIVE` 또는 `NEGATIVE` 수 |
| `supportedEvaluableEvidenceCount` | 지원 근거 중 `POSITIVE` 또는 `NEGATIVE` 수 |
| `neutralEvidenceCount` | `NEUTRAL` 근거 수 |
| `primaryEvidenceCount` | `EvidenceRole.PRIMARY`인 고유 이벤트 수 |
| `secondaryEvidenceCount` | `EvidenceRole.SECONDARY`인 고유 이벤트 수 |
| `distinctTaskCount` | 고유 `(taskId, taskVersion)` 수 |
| `distinctBehaviorDomainCount` | 고유 `BehaviorDomain` 수 |
| `distinctSessionCount` | 고유 완료 세션 수 |
| `confidence` | 8장의 v1 신뢰도 정책 적용 |
| `observedStrengths` | 반복된 긍정 이벤트 코드 요약 |
| `observedDifficulties` | 반복된 부정 이벤트 코드와 오류 유형 요약 |
| `interpretationLimits` | 데이터 부족, 특정 과제 집중, 제외율, 세션 무결성 문제 |

독립 근거는 다음 조건이다.

```text
evidenceUse == ASSESSMENT_PRIMARY
independenceLevel == INDEPENDENT
evidenceDirection IN (POSITIVE, NEGATIVE)
```

지원 근거는 다음 조건이다.

```text
evidenceUse == ASSESSMENT_PRIMARY
independenceLevel IN (
    SUPPORTED_LEVEL_1,
    SUPPORTED_LEVEL_2,
    SUPPORTED_LEVEL_3
)
evidenceDirection IN (POSITIVE, NEGATIVE)
```

`ASSISTED`는 현재 조력자 개입에 의해 `EXCLUDED`가 될 수 있으므로 supported 수행률에 포함하지 않는다.

성공률 계산식은 다음과 같다.

```text
successRate = positiveEvidenceCount
              / (positiveEvidenceCount + negativeEvidenceCount)
              * 100
```

분모가 0이면 `null`이다. `NEUTRAL`은 데이터량에는 표시하지만 성공률 분모에는 포함하지 않는다.

독립 수행률과 지원 수행률은 서로 다른 근거 집합일 수 있으므로 두 값을 빼서 `supportGain`을 만들지 않는다.

### 7.2 관찰 근거 요약

강점과 어려움은 LLM이 생성하지 않고 이벤트 코드를 기준으로 백엔드가 구조화한다.

```java
public record ObservedEvidenceSummary(
    String eventCode,
    ObservedOutcome outcome,
    IndependenceLevel independenceLevel,
    ErrorType errorType,
    int observationCount
) {}
```

강점 후보:

```text
outcome == SUCCESS
direction == POSITIVE
observationCount >= 2
```

어려움 후보:

```text
outcome IN (FAILURE, INCOMPLETE)
또는 direction == NEGATIVE
observationCount >= 2
```

단일 관찰은 강점이나 어려움으로 확정하지 않고 `interpretationLimits`에 “반복 확인 필요”로 남긴다.

---

### 7.3 지원 수준 프로파일

현재 정규화 결과에서는 지원 종류별 전후 효과를 안정적으로 비교할 수 없으므로 `SupportType`별 효과와 `supportGain`은 생성하지 않는다.

v1에서는 현재 저장된 지원 수준과 measurement만 사용한다.

| 프로파일 데이터 | 계산 |
|---|---|
| `levelObservations` | `IndependenceLevel`별 근거 수와 성공률 |
| `averagePromptLevel` | 평가·훈련 이벤트의 `promptLevel` 평균 |
| `totalSupportCount` | 각 완료 세션의 마지막 `supportCountSnapshot` 합계 |
| `medianHelpRequestLatencyMs` | `helpRequestLatencyMs` 중앙값 |
| `supportedSessionCount` | 지원 수준 이벤트가 하나 이상 있는 고유 완료 세션 수 |

```java
public record SupportLevelObservation(
    IndependenceLevel independenceLevel,
    int evaluableEvidenceCount,
    Double successRate
) {}

public record SupportProfile(
    List<SupportLevelObservation> levelObservations,
    Double averagePromptLevel,
    Integer totalSupportCount,
    Long medianHelpRequestLatencyMs,
    int supportedSessionCount
) {}
```

---

### 7.4 훈련 변화 프로파일

`TRAINING_PROGRESS` 이벤트를 `(taskId, taskVersion, sessionId)`로 그룹화한다.

```java
public record TrainingSessionObservation(
    UUID sessionId,
    UUID taskId,
    String taskVersion,
    Integer difficulty,
    String scenarioVariant,
    Instant startedAt,
    Instant endedAt,
    int evaluableEvidenceCount,
    Double successRate,
    Integer supportCount,
    Double averagePromptLevel
) {}
```

같은 `taskId`와 `taskVersion`의 완료 세션을 `endedAt` 순서로 정렬해 변화만 보여준다. 난이도나 `scenarioVariant`가 다르면 직접적인 향상·감소값을 계산하지 않는다.

현재 데이터에는 훈련·사후검사·유지검사·전이검사를 구분하는 메타데이터가 없으므로 다음 값은 v1에서 생성하지 않는다.

- `scoreGain`
- `maintenanceScore`
- `maintenanceInterval`
- `transferScore`
- `transferContext`

---

### 7.5 안전 프로파일

안전은 일반 수행률과 분리한다.

| 프로파일 데이터 | 계산 |
|---|---|
| `overallStatus` | 포함된 안전 이벤트 중 가장 높은 `SafetyStatus` |
| `redEventCount` | `safetyStatus == RED`인 고유 이벤트 수 |
| `yellowEventCount` | `safetyStatus == YELLOW`인 고유 이벤트 수 |
| `nearMissCount` | `NEAR_MISS` flag가 있는 고유 이벤트 수 |
| `repeatedSafetyEventCodes` | 두 번 이상 나타난 `sourceEventCode` |
| `professionalReviewRecommended` | RED가 하나 이상이거나 동일 YELLOW 코드가 두 번 이상이면 `true` |

안전 프로파일은 `EvidenceUse.SAFETY_ONLY`와 명시적인 `safetyStatus`가 있는 이벤트를 사용한다. `RED` 사건이 있더라도 다른 수행률과 평균내어 완화하지 않는다.

---

### 7.6 평가 유효성 프로파일

유효성 프로파일은 전체 정규화 이벤트를 대상으로 계산한다.

| 프로파일 데이터 | 계산 |
|---|---|
| `validEventCount` | `validityStatus == VALID`인 `NORMALIZED` 이벤트 수 |
| `invalidEventCount` | `VALID`이 아닌 `NORMALIZED` 이벤트 수 |
| `quarantinedEventCount` | `normalizationStatus == QUARANTINED` 이벤트 수 |
| `validityStatusCounts` | `ValidityStatus`별 이벤트 수 |
| `normalizationIssueCounts` | `NormalizationIssue.issueCode`별 수 |
| `openSessionCount` | `OPEN`, `OPEN_WITH_GAPS` 세션 수 |
| `gappedSessionCount` | `GAPPED` 세션 수 |
| `excludedEventRate` | `(invalid + quarantined) / 전체 이벤트 수` |

현재 정규화 결과만으로 조작 보정 통과 여부와 선호 지시방식을 확정할 수 없으므로 다음 필드는 생성하지 않는다.

- `controllerCalibrationPassed`
- `preferredInstructionMode`
- 세분화된 원본 `InvalidReason` 목록
- `requiredAdjustments`

대신 `ValidityStatus`와 `normalizationIssues`를 그대로 제공한다.

---

### 7.7 관찰 행동 패턴

현재 정규화 결과로 분모를 명확히 계산할 수 있는 지표만 생성한다.

| 프로파일 데이터 | 계산 |
|---|---|
| `selfCorrectionRate` | `SELF_CORRECTED` flag 이벤트 수 / `errorType != NONE`인 유효 이벤트 수 |
| `repeatedErrorRate` | `errorType == REPETITION`인 이벤트 수 / `errorType != NONE`인 유효 이벤트 수 |
| `helpRequestCount` | 도움요청 eventCode의 유효 이벤트 수 |
| `medianHelpRequestLatencyMs` | `helpRequestLatencyMs` 중앙값 |
| `medianStartLatencyMs` | `startLatencyMs` 중앙값 |
| `averagePathEfficiency` | 같은 `taskVersion` 안의 `pathEfficiency` 평균 |

도움 요청 eventCode는 v1 레지스트리에서 다음 코드를 사용한다.

```text
COMMON.HELP_REQUEST
SHOP.STAFF_HELP_REQUESTED
WORK.SUPERVISOR_HELP_REQUESTED
LOST.HELP_REQUESTED
```

현재 정규화 결과에는 재시도 기회, 도움요청 기회, 지도 사용 가능 조건이 없으므로 다음 값은 생성하지 않는다.

- `retryAfterFailureRate`
- `helpRequestOpportunityRate`
- `mapUsagePattern`

`averagePathEfficiency`는 서로 다른 `taskVersion`을 합쳐 계산하지 않는다.

---

### 7.8 추가 평가 필요 상태

추가 평가 필요 상태는 낮은 수행이 아니라 증거 부족 또는 상충을 나타낸다.

```java
public record EvidenceGap(
    String skillCode,
    EvidenceGapType type,
    String reason,
    String recommendedEvidence
) {}

public enum EvidenceGapType {
    NO_ASSESSMENT_EVIDENCE,
    INSUFFICIENT_EVIDENCE,
    SINGLE_TASK_ONLY,
    SINGLE_SESSION_ONLY,
    CONFLICTING_RESULTS,
    HIGH_EXCLUSION_RATE,
    SESSION_INTEGRITY_PROBLEM
}
```

`needsMoreAssessment`는 `Set<String>` 형태의 `skillCode` 집합으로 저장한다. 현재 프로젝트에 없는 `AbilityDomain` enum은 사용하지 않는다.

## 8. v1 신뢰도 정책

신뢰도는 수행률의 높고 낮음이 아니라 근거량과 다양성을 나타낸다.

```java
public enum ConfidenceLevel {
    INSUFFICIENT,
    LOW,
    MEDIUM,
    HIGH
}
```

`skillCode`별 신뢰도는 다음 순서로 계산한다.

| 등급 | v1 조건 |
|---|---|
| `INSUFFICIENT` | 평가 가능 근거가 0개 |
| `LOW` | 평가 가능 근거가 1~4개이거나 완료 세션이 1개뿐임 |
| `MEDIUM` | 평가 가능 근거 5개 이상, 서로 다른 과제 2개 이상, 완료 세션 2개 이상 |
| `HIGH` | 평가 가능 근거 10개 이상, 서로 다른 과제 3개 이상, 행동영역 2개 이상, 완료 세션 3개 이상, 전체 제외율 15% 이하 |

상위 조건을 만족하지 못하면 바로 아래 등급을 사용한다. `GAPPED` 세션의 이벤트는 평가 가능 근거에 포함하지 않는다.

이 임계값은 공인 기준이 아니라 개발 단계의 보수적인 내부 규칙이다. 모든 원시 카운트를 프로파일에 함께 저장해 이후 정책을 바꿔도 결과를 재검증할 수 있게 한다.

## 10. 프로파일 저장 구조

프로파일은 갱신 가능한 사용자 한 행이 아니라 생성 시점의 입력과 정책을 보존하는 스냅샷으로 저장한다.

### 10.1 `behavior_profile_snapshots`

| 컬럼 | 설명 |
|---|---|
| `id` | 프로파일 스냅샷 ID |
| `member_id` | 내부 사용자 FK |
| `profile_version` | `behavior-profile-v1` |
| `profile_policy_version` | `behavior-profile-policy-v1` |
| `normalizer_version` | 입력 정규화 버전 |
| `registry_version` | 입력 이벤트 레지스트리 버전 |
| `measurement_rule_version` | 입력 측정 규칙 버전 |
| `evidence_from` | 입력 기간 시작 |
| `evidence_to` | 입력 기간 종료 |
| `input_event_count` | 입력 이벤트 수 |
| `profile_data` | `BehaviorProfileData` JSONB |
| `generated_at` | 생성 시각 |

### 10.2 `behavior_profile_evidence_links`

| 컬럼 | 설명 |
|---|---|
| `profile_id` | 프로파일 스냅샷 FK |
| `normalized_event_id` | 사용하거나 제외한 정규화 이벤트 FK |

`behavior_profile_evidence_links`를 저장해 프로파일 결과에서 정규화 이벤트까지 역추적할 수 있게 한다.

## 11. 생성 순서

```text
1. memberId와 입력 기간 결정
2. v1 정규화 이벤트 조회
3. 세션 무결성 및 유효성 분류
4. evidence를 skillCode별로 그룹화
5. 독립·지원 성공률 계산
6. measurement 의미에 따라 집계
7. 훈련 회기·안전·유효성·행동 패턴 계산
8. 신뢰도와 evidenceGap 계산
9. BehaviorProfileSnapshot 저장
10. 사용·제외 이벤트의 evidence link 저장
11. LLM 입력용 익명 DTO 생성
```

프로파일 조회는 N+1 쿼리를 피하기 위해 이벤트 ID 목록으로 evidence와 measurement를 한 번에 조회한다.

```text
findNormalizedEvents(memberId, versions, evidenceFrom, evidenceTo)
findEvidenceByNormalizedEventIdIn(eventIds)
findMeasurementsByNormalizedEventIdIn(eventIds)
```

## 12. LLM 입력 경계

내부 프로파일 스냅샷은 `memberId` FK로 저장한다. LLM에는 실제 `memberId`, `sessionId`, `taskId`, 원본 이벤트 ID를 전달하지 않는다.

```java
public record LlmBehaviorProfileInput(
    String anonymousUserId,
    String profileVersion,
    Map<String, SkillPerformanceProfile> skills,
    SupportProfile supportProfile,
    SafetyProfile safetyProfile,
    BehaviorPatternProfile behaviorPatternProfile,
    Set<String> needsMoreAssessment,
    List<EvidenceGap> evidenceGaps,
    List<String> interpretationLimits
) {}
```

LLM 입력에는 다음 정보만 포함한다.

- 계산이 완료된 성공률과 데이터량
- 관찰된 이벤트 요약
- 안전 상태
- 효과가 아니라 현재 관찰된 지원 수준
- 추가 평가가 필요한 `skillCode`
- 결과 해석 제한

LLM이 원본 로그를 다시 해석하거나 사용자 능력점수를 재계산하게 하지 않는다.

## 13. v1에서 생성하지 않는 데이터

다음 데이터는 현재 정규화 결과만으로 정확하게 만들 수 없어 프로파일 스키마에서 제외한다.

- 고정된 6개 `AbilityDomain`
- 독립점수와 지원점수의 차이인 `supportGain`
- `SupportType`별 효과와 `effectiveSupports`
- 선호 지원방식
- 사전·사후 `scoreGain`
- 유지검사와 전이검사 결과
- 조작 보정 통과 여부
- 선호 지시방식
- 세분화된 접근성 조정 추천
- 재시도 기회 기반 비율
- 도움요청 기회 기반 비율
- `mapUsagePattern`

해당 값이 필요해지면 먼저 정규화 입력에 명시적인 분자·분모 또는 비교조건을 추가한 뒤 프로파일에 포함한다. 프로파일 계산 단계에서 원본 행동을 추정해 채우지 않는다.

## 14. 근거 및 해석 원칙

| 원칙 | 현재 프로젝트 적용 |
|---|---|
| 원본과 판단 분리 | 원본 → 정규화 → 프로파일 스냅샷으로 분리 |
| 평가와 훈련 분리 | `EvidenceUse`로 수행률과 훈련 변화를 구분 |
| 접근성 오류 제외 | `ValidityStatus`와 `normalizationIssues` 사용 |
| 안전 별도 관리 | `SafetyStatus`를 일반 성공률과 평균내지 않음 |
| 데이터 부족과 실패 구분 | 분모가 없으면 `null`, 신뢰도는 `INSUFFICIENT` |
| 단일 행동 과잉해석 방지 | 반복 횟수와 distinct task/session을 함께 저장 |
| 결과 재현성 | 모든 입력·정책 버전을 스냅샷에 저장 |

참고 설계 원칙은 WHO ICF, ETS Evidence-Centered Design, Evidence Trace File, PASS, EFPT, Testing Standards와 수행평가의 일반화 가능성 원칙을 사용한다. 이 자료들은 프로젝트의 성공률 임계값이나 진단 기준을 제공하지 않으므로 프로파일은 게임 안에서 관찰된 수행 결과로만 해석한다.

MVP 프로파일은 확정 진단이 아니라 다음 시뮬레이션의 과제·지원 수준·추가 평가 필요 조건을 결정하기 위한 입력으로 사용한다.

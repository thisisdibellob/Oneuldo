# 장보기 환경 변수 구현 · 진욱 → 정우·재현 인수인계

작성일: 2026-09-11

**현재 팀 전달본:** [장보기 환경 통합 보고서](market-team-report-2026-09-11.md). 이 문서 아래의 4분류·96종·계산대 1개·계산원 0~1명·단독 의자 설정과 검증 수치는 최초 구현 당시의 기록이다. 현재 상태는 통합 보고서와 [AI 실행 인터페이스](../frontend/docs/market-agent-contract.md)를 따른다.

최신 배치와 규칙은 [마트 구조 개편 v2 보고서](market-layout-v2.md)를 우선한다. 생활용품을 포함한 5분류, 세로 계산대 2개·계산원 0~2명, 입구 경보기와 점수, 입·출구 분리, 고정 휴게석·엘리베이터·ATM을 추가했다.

추가 변경: NPC·계산대 축소, 절반 크기의 쌍 진열대, 마트 1.3배 확대, UI 전환은 [마트 화면 수정 보고서](market-visual-refinement.md)에 정리했습니다.

마트를 반복 가능한 실험 환경으로 바꾸고, 사람과 이후 AI 실행기가 같은 구매·재시도·종료 규칙을 사용하도록 구성했습니다. 실행 전에 seed, 공간 배치, 상품과 수량, 정답 판정 난이도를 지정할 수 있습니다. 실행 결과는 설정과 행동 기록을 함께 가진 JSON 에피소드로 내보냅니다.

## 진욱이 직접 확인하고 팀에 전달하는 순서

1. `Oneuldo/frontend`에서 `pnpm web`으로 실행합니다. 일반 앱은 **게임 → 출발하기 → 마을의 하늘마트**로 들어가며, 개발 웹에서는 `http://localhost:8081/?marketLab=1`로 바로 확인할 수 있습니다.
2. 장보기 시작 전 **연습 환경 설정**을 엽니다. 사람 수, 기둥·의자 수, 계산원, 무인 계산대, 진열대 배치, 상품 조건과 재고를 바꾸고 **설정 적용**을 누릅니다. 상세 상품 목록과 후보 위치를 바꾸려면 **연구용 상세 설정 · JSON 가져오기**에 설정을 붙여 넣습니다.
3. **설정 JSON 저장**으로 동일 조건을 보관합니다. 정우·재현에게 이 JSON과 아래 인터페이스 문서를 같이 전달하면 같은 배치로 실험할 수 있습니다. 한 게임 안에서는 조건이 유지되고, 새 게임 시작 전에 바꿉니다.
4. 장보기에서 구매를 확정하고 재시도하거나 포기한 뒤 별점을 남기거나 건너뜁니다. **게임 기록 저장**으로 행동·결과 JSON을 받습니다. 완료 기록은 시작 화면의 **이전 게임 기록**에서도 다시 열 수 있습니다.
5. 상품 ID와 변형별 이름은 [상품 카탈로그 보고서](design-concepts/2026-09-11-market-product-catalog.md), 모델 연결 규격은 [AI 인터페이스 문서](../frontend/docs/market-agent-contract.md)를 참고합니다. 이 보고서를 전달용 문서로 사용하면 됩니다.

Expo 개발 서버가 다른 포트를 표시하면 위 주소의 포트를 맞춥니다. 이번 변경으로 추가한 런타임 패키지는 없습니다.

## 카카오 대화에서 요청한 범위

첨부 대화의 작업 분담은 정우·재현이 각자의 페르소나 AI를 준비하고, 진욱이 AI가 다음 주에 플레이할 장보기 환경을 조절할 수 있게 하는 것입니다. 이때 ‘환경 변수’는 PC의 `.env` 비밀값이나 서버 접속 주소가 아니라, 플레이 상황을 만드는 게임 설정값으로 해석했습니다.

같은 AI가 같은 마트에서만 반복하면 공간 배치나 특정 상품 위치에만 맞는 기록을 얻기 쉽습니다. 그래서 seed로 환경을 재현하면서 진열대 위치, 진열 상품과 재고, 사람·장애물, 계산원 유무, 구매 조건을 바꿀 수 있게 했습니다. 다른 페르소나에 동일한 seed와 설정을 주면 같은 조건에서 행동을 비교할 수 있습니다.

게임 설정은 실험 조건, 이동·담기·수정·직원 요청·재시도는 그 조건에서 발생한 행동, 최종 성공/포기와 별점은 결과 기록입니다. 기존 AI 분석·퀘스트 생성 파이프라인과 연결할 때에는 에피소드 식별자로 대응시키면 됩니다. 현재 작업은 프론트엔드와 로컬 실행 인터페이스이며, 백엔드나 기존 분석 파이프라인을 실제로 수정·호출하지 않았습니다.

| 7 | 유인 계산대 한 개 | 계산대 구조는 항상 한 개 존재. 계산원 실제 배치 여부만 별도 제어 |

요청 10의 ‘12개 배치’와 ‘9개 랜덤 선정’은 **9개의 서로 다른 상품을 선택하고 3칸에 그중 일부를 반복 진열**하는 것으로 함께 충족했습니다. 반복 진열된 같은 SKU를 별도 재고로 세지 않습니다.

## 환경 설정 항목

환경 설정은 `frontend/src/game/marketEnvironment.ts`의 `MarketEnvironmentConfig`입니다.

| 필드 | 허용값 | 의미 |
| --- | --- | --- |
| `seed` | 문자열 또는 유한 숫자 | 같은 입력의 배치를 재현하는 기준 |
| `employeeCount` | 1~3 또는 `{min,max}` | 계산원과 별개인 매장 종업원 수 |
| `customerCount` | 1~5 또는 `{min,max}` | 손님 수 |
| `pillarCount` | 0~4 또는 `{min,max}` | 기둥 수 |
| `chairCount` | 0~4 또는 `{min,max}` | 의자 수 |
| `cashierCount` | `0`, `1`, `'random'` | 처음부터 계산원이 있는지 |
| `kioskPresent` | `false`, `true`, `'random'` | 작동하지 않는 무인 계산대의 존재 여부 |
| `shelfOrder` | `fresh`, `produce`, `meal`, `drink`를 한 번씩 | 북서·북동·남서·남동의 분류 배치. 생략하면 랜덤 |
| `employeeSlotIds` | 종업원 후보 위치 ID 배열 | 종업원 랜덤 선정 후보를 제한 |
| `customerSlotIds` | 손님 후보 위치 ID 배열 | 손님 랜덤 선정 후보를 제한 |
| `pillarSlotIds` | 기둥 후보 위치 ID 배열 | 기둥 랜덤 선정 후보를 제한 |
| `chairSlotIds` | 의자 후보 위치 ID 배열 | 의자 랜덤 선정 후보를 제한 |

위치는 `MARKET_SHELF_SLOTS`, `MARKET_EMPLOYEE_SLOTS`, `MARKET_CUSTOMER_SLOTS`, `MARKET_PILLAR_SLOTS`, `MARKET_CHAIR_SLOTS`에 있습니다. 예를 들어 진열대는 `northwest/northeast/southwest/southeast` 네 자리이며, 종업원 위치에는 `staff-west-aisle`, `staff-east-aisle` 등이 있습니다. 임의 좌표 입력 대신 통행 가능한 후보를 선택하므로 사람이 진열대 안이나 계산대 위에 생기는 배치를 피합니다. 값 범위와 후보 ID 오류는 입력 단계에서 거부합니다.

생성된 환경에는 설정값뿐 아니라 실제 결정된 `shelves`, `employees`, `customers`, `objects`, `checkout`, `stations`, `obstacles`, `spawn`, `exit` 좌표가 저장됩니다. 따라서 다음에 코드가 바뀌어도 원래 실험에서 어떤 배치가 사용됐는지 확인할 수 있습니다.

## 상품·구매 조건 설정

| 필드 | 의미 |
| --- | --- |
| `difficulty` | `family`: 같은 품목군이면 통과. `exact`: 지정 SKU만 통과 |
| `objectives` | `{productId, quantity, match?}`. 필요한 품목과 수량, 선택적으로 개별 판정 규칙 지정 |
| `stockPerProduct` | 기본 재고 1~99개 |
| `stockOverrides` | 특정 SKU 재고를 0~99개로 지정 |
| `inventoryProductIds` | 각 분류의 진열 9종을 직접 고정. 생략하면 seed로 선택 |

예를 들어 `{productId:'low-fat-milk', quantity:2, match:'family'}`는 ‘우유 2개’로 표시하고 일반·저지방·초코 등 같은 우유군의 수량을 합쳐 판정합니다. `match:'exact'`이면 ‘저지방 우유 2개’로 표시하고 해당 상품만 통과합니다. 왕란·특란, 일반·제로 콜라도 같은 방식으로 구분합니다.

기본 생성은 구매 조건에 필요한 상품과 유사 변형을 진열에 포함합니다. 수량보다 실제 재고가 적거나, 같은 품목군 조건이 겹쳐 판정이 모호하거나, 한 분류의 필수 상품이 9종을 초과하는 설정은 실행 전에 오류를 냅니다. 설정을 몰래 바꾸어 성공시키지 않습니다. 현재 구매의 정오 판정은 품목과 정확한 수량을 사용합니다. 가격·장바구니 합계는 표시하지만 예산 초과를 별도 실패 조건으로 사용하지 않습니다.

## 플레이어에게 공개되는 정보

마트에서 물건을 담는 중에는 정답 상품 강조, 맞춘 개수, `1/2` 같은 진행률, 틀린 품목 알림을 제공하지 않습니다. 계산대에 도착해도 구매 확정 전에는 정답을 판정하지 않습니다.

첫 구매 확정이 틀리면 성공하지 못했다는 결과만 알려 줍니다. 재시도 후 두 번째 이상 확정이 틀리면 어느 품목과 수량이 다른지 공개합니다. 재시도 제한은 없으며, 포기하면 그 시점까지의 구매 제출 횟수와 실패(포기)를 기록합니다. 계산대 방문, 잘못된 행동 요청, 직원 호출은 제출 횟수를 늘리지 않습니다.

난이도 별점은 1점 ‘쉬웠어요’부터 5점 ‘어려웠어요’, 흥미는 1점 ‘재미없었어요’부터 5점 ‘재미있었어요’입니다. 각 항목의 방향을 화면에 적고 둘 다 기록하거나 평가를 건너뛸 수 있습니다.

## 다음 주 AI 연결 방법

자세한 타입·호출 예시는 [장보기 AI 인터페이스](../frontend/docs/market-agent-contract.md), 실제 설정 파일은 [환경 설정 예시](../frontend/docs/market-environment.example.json)를 참고합니다.

```ts
import { createMarketAgentAdapter } from './frontend/src/game/marketSession';

const game = createMarketAgentAdapter({
  seed: 'compare-personas-001',
  sessionId: 'persona-a-run-001',
  startedAt: new Date().toISOString(),
  difficulty: 'exact',
  objectives: [{ productId: 'low-fat-milk', quantity: 2 }],
  environment: { cashierCount: 0, customerCount: 5 },
  provenance: { source: 'synthetic', agentModel: '실제 모델/버전', personaId: 'persona-a', personaVersion: '1' },
});

const observation = game.observe();
const next = game.act({ type: 'move', dx: 0, dy: -20, at: new Date().toISOString() });
// 모델이 next를 읽고 다음 행동을 선택하도록 연결합니다.
// 종료 후 game.exportEpisode()로 전체 자료를 받습니다.
```

행동은 `move`, `interact`, `add`, `remove`, `closeStation`, `viewCart`, `viewHelp`, `closeView`, `checkout`, `requestCashier`, `submit`, `retry`, `giveUp`, `rate`, `skipRating`입니다. 상품 담기에는 해당 진열대 접근, 계산 요청에는 해당 직원 접근·대화, 구매 확정에는 계산대 접근과 계산원 배치가 필요합니다. `exit`에 가까이 가서 상호작용하면 포기로 종료되며, 명시적 `giveUp`은 어디서든 가능합니다. 진열대·대화·장바구니·도움 화면을 닫은 후 이동합니다. `move`는 한 번에 32px 이하이고 경로 충돌을 검사하므로 위치를 순간이동시키는 행동으로 과정을 생략할 수 없습니다.

구조화된 관측은 마트 전체 위치 정보를 보여 주되, 상품과 재고는 실제로 접근하여 연 진열대만 공개합니다. 장바구니도 직접 열거나 계산·종료 화면일 때만 보이며 평소에는 `null`입니다. 따라서 모델도 목록을 보고 기억하고 진열대를 찾아 확인하며, 담은 수량을 보려면 장바구니를 여는 행동이 필요합니다. 사람의 실제 시야나 시각 인지를 복제한 화면 기반 에이전트는 아닙니다. 현재 게임 화면용 상태 동기화 함수의 `setPosition`은 실제 조이스틱 이동 결과를 받아 기록하는 신뢰된 UI 전용 경로이고, AI 어댑터에서는 차단합니다.

진열대 화면 안에서 장바구니를 펼치면 해당 진열대와 장바구니가 함께 보이며, 물건을 계속 담거나 뺄 수 있습니다. 진열대를 닫고 일반 장바구니만 열었을 때는 상품을 원격으로 담을 수 없습니다.

## JSON 기록

종료 후의 `exportMarketEpisode()`는 다음 내용을 제공합니다.

```text
schema/version/sessionId/seed
provenance                         사람 또는 합성, 모델/페르소나 버전
config/environment                 실험 입력과 실제 공간 스냅샷
objectives/shelfSlots/initialStock  구매 조건, 진열 배열, 최초 재고
finalCart/finalStock                최종 장바구니와 재고
attempts/outcome                    제출 횟수, success 또는 gave-up
ratings/ratingSkipped              두 별점 또는 건너뛰기
events[]                           순번, 시각, 행동 유형, 행동별 자료
```

이벤트 유형에는 `session_started`, `player_moved`, `station_interacted`, `cashier_requested`, `cart_viewed`, `help_viewed`, `view_closed`, `cart_changed`, `purchase_submitted`, `retry_started`, `session_finished`, `ratings_submitted`, `ratings_skipped`, `action_rejected`가 있습니다. 구매 제출에는 내부 전체 평가와 실제 사용자에게 공개한 피드백을 둘 다 남깁니다. 이는 종료 후 연구 자료이며, 행동을 고르는 AI에게 제공하는 `observe()` 결과에는 포함하지 않습니다. 진행 중 연구용 내보내기는 차단합니다.

실제 수집에서는 `startedAt`과 각 행동의 `at`에 실행 시각을 전달합니다. 생략 시 기본 논리 시계로 재현 가능한 시각을 만들므로 그 기록을 실제 반응 시간으로 해석하면 안 됩니다. 화면에서는 실제 시각을 전달하며, 이동 기록은 화면 이동을 일정 간격으로 표본 수집하므로 프레임마다의 완전한 연속 궤적은 아닙니다.

사람 플레이는 `source:'human'`, AI는 `source:'synthetic'`로 저장합니다. 어댑터는 합성 출처, 모델, 페르소나 ID를 요구합니다. 페르소나 AI의 행동을 실제 장애인 집단의 특성이나 임상적 근거로 표기하지 않습니다. 아래 스모크 테스트는 모델이나 장애 페르소나를 쓰지 않는 결정적 소프트웨어 검증기이고, 출처에도 이를 명시합니다.

이번 브라우저 조작 검증으로 생성된 `qa-purchase`, `qa-no-cashier` 시드의 기록은 UI 기능 확인용이며 실제 참여자 기록이 아닙니다. 일반 화면의 기본 `human` 설정으로 실행된 QA 기록이므로 학습·실험 데이터에서 제외합니다. 실제 AI 실험은 시작 전에 합성 출처와 모델·페르소나 정보를 지정하고 AI 어댑터로 실행합니다.

## 완료 기록의 로컬 보관

`frontend/src/game/marketEpisodeStore.ts`가 성공·포기 직후 기록을 보관하며, 같은 게임의 별점 입력이나 건너뛰기는 기존 기록에 갱신합니다. ‘이전 게임 기록’에서 다시 확인하고 JSON으로 저장할 수 있습니다.

- 웹은 해당 브라우저의 `localStorage`에 최근 최대 20회를 보관합니다. UTF-16 문자열 크기를 문자당 2바이트로 계산하여 5MiB 한도 안에서 오래된 기록부터 캐시에서 제외합니다. 그래서 기록이 크면 브라우저 재시작 후 남아 있는 횟수가 20회보다 적을 수 있습니다.
- 네이티브 앱은 현재 앱 프로세스의 메모리에 보관합니다. 앱을 완전히 종료한 뒤에도 남는 영구 저장은 이번 범위에 없으므로 JSON 공유로 별도 저장해야 합니다.
- 브라우저 저장이 차단되었거나 용량이 부족하면 게임은 계속되고 현재 세션 메모리에 보관합니다. 화면에 저장 상태를 알리고 JSON 저장·공유 경로를 제공합니다.
- 연구 자료를 서버나 외부 서비스로 자동 업로드하지 않습니다. 일반 사용자 기록과 합성 기록의 출처 정보도 JSON에 유지합니다.

개발 웹 서버가 8081 포트에서 실행 중이면 [장보기 개발 화면](http://localhost:8081/?marketLab=1)으로 직접 진입할 수 있습니다. 이 경로는 `__DEV__`가 참인 웹 개발 모드에서만 활성화되며, 일반 앱 로그인·게임 진입 과정과 분리된 UI 검증용 진입점입니다. 실제 개발 서버 포트가 다르면 해당 포트로 바꿉니다.

스모크 실행은 지도에서 충돌을 피하며 직원에게 이동하여 계산을 요청하고, 빈 장바구니로 한 번 실패한 뒤 진열대로 이동해 보이는 상품명을 읽어 담고, 두 번째 제출에서 성공하고, 평가를 건너뛴 에피소드를 만듭니다. 숨은 정답 SKU나 완료 내보내기를 읽어 행동을 선택하지 않습니다. 예시 파일은 `exact` 과제로 작성되어 있고 이 단순 검증 정책은 정확한 표시명 과제만 지원합니다. JSON 설정 경로는 `--config 경로`로 바꿀 수 있습니다.

## 남은 연결 업무

정우·재현은 모델에 관측을 전달하고 행동 JSON을 파싱하는 실행기를 연결하면 됩니다. 페르소나별 실행 ID, 모델 버전, 페르소나 버전, 실행 횟수와 공통 seed 목록을 남겨 주세요. 진행하지 않는 모델을 멈출 최대 스텝/시간 제한은 실행기에서 정하며, 제한 도달 시 `giveUp`과 수집 측 종료 사유를 보존해야 합니다.

에피소드 저장 API와 기존 분석·퀘스트 결과의 식별자 연결, 합성/실제 플레이 데이터를 분리한 검토, 실제 모델을 통한 반복 플레이와 품질 평가는 다음 단계입니다. 이번 구현만으로 모델 플레이, 서버 수집 또는 파인튜닝이 완료된 것은 아닙니다.

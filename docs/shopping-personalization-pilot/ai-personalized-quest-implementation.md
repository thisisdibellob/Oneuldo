# AI 사용자 상태 기반 장보기 퀘스트 생성 구현

## 1. 구현 결과

장보기 행동 데이터에서 생성된 사용자 프로파일을 Groq의 Qwen 모델에 전달하고, 모델이 다음 장보기 퀘스트의 난이도·품목·수량·예산·안내 문장을 생성하는 경로를 구현했다.

기존 `market-personalization-v1` 규칙은 더 이상 정상 생성 경로의 최종 퀘스트를 결정하지 않는다. AI 호출 또는 출력 검증이 실패했을 때만 안전한 대체 미션을 만드는 fallback으로 사용한다.

## 2. 전체 흐름

```text
장보기 플레이
  → 행동 로그 저장 및 정규화
  → 완료 세션 기반 행동 프로파일 생성
  → 언어·수리·돈 관리·실행 기능 근거를 비식별 LLM 입력으로 변환
  → Groq/Qwen이 추천 난이도 1~3과 조정값 생성
  → 서버가 난이도 범위·조정값 형식 검증 후 추천 스냅샷 저장
  → 같은 AI 추천 난이도로 Groq/Qwen이 맞춤 장보기 퀘스트 JSON 생성
  → 서버가 상품·수량·예산·문장·JSON 형식 검증
  → 통과: source=AI
  → 실패: 오류 이유를 넣어 1회 재생성
  → 재실패 또는 AI 장애: source=RULE_FALLBACK
  → 프론트 장보기 미션에 적용
  → 적용된 미션 ID와 난이도로 다음 행동 로그 수집
```

## 3. AI가 받는 사용자 상태

AI 입력에는 이름, 이메일, 장애 정보, IQ, 생년월일을 넣지 않는다. 다음과 같은 게임 행동 근거만 전달한다.

- 대상 기술별 독립 수행 성공률과 지원 수행 성공률
- 독립·지원 평가 근거 수
- 프로파일 신뢰도
- 반복 관찰된 강점과 어려움의 이벤트 코드
- 오류 유형
- 평균 지원 수준과 도움 요청 지연시간
- 세션 누락·제외 비율과 추가 평가가 필요한 기술
- 안전 관련 관찰 상태
- 사용자가 설정한 선호 난이도·지원 수준·세션 길이

프로파일이 없거나 신뢰도가 부족한 경우도 숨기지 않고 각각 `NO_PROFILE`, `INSUFFICIENT_EVIDENCE`로 AI에 전달한다. 이때 AI는 능력을 단정하지 않고 난이도 2의 관찰 가능한 기초 과제를 생성하도록 지시받는다.

## 4. AI가 동적으로 결정하는 항목

- 사용자 종합 추천 난이도 `1~3`
- 추천 품목 수, 수량 복잡도, 예산 압박, 문장 지원 수준
- 퀘스트 제목과 설명
- 목표 상품 `2~4개`
- 상품별 수량 `1~3개`
- 목표 상품 총액을 반영한 예산
- 시작 안내 `1~3문장`
- 계산대 확인 문장 2개
- 성공 문장
- 어떤 행동 근거를 반영했는지 보여 주는 조정 요약
- 짧은 판단 사유 코드

따라서 난이도 1·2·3을 정하는 고정 성공률 분기는 정상 AI 경로에 사용하지 않는다. 첫 AI 단계가 프로파일 전체를 보고 추천 난이도를 정하고, 두 번째 AI 단계가 그 난이도 안에서 과제를 구성한다. 서버 규칙은 AI 추천 실패 시에만 fallback으로 사용한다.

## 5. 서버가 고정하는 안전 경계

AI가 자유롭게 생성하더라도 다음 항목은 서버가 강제로 검증한다.

| 항목 | 허용 범위 |
|---|---|
| 상품 | 우유, 사과, 순한 카레, 오렌지 주스 |
| 품목 수 | 2~4개 |
| 수량 | 품목별 1~3개 |
| 예산 | 목표 총액 이상, 목표 총액+4,000원 이하 |
| 안내 | 1~3문장, 문장당 80자 이하 |
| 계산대 대화 | 정확히 2문장, 문장당 80자 이하 |
| 사유 코드 | 영문 대문자·숫자·밑줄 형식 |
| 금지 내용 | 의학적 진단, IQ·장애 추정, 실제 결제, 위험 행동, 시간 압박 |

AI가 허용되지 않은 상품을 만들거나 가격 계산을 잘못하면 해당 결과를 화면에 전달하지 않는다.

추천 난이도 생성도 서버 검증을 거친다. 난이도는 1~3, 품목 수는 2~4여야 하며 수량 복잡도·예산 압박·문장 지원은 정의된 enum만 허용한다. 퀘스트 생성 결과의 난이도가 앞서 저장한 AI 추천 난이도와 다르면 재생성 대상으로 처리한다.

## 6. API

```http
GET /api/market-personalization/quest
Authorization: Bearer <access-token>
```

핵심 응답 필드는 다음과 같다.

```json
{
  "source": "AI",
  "model": "qwen/qwen3.6-27b",
  "latencyMs": 1588,
  "personalizationMode": "NO_PROFILE",
  "promptVersion": "market-ai-quest-v1",
  "quest": {
    "difficulty": 2,
    "title": "첫 장보기: 우유와 사과",
    "budget": 5000,
    "objectives": [
      { "productId": "milk", "quantity": 1 },
      { "productId": "apple", "quantity": 1 }
    ]
  },
  "adaptationSummary": "행동 근거 부족으로 난이도 2의 관찰 가능한 과제 생성...",
  "reasonCodes": ["NO_EVIDENCE", "BASELINE_ASSESSMENT"]
}
```

`source`의 의미는 다음과 같다.

- `AI`: 모델 생성과 서버 검증을 모두 통과했다.
- `RULE_FALLBACK`: 모델 장애 또는 두 번의 출력 검증 실패로 규칙형 안전 미션을 사용했다.

## 7. 프론트 적용

로그인 토큰이 있으면 사용자가 마트에 진입할 때마다 AI 장보기 퀘스트 API를 호출한다. 직전 장보기 완료 후 다시 마트에 들어오면 갱신된 행동 프로파일로 새 퀘스트를 생성한다. 응답의 `quest`를 그대로 장보기 미션으로 사용하며, 행동 로그에는 AI가 만든 미션 ID, 난이도, 목표 수량, 예산이 기록된다.

개발 로그 예시는 다음과 같다.

```text
[market-personalization] AI quest applied
{
  source: "AI",
  model: "qwen/qwen3.6-27b",
  difficulty: 2,
  mode: "NO_PROFILE",
  summary: "...",
  reasons: ["NO_EVIDENCE", "BASELINE_ASSESSMENT"]
}
```

인증 만료나 API 연결 실패 시 프론트는 기존 기본 장보기 미션을 사용한다.

## 8. 실제 연결 검증

2026-08-29 로컬 PostgreSQL과 실제 Groq API를 사용해 다음 결과를 확인했다.

| 항목 | 결과 |
|---|---|
| 생성 출처 | `AI` |
| 모델 | `qwen/qwen3.6-27b` |
| 지연시간 | 1,588ms |
| 프로파일 상태 | `NO_PROFILE` |
| 생성 난이도 | 2 |
| 생성 목표 | 우유 1개, 사과 1개 |
| 생성 예산 | 5,000원 |
| 서버 검증 | 통과 |

이 결과는 테스트 계정에 행동 프로파일이 없었기 때문에 AI가 기초 평가용 퀘스트를 만든 사례다. 행동 프로파일이 쌓이면 같은 API가 능력별 성공률, 오류, 지원 수준을 포함한 입력으로 다시 생성한다.

## 9. 테스트

- AI JSON 정상 파싱과 퀘스트 반환
- 허용되지 않은 상품 생성 시 거부
- 검증 실패 시 1회 수정 생성
- 재실패 시 규칙형 fallback
- 기존 대중교통 AI 생성 회귀 테스트
- 프론트 타입 검사와 전체 Jest 테스트
- 백엔드 전체 Gradle 테스트

## 10. 생성 스냅샷 저장

Flyway `V28`에서 `market_ai_quest_generations` 테이블을 추가했다. AI 생성 요청 한 건마다 다음 정보를 영구 저장한다.

- 생성 ID와 사용자 ID
- 생성에 사용된 행동 프로파일 스냅샷 ID
- `AI` 또는 `RULE_FALLBACK` 출처
- 모델명, 전체 지연시간, 개인화 모드, 프롬프트 버전
- 1차·2차 AI 원문과 각 검증 실패 이유
- 서버 검증을 통과해 실제 적용한 최종 퀘스트 JSON
- fallback으로 전환된 최종 실패 이유
- 생성 시각

AI 원문은 실행하지 않고 JSONB 감사 데이터로만 보관한다. 프로파일이 없는 사용자는 `profile_snapshot_id`가 비어 있고, 프로파일이 생성된 이후부터 해당 스냅샷 ID가 연결된다.

실제 PostgreSQL 검증 결과는 다음과 같다.

```json
{
  "source": "AI",
  "model": "qwen/qwen3.6-27b",
  "attemptCount": 1,
  "questTitle": "첫 번째 장보기 미션",
  "profileLinked": false
}
```

## 11. 현재 한계

- 현재 허용 상품은 프론트에서 확실히 표시할 수 있는 4개로 제한했다.
- 프로파일이 갱신되지 않은 상태에서도 화면을 다시 열면 새로운 AI 미션이 생성될 수 있다.
- AI 판단은 임상 평가가 아니며 사용자 능력이나 장애 정도를 확정하는 근거로 사용하면 안 된다.
- 다음 검증에서는 실제 행동 프로파일이 있는 계정으로 약점·강점이 서로 다른 경우의 생성 차이를 비교해야 한다.

## 12. AI 생성 기록과 플레이 로그 연결

AI 생성 응답의 `generationId`를 장보기 플레이 세션까지 전달한다. 플레이 중 생성되는 모든
`behavior_logs` 이벤트에는 다음 `simulation` 문맥이 포함된다.

```json
{
  "simulation": {
    "questInstanceId": "AI 생성 감사 기록의 generationId",
    "contentSource": "GENERATED",
    "simulationStarted": true
  }
}
```

출처 매핑은 다음과 같다.

- AI 생성 성공: `GENERATED`
- 서버 규칙형 폴백: `FALLBACK`
- 로그인하지 않았거나 생성 API 호출에 실패해 기본 미션 사용: `STATIC`

AI 생성 성공과 규칙형 폴백은 모두 `market_ai_quest_generations.id`와 동일한
`quest_instance_id`를 저장한다. 따라서 생성 감사 데이터와 실제 플레이 이벤트를 ID로
조회할 수 있다. 재시도 플레이는 새 `session_id`를 발급하지만 동일한 퀘스트를 다시
수행하므로 기존 `quest_instance_id`를 유지한다.

이 변경 이전에 저장된 행동 로그의 `content_source`와 `quest_instance_id`는 소급하여
채우지 않는다. 변경 이후 새로 시작한 장보기 세션부터 값이 기록된다.

## 13. 사용자 능력 분석 화면

기존 하단 `AI` 탭을 `분석` 탭으로 교체했다. 이 화면은 보호자용 상세 대시보드가 아니라
사용자 본인이 최근 수행 기록을 간단히 확인하는 용도다.

- 전체 추천 난이도 1~3
- 언어 이해, 수 개념, 돈 관리 능력
- 능력별 독립 수행 성공률과 레벨
- 잘하고 있는 능력, 발달 중인 능력, 연습이 필요한 능력
- 분석 근거 수준과 수행 세션 수
- 근거 부족 시 단정하지 않고 `더 지켜볼게요`로 표시
- `분석한 행동` 버튼을 누르면 강점·어려움으로 집계된 행동, 독립·지원 여부와 관찰 횟수 표시

프론트는 `GET /api/behavior-profiles/latest`에서 최신 행동 프로필을 읽고,
`GET /api/market-personalization/recommendation`에서 AI가 생성한 전체 추천 난이도를 읽는다. 탭을 열 때
새 프로필을 생성하지 않고 자동 갱신 과정에서 저장된 최신 스냅샷만 조회한다.

능력 레벨 표시는 현재 개인화 정책의 성공률 경계와 맞춘다.

- 50% 미만: `Lv.1`, 연습 필요
- 50% 이상 80% 미만: `Lv.2`, 발달 중
- 80% 이상: `Lv.3`, 강점
- 성공률 없음 또는 신뢰도 `INSUFFICIENT`: 측정 중

이 화면은 행동 기반 맞춤화 정보이며 의학적·심리학적 진단이 아니라는 안내를 항상
표시한다.

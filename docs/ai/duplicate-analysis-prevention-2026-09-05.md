# 중복 분석·퀘스트 생성 방지

## 결과

동일 계정의 진행 중 요청을 공유하고, 행동이 바뀌지 않았으면 기존 입력 및 검증된 완료 결과를 재사용하도록 변경했다. 원본 행동, AI 성패 판단, 난이도, 검증 기준은 수정하지 않았다.

수정 전 실제 앱에서는 21:25:09 / 21:25:35 / 21:25:48에 같은 계정의 246사건으로 서로 다른 데이터셋 3개가 생성됐다. 각 작업은 17구간을 별도로 분석했고 같은 API 한도를 경쟁했다. 화면을 나가도 서버 작업이 중단되지 않아 재진입으로 중복될 수 있었다. 실제 응답은 약 1~2초였지만 대기를 포함해 1~6분씩 걸렸다.

## 변경 내용

| 계층 | 변경 |
|---|---|
| 프론트 | 동일 로그인 토큰의 진행 중 퀘스트 Promise를 공유. 화면을 나갔다 들어와도 같은 요청에 연결 |
| 퀘스트 서비스 | 인증된 회원 ID별 진행 중 생성 작업을 하나로 공유 |
| 분석 서비스 | 회원·요청 범위별 작업을 공유하고, 회원·데이터셋별 실제 분석도 공유 |
| 입력 저장 | 기본 누적/세션 요청은 원본 사건 ID 집합이 정확히 같으면 기존 스냅샷 사용 |
| 분석 완료 | 같은 데이터셋·모델·프롬프트·주요 설정의 READY 결과를 DB에서 재사용하고 현재 검증기로 재검사 |
| 퀘스트 완료 | 같은 AI 분석·연습 계획·모델·프롬프트·카탈로그의 검증된 퀘스트를 DB에서 재사용 |

진행 중 작업은 `SingleFlight`의 공유 Future로 합친다. 첫 요청이 작업을 수행하고 후속 요청은 그 결과/실패를 함께 받는다. 작업 완료·실패 때 항목을 제거하므로 실패가 영구 캐시가 되지 않는다. 다른 계정이나 서로 다른 분석 범위를 같은 응답으로 합치지 않는다.

스냅샷 생성 트랜잭션 동안만 회원 행 잠금을 사용하여 누적 분석/세션 분석이 동시에 같은 원문 스냅샷을 새로 만드는 경쟁도 줄였다. 이 잠금은 입력 생성/조회가 끝나면 해제하며 AI 호출 동안 유지하지 않는다.

## 재사용과 새 분석을 구분하는 기준

- 사건 **개수만** 비교하지 않고 불변 원본 사건 ID 집합을 비교한다. 같은 개수의 다른 세션은 합치지 않는다.
- 기본 요청에서 최근 같은 개수·시작 범위의 스냅샷 최대 20개를 대조한다. 명시적 날짜 범위 요청은 기존 생성 동작을 유지한다.
- 행동이 추가되면 다른 스냅샷으로 분석한다. 진행 중 도착한 새 행동은 현재 스냅샷에 몰래 끼워 넣지 않고 다음 요청에서 반영한다.
- 완료 재사용 키는 SHA-256이며 JSON 객체 속성 순서만 정규화한다. 배열·원문 값·회원 경계를 보존한다.
- 분석 키에는 모델, 입력, 시스템/관찰/통합/FINAL 지시와 버전, 주요 토큰 설정을 포함한다.
- 퀘스트 키에는 AI 분석과 연습 설정, 전체 콘텐츠, 시스템/사용자 지시, 모델·출력 설정을 포함한다. 매 조회 때 바뀌는 추천 ID·생성 시각과 분석의 표시용 소요 시간·생성 시각만 제외한다.
- 실패한 분석·퀘스트는 완료 캐시로 반환하지 않는다. 재요청 시 동일 스냅샷의 검증된 중간 체크포인트부터 재사용할 수 있다.
- 정상 결과를 재사용하면 기존 analysisId/generationId를 반환한다. 새 분석·퀘스트 감사 기록을 허위로 만들지 않는다. 응답의 latencyMs/createdAt은 원래 생성 당시 값이다.
- ‘새 행동 분석하기’도 같은 원문·설정이면 완료 결과를 재사용한다. 강제 재생성 옵션은 이번에 추가하지 않았다.

DB 마이그레이션 V34는 `ai_behavior_analyses`와 `market_ai_quest_generations`에 nullable `request_key`와 조회 인덱스를 추가한다. 과거 결과는 키가 없으므로 임의로 새 완료 캐시로 승격하지 않는다. 기존 체크포인트와 행동 기록은 삭제하지 않는다.

## 검증

백엔드 전체 **112개 중 110개 통과, 실제 API 재호출 테스트 2개 제외, 실패·오류 0개**. 프론트 관련 **15개 통과**, TypeScript 타입 검사와 `git diff --check` 통과.

추가 검증은 실제 서비스/저장소와 H2를 사용하고 AI 공급자만 테스트 응답으로 대체했다.

1. 동일 인증 사용자의 HTTP 분석 POST 3개를 동시에 보내 AI 클라이언트 호출이 1회이고 분석 ID·데이터셋 ID가 같은지 확인.
2. 퀘스트 생성 서비스 3개 동시 요청이 같은 generationId를 반환하며 분석 1회 + 퀘스트 1회만 호출하는지 확인.
3. 별도 서비스 인스턴스로 재진입해도 DB 완료 결과가 재사용되어 AI 추가 호출이 없는지 확인.
4. 새 행동을 추가하면 새 데이터셋·분석·퀘스트가 생성되는지 확인.
5. 실패 후 재시도는 허용하고, 동일 사건 수의 다른 세션 및 다른 계정은 합치지 않는지 확인.
6. 프론트 재진입의 Promise 공유, 계정 분리, 완료/실패 후 메모리 해제를 확인.

이번에 별도의 유료/실 모델 장시간 호출을 시작하지 않았다. 위 테스트 통과가 실제 모델의 문장 품질 또는 퀘스트 계약 준수를 보장하지는 않는다.

## 실행 반영과 남은 한계

기존 서버의 중복 작업을 중지하고 새 서버를 21:47 KST에 시작했다(PID 40540, 8080). 실제 PostgreSQL에 V34를 적용했다. 테스트 계정 원본 로그 246개와 기존 중간 체크포인트 8개는 유지했다. 서로 다른 과거 데이터셋의 체크포인트를 임의로 섞지 않았다.

21:57 KST에 무무에서 앱 재실행과 개발 서버(8081) 재연결을 마쳤고, 오늘도 로그인 시작 화면을 직접 확인했다. 앱 데이터 초기화나 재설치는 하지 않았다. 재실행 후 로그인 시작 화면이 표시되어 로그인은 사용자에게 넘겼다(computer-use 스킬의 인증 화면 자동 조작 금지). 따라서 이번 실행 확인은 앱 시작 화면까지이며, 로그인 이후 실제 모델을 이용한 퀘스트 생성 완료를 검증했다는 의미는 아니다.

진행 중 작업 공유는 **현재 단일 백엔드 프로세스 범위**다. 서버 여러 대를 함께 운영하려면 분산 작업 잠금/공유 작업 큐가 추가로 필요하다. 프론트 요청 공유는 현재 JS 런타임 범위이며 앱 프로세스를 다시 켜면 서버의 작업 공유/DB 재사용이 담당한다.

처음 분석하거나 새 행동으로 입력이 바뀌면 여전히 전체 원문 구간 분석과 API 한도 대기가 필요하다. 이번 변경은 중복 작업을 없애는 것이지 첫 분석을 몇 초로 단축하는 것은 아니다. 최신 진행 구간을 화면에 표시하는 기능은 아직 없다.

별도로 확인된 S01 고정 예산 7,000원 대신 AI가 5,800원을 쓰는 문제 및 문장 품질 문제는 수정하지 않았다. 자세한 실 모델 결과는 [최종 입력 축소 보고서](./final-input-compaction-report-2026-09-05.md)를 참고한다. 실패 검증을 풀거나 서버가 예산·성패를 대신 수정하지 않았다.

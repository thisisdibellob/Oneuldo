# 27B QLoRA 첫 본학습과 동일 조건 비교

상태: 2026-09-25 KST 완료. 원본 평가 25건 → 본학습 60/60 → 후평가 25건 및 운영 복구 확인. 앱 검증기 통과는 25/25→19/25로 악화돼 운영 적용하지 않는다. [최종 비교 보고서](comparison-report.ko.md)와 [응답 원문](model-responses.ko.md)을 참조한다.

## 실행 범위

사용자가 요청한 1~3단계: 원본 평가 25건, 학습 60개를 1회씩, 튜닝 후 동일 25건 평가. 운영 모델 교체는 포함하지 않는다. 물리 GPU 1만 사용한다. 기존 Ollama 및 게이트웨이는 시험 동안 중지하고 종료·실패 시 다시 시작한다. 최대 실행 시간은 3시간이다. GPU 0, 노트북 서버, 방화벽, 시스템 Java는 변경하지 않는다.

정확한 사전 설정과 데이터 해시는 `protocol.json`에 고정했다. 평가 파일은 system/user 메시지만 포함한다. 평가 정답·채점 기준은 서버의 추론 입력에 들어가지 않는다. 60개의 assistant 정답만 학습한다. 기존 native-v3 파일과 과거 승인 메타데이터는 변경하지 않는다.

## 비교 조건

- 고정 HF 원본 revision, NF4 double quantization, FP16 연산, CPU 동결 입력 임베딩을 두 평가 모두 동일하게 사용한다.
- 기존 운영 GGUF와 이번 HF 원본의 정확한 가중치 동등성은 확인되지 않았다. 운영 Ollama 이전 평가와는 별도로 이번 HF 전후 비교를 해석한다.
- rank 8 / alpha 16 / dropout 0 / 학습률 1e-5 / batch 1 / 1 epoch / 고정 순서 seed 240924.
- assistant 토큰만 학습하며 입력이나 정답을 자르지 않는다. 32토큰 단위의 출력 행렬 재계산으로 원래 토큰 평균 CE를 유지한다.
- 평가: greedy, thinking off, 최대 출력 1024토큰, 사례당 최대 360초. 자동 재시도, 문법 강제, 응답 수정 없이 원문을 기록한다. 길이/시간 제한 종료도 별도 기록한다.
- 두 평가 전에 4토큰 준비 생성을 수행한다. 각 사례의 입력 처리 시간, 출력 수, 전체 시간, GPU 최대 메모리를 남긴다.
- 재실행에서는 10/20/40/60스텝 어댑터를 저장한다. 최종 파일의 모든 텐서를 메모리 값과 비교하고 디스크에서 재적용한 뒤 후평가한다.

## 실행 전 검증

`inference-check.json`: GPU 1의 작은 하이브리드 Qwen 모델에서 캐시 생성 대 전체 재계산 비교, CPU 임베딩 및 혼합 dtype의 ConditionalGeneration 경로, EOS/길이 종료, LoRA 저장/재적용 검사를 수행했다. 학습 메모리 구성은 이전 memory-optimization-v4의 긴 입력 3스텝 시험에서 통과했다. 작은 모델 검사만으로 실제 27B 전체 실행 성공을 보장하지 않는다.

`FinetuningMatchedComparisonTest`: 원문을 실제 프로젝트 파서·검증기에 넣는 오프라인 도구. 생성 결과가 생긴 후 활성화해야 한다. 컴파일 성공이나 비활성 상태의 테스트 성공은 50건 검증 완료가 아니다.

## 결과 판단

1. 실제 파서·검증기 통과 수, 시간/길이 제한 종료 수.
2. 입력에 없는 사실 단정, 관찰과 해석 구분, 실제 사건과 근거 참조 일치.
3. 과거와 현재 구분, 보고된 선호 보존, 잘못된 이전 분석의 무비판적 복사 여부.
4. 다음 퀘스트의 문장과 구조화 설정 일치, 입력 조건에 따른 구체적인 조정.
5. 사례별/종류별 시간과 토큰 수. 동일 사례 전후 비교를 함께 제시.

채점은 출력 후처리 규칙이나 운영 판단 로직으로 사용하지 않는다. 정답 문장과 정확히 같다는 이유만으로 좋은 분석으로 보지 않는다. 의미 판단에는 원문 인용과 입력 근거를 붙인다. 코딩 에이전트의 개발 검토이며 전문가·임상 검증은 아니다.

합성 학습 자료이고 평가 25건도 이미 개발 중 확인한 사례다. 시나리오 계열이 학습과 겹치므로 독립적인 실제 사용자 일반화나 교육 효과를 입증하지 못한다. 결과가 개선돼도 별도의 미공개 평가와 전문가 검토 없이 운영 적합성을 확정하지 않는다.

## 첫 실행 실패와 수정

첫 실행의 Transformers `apply_chat_template(tokenize=True)` 반환값은 정수 목록이 아닌 `BatchEncoding`이었다. 본학습 코드가 이를 목록으로 취급해 경계 검사에서 중단했다. 모델 로딩·학습 이전 실패로 가중치 변화는 없다. 원래 스크립트와 실패 기록은 `attempts/01-tokenizer-return-type`에 보존했다.

이전에 통과한 메모리 시험과 동일하게 템플릿을 문자열로 만든 다음 `tokenizer.encode(add_special_tokens=False)`로 정수 토큰을 얻도록 수정했다. 해당 함수를 데이터 사전 검사와 본 실행이 함께 사용한다. `data-preflight.json`에서 학습 60건·평가 25건의 정수 토큰, 경계 일치, EOS, 길이, 입력 해시를 검사했다. 가장 긴 학습 예제는 기존과 동일한 3557토큰이다. 서비스 중단 전에 이 CPU 검사부터 실행하도록 제어 스크립트도 바꿨다.

## 13번째 학습 시도의 기울기 오류와 복구 계획

첫 본학습 실행은 12개의 optimizer update를 마친 후 T43 역전파에서 비유한 기울기를 검출했다. 손실은 유한값 검사에 통과했으나 기울기는 그렇지 않았다. 해당 비정상 기울기는 적용하지 않았고 기존 서비스는 복구됐다. 실패 기록과 코드, 25건 baseline은 `attempts/02-gradient-nonfinite`에 보존했다. 이는 메모리 부족 오류가 아니다.

기존 구현은 비유한 기울기가 한 번만 나와도 종료했다. `stable_step.py`는 이때 optimizer.step을 호출하지 않고 AMP 배율을 절반으로 줄여 같은 예제를 재계산하게 한다. 예제마다 최대 8번 시도하며 성공한 optimizer update만 60스텝으로 센다. 비유한 손실·기울기 반복 실패·0인 gradient norm 등은 계속 실패로 처리한다. [PyTorch AMP 문서](https://docs.pytorch.org/docs/2.10/amp.html)의 gradient scaling과 비유한 기울기에 대한 배율 감소 원칙을 따른다.

`stable-step-check.json`은 실제 GPU FP16 overflow를 만든 단위 검사다. overflow 시 가중치와 Adam 상태가 변하지 않고, 배율 256→128 뒤 동일 예제에서 정확히 한 번만 갱신됨을 확인했다. NaN 손실은 갱신 없이 거부했다. 이 검사는 실제 27B의 T43 해결을 아직 보장하지 않는다.

재실행은 원본에서 새 LoRA를 초기화해 60개를 다시 학습한다. 실패 실행의 12스텝은 합치지 않는다. baseline 25건의 파일·입력·추론 코드·프로토콜 해시, 환경을 검사하고, E01 원본 생성 토큰이 기존과 정확히 같을 때만 25건을 재사용한다. 새 baseline을 생성한 것처럼 기록하지 않는다. 중간 어댑터 저장은 10/20/40/60스텝이다. 최종 운영 배포는 여전히 범위 밖이다.

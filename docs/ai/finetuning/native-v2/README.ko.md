# 학습 예제 운영 입력 재작성 결과 — 2026-09-24

**학습 후보 60개·평가 후보 25개를 새 버전으로 작성했고, 모두 실제 운영 프롬프트 생성기와 출력 파서·구조 검증기를 통과했다.** 기존 원본 85개와 이전 기준 응답은 변경하지 않았다. 이번 작업은 데이터 재작성과 오프라인 검사이며, LoRA 학습이나 새 모델 추론은 실행하지 않았다.

이 자료는 작성자가 만든 합성 사례다. 실제 지적장애 참여자의 행동 기록, 장애 집단의 대표적인 행동 분포, 전문가가 승인한 정답으로 취급하면 안 된다. `training_approved=false`를 유지한다. 구조가 맞는 것과 교육적·임상적으로 타당한 것은 별개다.

## 수량과 단계

| 단계 | 학습 후보 | 평가 후보 | 운영 출력 |
|---|---:|---:|---|
| 원본 사건에서 세션 최종 분석 초안 | 40 | 17 | 압축 `s/f/a/u/p/c`, 사건 E·세션 S 참조 |
| 이전 프로필 + 현재 분석에서 프로필 갱신 | 20 | 8 | 프로필 JSON, 허용된 R 근거 참조 |
| 합계 | **60** | **25** | 단계별 파일도 별도로 제공 |

지난 `contract-v1`은 6개만 실제 입력 프롬프트까지 만들었다. 이번에는 **57개 세션 입력과 28개 프로필 입력을 모두 생성**했다. 모델 출력을 검사하는 두 번째 AI 검토 단계의 학습 자료까지 만들었다는 뜻은 아니다. 나중에 학습할 때 단계별 어댑터를 사용할지, 두 작업을 함께 학습할지 별도로 정해야 한다.

## 무엇을 바꿨나

### 1. 모델이 받지 않는 정보를 정답에서 요구하지 않도록 했다

세션 예제는 현재 앱에서 쓰는 수량 변경, 장바구니 열기, 선반 열기, 목표 제시, 제출, 배경/전경 전환, 종료 사건과 DTO 필드로 재작성했다. 미지원 조건을 임의의 `marketContent` 필드에 넣어 통과시키지 않았다.

- **T40:** DTO에 수신 시각을 넣어도 운영 프롬프트 압축 단계에서 빠지는 것을 확인했다. 정답에서 수신 25초·21초와 네트워크 지연 비교를 제거하고, 실제 남는 경과 10초·20초와 사건 순서만 사용한다.
- **T09:** 원래 UI 차단/입력 무시 사례를 실제 앱 배경/전경 전환 사례로 바꿨다. 배경 상태 180초를 전체 조작 시간과 구분하며, 네트워크 장애나 집중력 저하라고 하지 않는다.
- **E13:** 진행자의 대리 조작이라는 미수집 조건을 제거하고, 목표 장바구니 화면만 있고 선택 과정과 제출은 없는 사례로 교체했다. 이 새 사례로 대리 조작 판별 성능을 평가할 수는 없다.
- **E12:** 이전 목표와 새 목표, 각 세션의 장바구니·제출은 유지했다. 장바구니가 같은 이유를 ‘자동 복원’으로 확정하지 않는다.
- **T47:** 무촉구 조건의 판정 의미가 미해결인 원래 사례는 원본에 그대로 남겼다. 새 버전의 같은 번호는 수량·예산 초과 사례다. **원래 라벨 정책을 해결했다는 뜻이 아니다.**

목표가 없는 T42/E18에는 목표를 보충하지 않았다. 일부 사건만 있는 T05/T14/T49 등의 `integrity`도 임의로 완료 처리하지 않았다. 수신 상태와 전체 행동 관찰을 구분한다.

원래 조건을 없앤 사례의 평가 항목은 실제로 줄었다. 보고의 출처 구분, 대리 조작, 재전송, 목표 버전 상충 등의 원래 시험을 전부 유지했다는 주장은 하지 않는다. 각 번호의 변경 이유와 새 입력·목표 답변은 [사례별 검토 문서](cases-review.ko.md)에 있다. 번호는 원본 계보를 뜻하며, v1과 같은 과제를 뜻하지 않을 수 있다.

### 2. 프로필 근거를 실제 입력에서 볼 수 있게 했다

운영 프로필 모델은 원본 사건 배열을 받지 않고 이전 프로필과 현재 분석을 받는다. 원본 초안에서는 28개 중 22개가 그 배열에 없는 근거 ID를 목표 답변에서 요구했다.

이번에는 원래 **입력의 사건·과제 조건**으로 합성 분석 스냅샷을 작성하고, 각 관찰 문장 옆에 해당 사건 ID를 넣었다. 목표 답변을 읽어 입력을 만들지 않으며, 목표 답변을 임의로 바꿔도 입력이 같다는 검사를 추가했다.

- E22: 현재 AI의 잘못된 ‘글을 완전히 이해했다’는 해석은 정정 대상으로 남겼다. 동시에 ‘목록 글은 잘 모르겠어요’라는 **사용자 보고**와 올바른 제출값이 현재 분석의 관찰 항목에 들어간다.
- E23: 보호자와 진행자의 서로 다른 매장·날짜에 대한 보고를 각각의 출처와 함께 전달한다. 그 보고를 실제 수행을 직접 관찰한 사실로 바꾸지 않는다.
- E21: `sameSessionReanalysis=false`라도 재수집이라고 명시된 같은 원 플레이를 새 성공으로 세지 않는 사례를 유지한다.
- T21/T22/T24/T51: 실제 프로필 생성기가 산출한 동일 세션 플래그로 해석 정정과 새 플레이를 구분한다.

이 스냅샷은 **작성한 상위 분석 입력**이지, 앱에서 수집해 AI 분석까지 실행한 결과가 아니다. 특히 사람의 보고, 외부 지원, 수집 비고가 실제 게임 수집기에 구현되었다는 뜻이 아니다. 프로필은 그러한 정보가 기존/현재 분석에 명시적으로 들어왔을 때의 처리만 연습한다. 실제 수집 경로와 모델이 이 사실을 정확히 전달하는지는 별도 통합 검증이 필요하다.

### 3. 문헌 인용과 정답 근거를 분리했다

선택한 세션 운영 경로에는 문헌 카드가 없으므로 출력 `c`와 프로필 `usedEvidenceCardIds`는 빈 배열이다. T52/T58의 계획에서 제공되지 않은 연구 효과를 근거로 삼는 표현을 수정했다. E24도 원문이 없는 연구 주장을 개인 기억 특성으로 확정하지 않도록 고쳤다.

원래 참고 카드 ID와 이용 조건·검토 상태는 `manifest.json`과 `seed-v1`에 보존했다. 인용을 제거한 것으로 이용 조건 확인이나 전문가 검토가 끝난 것은 아니다. 원문을 모델에 학습시키거나 원문 전체를 복사하지 않았다.

## 검사 결과

- **Java 테스트 3개 통과:** 85개 실제 생성기·파서·검증기 왕복, 보고 근거 제거 시 해당 근거 인용 거부, 실제 동일 세션 플래그 확인.
- **Python 테스트 7개 통과:** 답변/평가 기준의 입력 유출 방지, 60/25 및 단계별 수량, 이벤트 식별자 분리, 압축 후 주요 사실 보존, 프로필의 관찰·근거 인접 확인, 미지원 사건 거부, 원본·생성 입력 해시 확인.
- **정규화한 입력의 완전 중복 0건:** 사례 식별자를 제거하고 실제 펼친 프롬프트를 비교했다. 처음 발견한 T19/T45 중복은 T45를 다른 수량·예산의 새 합성 사례로 바꿔 제거했다.
- **모든 85개 템플릿/토큰 경계 검사 통과:** system/user와 assistant 시작 부분을 제외하고 답변·종료 토큰만 학습 대상으로 분리할 수 있음을 확인했다. 실제 역전파를 실행한 것은 아니다.

| 구분 | 개수 | 입력+정답 토큰 중앙값 | 최대 |
|---|---:|---:|---:|
| 학습 세션 분석 | 40 | 3,231 | 3,557 |
| 학습 프로필 | 20 | 1,891 | 2,044 |
| 평가 세션 분석 | 17 | 3,236 | 3,947 |
| 평가 프로필 | 8 | 1,896.5 | 2,061 |

공식 고정 리비전의 대화 템플릿과 기존 로컬 토크나이저를 사용했다. `enable_thinking=false`, 자르기·패딩 없이 측정했고 4096 초과는 없다. 이는 **이 후보 파일의 길이**다. 실제 긴 플레이의 입력 길이나 24GB GPU에서 학습 가능 여부를 증명하지 않는다. 원본 체크포인트와 현재 GGUF 서버 가중치의 대응도 아직 확인되지 않았다.

정확한 파일·토큰 해시는 [검증 기록](verification.json), [토큰 기록](token-audit.json), [중복 검사](split-audit.json)에 있다. 운영 생성기의 JSON 객체 출력 순서가 실행 환경에 따라 달라지면 재생성 파일의 바이트 해시와 토큰 수가 조금 달라질 수 있으므로 비교 실험에는 지금 동결한 파일을 사용한다.

## 남은 품질 한계

1. 합성 세션은 **부분 장면과 짧은 사건 발췌**다. 최소 목표 스냅샷을 첫 제공 사건에 부착했고 일부 상품 이름은 합성 ID다. 실제 앱의 완전한 장면/상품 카탈로그와 동일한 로그 재생본은 아니다. 실제 수집 로그의 긴 입력·누락·동시 사용자 분포 검증이 필요하다.
2. 원본에 없던 사건 시각은 새 사례를 만들기 위한 명시적인 합성 시각으로 정했다. 여러 세션의 날짜도 명시된 간격이 없는 경우 순서대로 만들었다. 원본 기록에서 복구한 시간이나 장애 집단의 행동 속도가 아니다.
3. 정답을 보면서 고친 25개는 **개발 평가 자료**다. 완전 중복이 없어도 유사한 사례 유형이 학습/평가에 있다. 최종 성능이나 일반화는 새 독립 사례와 별도 검토로 확인해야 한다.
4. 이번 구조 검사는 의미 정확성의 완전한 자동 판정기가 아니다. 성공/실패 판정을 하는 운영 규칙은 추가하지 않았다. 전문 검토, 자료 이용 조건 확인과 실제 사용자 평가가 남아 있다.
5. 이전 `baseline-v1`의 25개 응답 시간·품질은 옛 입력 기준이다. 새 후보를 사용한 개선 효과로 재사용할 수 없다.

## 다음 순서

1. 이 새 형식의 평가 후보 25개를 고정해 **미튜닝 모델의 새 기준 응답**을 측정한다. 세션 17개/프로필 8개를 따로 보고 원래 자료와 합산하지 않는다.
2. 근거 누락, 보고의 사실화, 목표 혼동, 과도한 일반화, 계획 모순을 새 응답에서 검토하고 후보 정답도 함께 점검한다.
3. 학습할 원본 체크포인트/라이선스와 서버 GGUF 대응을 확인한 뒤 GPU 1에서 소수 스텝 메모리 시험을 한다. 운영 추론에 영향을 줄 수 있으므로 실제 작업 시 점유 상태와 함께 진행 범위를 정한다.


프로젝트 루트에서:

```bash

```

```bash
python docs/ai/finetuning/audit_native_v2.py
```

서버, 운영 프롬프트, 운영 검증기, 런타임 설정은 변경하지 않았다.

## LoRA는 무엇인가

LoRA는 **기존 모델 가중치를 고정하고 작은 추가 가중치만 학습하는 방법**이다. 이름은 Low-Rank Adaptation의 약자다. 예를 들어 27B 모델의 모든 가중치를 업데이트하는 대신, 선택한 층에 작은 행렬을 붙여 이번 과제에 맞는 변화만 학습한다.

```text
기존 27B 모델의 가중치: 고정
            +
작은 LoRA 가중치: 검토한 예제로 학습
            ↓
오늘도 분석에 맞게 조정한 출력
```

추가 가중치는 보통 어댑터 파일로 저장한다. 동일한 원본 모델에 붙여 사용하거나, 지원되는 도구로 원본과 합쳐 별도 모델로 저장할 수 있다. 학습하는 파라미터가 줄어 메모리·저장 비용을 줄일 수 있지만, 원본 모델의 추론 계산까지 없어지는 것은 아니다. 기존 27B가 작은 모델로 바뀌거나 분석 속도가 자동으로 빨라지는 방법은 아니다. [Hugging Face PEFT LoRA 설명](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora)

**QLoRA**는 원본 모델을 학습용 4비트 방식으로 불러오고 LoRA 가중치를 학습하는 접근이다. Ollama의 `Q4_K_M` GGUF 파일과 학습용 양자화는 구분해야 한다. 현재 GGUF에 문서를 넣어 수정하는 작업이 아니며, 대응하는 학습용 원본 모델·토크나이저·채팅 템플릿을 확인해야 한다. [PEFT 양자화 설명](https://huggingface.co/docs/peft/developer_guides/quantization)

이 데이터셋으로 LoRA 학습이 가능한지는 아직 시험하지 않았다. 학교 서버 GPU 1의 24GB에서 실제 입력 길이로 실행 가능한지도 미확인이다. GPU 0 사용, 추론 서비스 중단, 원본 모델 변경은 이번 작업에 포함되지 않았다.

## 무엇을 학습하도록 작성했나

| 범위 | 사례 |
|---|---|
| 목표와 실제 값 비교 | 명확한 성공, 수량·품목·예산 조건 미충족, 수정 후 성공 |
| 모르는 것을 보존 | 부분 로그, 장바구니 열기와 읽기·의도 구분, 위치와 시선 구분 |
| 데이터 의미 유지 | 구 수집기 라벨, 가격표 버전, 수신 범위, 중간 요약과 원본 충돌 |
| 지원·환경 구분 | 촉구, 기술 지연, 문구 변경, 속도와 정확도, 새로운 배열 |
| 누적 프로필 정정 | 동일 세션 재분석, 의도 추정 철회, 과거 오류 수정, 확인된 사실 유지 |
| 조건에 맞는 제안 | 품목 수·수량·예산·문자 지원 범위 안에서 다음 연습 제안 |

성공 사례도 명확히 포함했다. 불확실한 문장을 무조건 늘리는 학습을 목표로 하지 않는다. 근거가 충분하면 성공·실패를 설명하고, 근거가 부족한 부분만 보류하도록 작성했다. 실제 근거가 있는 대안 설명 사례와 빈 배열이 타당한 사례를 함께 포함했다.

성패·심리·지원 필요성을 결정하는 운영 코드나 횟수 기반 규칙은 추가하지 않았다. 목표 답변과 평가는 검토 가능한 작성자의 판단 초안이다. 검증 스크립트도 성공·실패를 자동 계산하거나 장애 특성을 판정하지 않는다.

## 60개·25개 확장 내용

기존 T01~T30, E01~E10을 보존하고 T31~T60, E11~E25를 추가했다. 문헌 카드의 범위는 기존 18개를 유지했다.

- 추가 세션 분석: 예산 경계값, 허용·금지 추가 상품, 묶음 단위, 허용 품종, 미확정 제출, 재전송과 실제 행동, 시간 순서, 모순된 금액, 목표 누락, 자동 UI, 조작 거절, 빈 관찰.
- 추가 프로필: 목표 버전 정정, 지원 조건 변화, 선호 추측 수정, 강점 보존, 미확인 기준선·성공 횟수, 기술 문제, 네 품목 수행, 지원 기능 정정.
- 추가 평가: 상충하는 최종 스냅샷, 장바구니 이월, 대리 조작, 자기보고와 수행 불일치, 유지·복습, 미제공 교육, 도전 선호, 잘못 전달된 목표, 잘못된 문헌 메모, 완료 뒤 중단.
- 프로필 평가에는 서로 다른 세션 ID라도 같은 플레이를 재수집한 경우, 최신 AI 분석 자체가 틀린 경우, 서로 다른 정보원, 연구 대상 연령의 차이, 과거 일반화 철회도 포함했다.

이 확장은 사례 개수와 범위를 늘린 것이며 전문가 검토나 모델 성능 검증을 완료한 것은 아니다.

## 문헌을 사용한 방식

기존 `source-catalog.json`과 후속 `reading-audit.json`을 함께 읽었다. P01처럼 확인 범위가 보완된 경우에는 후속 검토 기록의 범위를 우선했고, 이용 조건은 카탈로그의 미확인 상태를 보존했다. 이번 작업에서 모든 원문을 새로 읽거나 전문가가 검토한 것은 아니다.

카드에는 제목, 원출처 URL, 연도, 대상, 요약, 한계, 읽은 범위와 이 초안에서 참고한 용도가 들어 있다. 문헌 카드의 주장은 입력에도 제공하므로 출처 이름만 외워 답하도록 구성하지 않았다. 지원 제안이나 과잉 일반화 제한을 위한 참고이며, 가상 사용자가 어떤 행동을 했는지 증명하는 근거는 합성 사건 자체다.

자료에는 실제 매장의 장보기 연구뿐 아니라 금전 과제, 의사소통, 접근성, 읽기 교육, 방법론 자료도 있다. 읽기나 조리 연구를 오늘도의 장보기 교육 효과로 바꾸어 주장하지 않는다. 참고 범위와 전이 한계를 각 사례에 남겼다. T19는 문헌이 없는 제품 동작 확인 사례로, 출처를 지어내지 않아야 한다.

전부 `draft`, `domain_expert_reviewed=false`, `source_rights_reviewed=false`, `training_approved=false`다. 기존 자료를 **학습 승인 완료 데이터로 표시하지 않았다**. 문헌·이용 조건과 목표 답변 검토가 끝난 사례만 실제 학습본으로 선별해야 한다. 초안의 체크를 통과했다고 전문가 검토를 통과한 것은 아니다.

## 학습과 평가 분리

- 학습: T01~T60. 문헌 G01, G04, M01, P01, P02, P03, P11, P14, P27, P40.
- 평가: E01~E25. 문헌 G06, G07, M02, P10, P16, P20, P30, P31.
- 두 분리 사이에 문헌 ID·URL, 합성 참여자 그룹, 시나리오 ID, 세션 UUID와 동일 입력이 겹치지 않는지 검사한다. 생성 UUID를 제거한 과제·사건도 학습/평가 사이에 동일하게 겹치는지 검사한다. 의미적으로 비슷한 모든 사례를 자동 탐지하는 검사는 아니다.
- 평가 사례의 답변·평가 항목은 학습에 넣지 않는다. 문헌 카드가 입력으로 제공되는 조건이므로 이 평가는 문헌 암기보다 제공 근거를 사용하는 분석을 확인한다.
- 서로 다른 문헌이 같은 선행 연구를 인용할 가능성까지 완전히 제거한 것은 아니다. 같은 작성자의 소규모 합성 자료이므로 외부 독립 평가셋이라고 부르지 않는다.
- 사례의 의미와 검토 기준은 겹칠 수 있다. 예를 들어 과잉 일반화를 피하는 원칙은 두 분리에 모두 필요하다. 새로운 실제 사용자·더 긴 로그·다른 난이도로의 일반화 성능은 별도 검증해야 한다.
- 이 평가셋을 보고 반복 수정하기 시작하면 개발 평가셋으로 취급하고, 최종 성능 확인용 새 평가셋을 별도로 확보한다.

## 현재 서비스 형식과의 관계

출력은 `AiBehaviorAnalysis`의 펼친 JSON 필드에 맞췄다. 프로필 출력은 `AiUserProfilePromptFactory`의 출력 계약에 맞춰 `sessionAssessments`를 제외했다. 현재 프로필 API가 별도로 전달하는 세션 평가의 존재와 혼동하지 않는다.

입력은 이해·검토를 위한 **정규화한 합성 형식**이다. `sourceEventDetails.type`, `taskContext`, 간단한 `previousProfile`은 실제 서버 요청 DTO와 완전히 같지 않다. 프로필 초안에는 판단을 대조하기 위해 원본 사건도 함께 제공했다. 실제 프로필 요청에 같은 원본 범위가 제공되지 않으면 이 학습 입력을 그대로 서비스 입력과 같다고 취급할 수 없다.

현재 서비스의 압축 `s/f/a/u/p/c` 출력, E/R 참조 인코딩, 구간 관찰 모델까지 모두 재현한 학습셋은 아니다. 실제 학습 전에는 학습할 단계(최종 세션 분석 또는 프로필 갱신)를 정하고 해당 단계의 운영 프롬프트·인코더·출력 스키마와 연결해야 한다. 프롬프트 차이를 방치한 채 두 작업을 한꺼번에 학습하지 않는다.

JSONL 각 행의 구성:

```text
id / split / task / title
provenance        합성 여부, 출처, 참여자·세션 그룹
review            검토·학습 승인 상태
rubric            포함해야 할 의미 / 피해야 할 주장 (모델 입력으로 넣지 않음)
messages
  system          분석 역할과 출력 제한
  user            합성 사건, 과제, 문헌 카드, 출력 계약
  assistant       검토할 목표 답변 JSON 문자열
```

향후 학습 도구에는 검토한 `messages`만 전달한다. `rubric`, 검토 결과, 평가 행을 프롬프트에 넣으면 답 유출이나 평가 오염이 생긴다. `assistant.content`가 JSON 문자열인 것은 대화형 학습 형식에 맞춘 것이며, 학습 스크립트에서 채팅 템플릿을 한 번만 적용해야 한다.

## 재생성과 검사

프로젝트 루트에서 다음을 실행한다. 네트워크·서버 호출이나 모델 학습은 하지 않는다.

```bash
python3 docs/ai/finetuning/seed-v1/build_dataset.py
python3 docs/ai/finetuning/seed-v1/validate_dataset.py
```

생성 파일을 직접 고치면 다음 생성 때 덮어써진다. 사례는 `build_dataset.py`와 `additional_cases.py`에 정의되어 있고, 이번 교정은 마지막에 적용되는 `review_revisions.py`에 있다. 수정 후 재생성하고 해당 검토 기록을 갱신한다. `content-review.*`는 검토 시점의 고정 기록이므로 재생성만으로 검토 완료 상태가 갱신되지 않는다.

2. 완료: 별도 평가 25개를 동결하고 현재 모델로 각 1회 실행했다. [기준 평가 결과](../baseline-v1/report.ko.md): HTTP 25/25, 자체 구조 검사 24/25, 중앙값 33.853초. 내용 문제는 별도 검토했으며 실제 앱 전체 시험·임상 검증은 아니다.
3. 1차 연결·검사 완료: [운영 형식 검토](../contract-v1/README.ko.md). 출력 57개는 실제 파서 왕복을 확인했고, 입력은 6개만 미리보기로 연결했다. 나머지는 필드·근거·단계 차이를 보완해야 한다. 원본 85개와 운영 예시 6개의 실제 템플릿 토큰 길이를 측정했다. 전체 전환/학습 준비 완료는 아니다.
4. 실제 허용된 GPU에서 소수 스텝으로 메모리와 호환성을 시험한다. GPU 0 사용이나 운영 추론 중단은 별도로 조율한다.
5. 학습 전후를 같은 입력·문헌·생성 설정으로 비교한다. JSON 성공뿐 아니라 사건 근거 적합성, 근거 없는 의도 추정, 모순, 프로필 정정, 실행 가능한 지원을 사람이 평가한다.

60개는 예제 설계와 작은 시험을 위한 규모다. 이것만으로 모델 품질 향상, 실제 이용자 지원의 타당성, 교육 효과를 보장하지 않는다.

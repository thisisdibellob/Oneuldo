# 운영 형식 연결 및 토큰 검토 — 2026-09-24

**운영 형식 연결 도구와 검증을 만들었다. 하지만 60개 학습·25개 평가 자료 전체의 운영 형식 전환은 아직 완료되지 않았다.** 원본 85개는 변경하지 않았고, 변환 가능한 부분과 보완할 부분을 구분했다. 학습·배포·서버 설정 변경은 실행하지 않았다.

## 무엇을 확인했나

| 구분 | 학습 | 평가 | 결과 |
|---|---:|---:|---|
| 기존 후보 유지 | 60 | 25 | 원본 해시 동일 |
| 세션 분석 출력 변환 | 40 | 17 | 압축 출력·E/S 참조로 변환한 미리보기 57개 |
| 운영 DTO 입력 및 실제 프롬프트 생성 | 5 | 1 | 합성 입력 미리보기 6개 |
| 그 외 세션 입력 | 35 | 16 | 이번 변환기에 매핑이 없는 정보가 있어 보류 |
| 프로필 갱신 | 20 | 8 | 다른 입력·R 참조 경로이므로 분리 |

57개는 **출력 변환 수**다. 57개가 운영 입력까지 갖춘 학습 자료라는 뜻이 아니다. 입력 미리보기는 T01·T02·T03·T19·T48·E06이며, 이 6개도 의미 검토·대표성·이용 조건을 해결한 학습 승인본은 아니다.

현재 변환기에서 보류했다는 이유만으로 해당 정보를 서비스가 영원히 지원할 수 없다는 뜻도 아니다. 실제 수집 필드와 그 의미를 확인해 매핑하거나, 해당 정보를 제공하는 운영 입력으로 예제를 다시 작성해야 한다. 정보가 빠진 상태로 원래 정답만 유지하지 않는 것이 핵심이다.

## 학습할 단계

첫 대상은 **원본 사건을 읽는 세션 최종 분석 초안 단계(WHOLE_SOURCE_FINAL_DRAFT)**로 정했다. 긴 로그의 구간 관찰, 두 번째 AI 검토, 프로필 갱신을 같은 학습 형식으로 섞지 않는다.

운영 코드를 직접 호출했다.

- `AiBehaviorAnalysisPromptFactory.wholeSourceSystem()` / `wholeSourcePrompt()`
- `AnalysisReferences.encode()` / `read()`
- `AiBehaviorAnalysisValidator.validate()`

이 경로는 학교 설정처럼 입력 예산이 8192보다 크고 실제 예산 검사에 들어맞을 때 선택된다. 모든 실제 요청이 항상 이 경로를 타는 것은 아니다. `TimelineAnalysisPipeline`은 크기에 따라 다른 경로를 사용하고, 설정에 따라 별도의 AI 검토도 한다.

| 단계 | 운영 형식 | 이번 작업 |
|---|---|---|
| 세션 최종 분석 초안 | `s/f/a/u/p/c` 압축 JSON, `E1` 사건·`S1` 세션 | 출력 변환·일부 입력 연결 |
| 최종 분석 AI 검토 | `claim-evidence-v2`, 문장별 `text/evidenceEventIds` | 계약 확인, 학습 예제 변환 제외 |
| 프로필 갱신 | 누적 프로필 + 현재 분석, 허용된 `R1` 근거 | 입력 차이와 근거 누락 감사, 별도 처리 |

첫 단계만 학습한다고 두 번째 검토나 프로필 성능이 자동으로 개선된다고 가정하지 않는다. 나중에 어댑터를 어느 호출에 적용할지도 따로 연결해야 한다.

## 어떤 변환을 했나

기존 답변의 관찰·해석·판정·지원 문장은 그대로 두고, 필드 배열과 구조화된 참조만 바꿨다. 예를 들어 UUID 사건 세 개는 해당 요청의 `E1/E2/E3`로 바뀐다. 성공·실패를 계산하는 규칙은 추가하지 않았다.

```text
summary             → s
findings            → f: [id, skill, observation, interpretation,
                         alternativeExplanations, evidenceEventIds, suggestedSupport]
sessionAssessments  → a: [sessionId, judgment, explanation, evidenceEventIds]
uncertainties       → u
practicePlan        → p: 운영 계약에 정해진 순서의 배열
usedEvidenceCardIds → c
```

선택한 운영 원본 분석 경로는 문헌 카드를 전달하지 않아 `c`는 빈 배열이다. 원래 카드 ID는 원본 자료와 `migration-manifest.json`의 `removed_output_card_ids`에 보존했다. **문헌 인용을 지운 것만으로 답변 의미 검토나 자료 이용 조건 확인이 끝난 것은 아니다.** 카드 내용에 의존한 답변을 근거 없는 정답으로 만들지 않도록 모든 출력은 미리보기로 표시했다.

입력 변환은 확인된 수량 변경·장바구니·제출·종료 등의 필드에 한정했다. 없는 시작/제출 사건, 가격, 조작 주체를 추가하지 않는다. 목표는 첫 기존 사건의 부분 장면 스냅샷에 부착했다. 상품 이름은 합성 상품 식별자로 유지하며 현재 운영 카탈로그의 SKU나 가격으로 바꾸지 않았다.

시간이 없는 사건은 DTO를 읽기 위한 동일한 합성 시각과 경과 시간 0을 사용한다. 이는 실제 행동 속도 0초라는 관찰이 아니다. 별도 의미 검토 전 학습하면 안 되는 이유 중 하나다. E06의 명시된 14일 간격은 보존했다. 수신 상태인 `integrity`는 null로 두었으며, 초안의 `coverage=COMPLETE`를 수신 완료나 모든 장면 관찰의 증거로 바꾸지 않았다. 부분 관찰 사례는 이 구분을 다시 작성할 때까지 보류했다.

따라서 6개 입력은 **실제 DTO·프롬프트 생성기를 통과하는 최소 합성 스냅샷**이지, 실제 앱에서 수집한 완전한 장면·행동 로그와 같다는 주장이 아니다.

## 발견한 입력 차이

### 프로필 28개는 단순 변환으로 해결되지 않는다

운영 프로필 입력에는 이전 프로필과 현재 AI 분석이 들어간다. 초안처럼 모든 원본 사건과 별도 문헌 카드가 함께 전달되지 않는다. `AiUserProfileReferences`는 실제 이전/현재 분석에 연결된 사건만 R 참조로 허용한다.

- 28개 모두 이전 프로필이 간단한 요약 중심이며 운영 입력의 여러 필드가 빠져 있다.
- 22개는 목표 답변이 인용하는 사건 일부가 이전/현재 분석의 구조화된 근거 목록에 없다.
- 원본에만 있는 보고나 상충 값을 정답에 요구하면, 모델이 볼 수 없는 정보를 맞히도록 학습시키는 문제가 생긴다.

해결은 원본 사건을 무조건 정답에 복사하는 것이 아니다. 이전 프로필과 현재 분석에 사실·보고·불확실성이 근거와 함께 전달되는 합성 입력을 다시 작성하고, 그 입력으로 가능한 정답인지 재검토해야 한다. 현재 경로로 전달되지 않는 원본 대조 능력을 평가하려면 입력 경로 개선까지 별도 작업해야 한다.

### 세션 사례에도 추가 매핑이 필요하다

보호자/사용자 보고, 진행자 대리 조작, 재전송, 수신 누락, 자동 UI, 상충 목표, 별도 가격 정책 등은 현재의 보수적인 변환기가 처리하지 않는다. 일부는 운영의 다른 필드에 연결할 수 있고, 일부는 현재 실제 수집 여부부터 확인해야 한다. T15처럼 구간 분석이 추가된 사례는 이번 원본 직접 분석 단계와 입력 종류 자체가 다르다.

해당 필드를 버린 채 나머지만 통과시키지 않았다. 모든 사례의 원래 번호와 사유는 [사례별 연결 상태](mapping-review.ko.md)에 남겼다. T47의 라벨 의미 보류도 유지했다.

## 실제 토큰 측정

공식 [Qwen3.6-27B의 고정 리비전](https://huggingface.co/Qwen/Qwen3.6-27B/tree/6a9e13bd6fc8f0983b9b99948120bc37f49c13e9)에서 토크나이저 설정·대화 템플릿·모델 설정·라이선스만 확인했다. 모델 가중치는 다운로드하거나 로딩하지 않았다. 로컬의 기존 tokenizer.json은 고정 SHA-256을 검사해 사용했다.

| 측정 범위 | 개수 | 입력+정답 최소 | 중앙값 | 최대 |
|---|---:|---:|---:|---:|
| 기존 정규화 초안 | 85 | 1,586 | 2,277 | 2,922 |
| 운영 프롬프트 입력 미리보기 | 6 | 2,949 | 3,098.5 | 3,329 |

모두 이번 파일 기준 4096토큰 이내였다. **원본 모델의 대화 템플릿까지 적용한 길이**이며 글자 수로 추산하지 않았다. 다만 실제 긴 플레이 입력, 긴 프로필이나 변환하지 않은 79개가 같은 길이라고 가정할 수 없다. 4096에서 길이가 들어간다고 TITAN RTX 24GB에 학습이 들어간다는 뜻도 아니다.

`enable_thinking=false`, 무잘림·무패딩으로 측정했다. 템플릿을 한 번만 적용하고 별도 특수 토큰을 다시 붙이지 않았다. system/user 및 assistant 시작 부분은 학습 손실에서 제외하고 답변과 종료 토큰만 남길 수 있는지, 문자열과 토큰 경계 모두 검사했다. 실제 학습이나 역전파는 실행하지 않았다.

현재 GGUF 서버 모델이 이 원본 체크포인트에서 만들어졌다는 연결은 이번에 검증하지 않았다. 학습 시작 전 원본 가중치·토크나이저·서버 모델의 대응 확인이 남아 있다. 파일별 출처·해시는 [모델 메타데이터 기록](model-metadata/provenance.json)에 있다.

## 테스트 결과

- Java 3개 통과: 57개 압축 출력의 실제 파서·검증기 왕복, 6개 실제 프롬프트 생성 및 입력 불변성, 허위/다른 세션 참조 거부. 검증기가 성공·실패를 규칙으로 계산하지 않는지도 확인했다.
- Python 6개 통과: 미지원 필드·조작 주체·자동 UI를 버리지 않고 거부, 부분 수신 의미 보존, 새 목표와 이전 목표 분리, 프로필 분리, 원본 문장·판정 보존.
- 91개 길이 측정에서 프롬프트/답변 토큰 경계와 답변 종료 토큰 확인.
- 원본 학습 60개·평가 25개 및 이전 평가 동결본의 해시 확인.

구조 검사 통과는 내용 정확성이나 임상적 타당성 검증을 뜻하지 않는다. 이번에는 모델을 다시 호출하지 않았다. 이전 25개 응답/시간과 새 형식의 모델 성능을 같은 결과로 취급하면 안 된다.

## 다음에 해야 할 일

1. **60/25 규모는 유지하며 예제를 운영 단계별로 다시 작성한다.** 처음 정한 학습 40개 분석·20개 프로필, 평가 17개 분석·8개 프로필의 분리를 유지하되 입력을 해당 단계가 실제 제공하는 형태로 맞춘다. 서로 다른 단계의 프롬프트/출력을 하나의 형식으로 강제하지 않는다.
2. 보고·대리 조작·자동 UI 등 각 보류 이유를 실제 수집 필드와 대조한다. 필드가 없는 조건은 정보를 제공할 경로를 만들거나 현재 서비스 평가 범위 밖 사례로 명시한다. 없는 정보를 정답으로 요구하지 않는다.
3. 새 입력에 맞춰 정답의 근거·지원 분포를 재검토한다. 기존 카드 이용 조건·전문가 검토·T47 의미 합의도 해결한다. 이번 6개만으로 학습 자료가 충분하다고 판단하지 않는다.
4. 새 형식 평가본을 별도로 고정하고 같은 조건으로 새 기준 응답을 측정한다. 기존 `baseline-v1`은 수정하지 않는다.
5. 대응 원본 모델을 확인한 뒤 GPU 1에서 소수 스텝 메모리 시험을 한다. GPU 0 사용이나 운영 추론 중단은 이 작업에서 하지 않았다.

# 분석 전처리 개선 및 검증 — 2026-09-29

## 결과

실제 장보기 분석 스냅샷 **7,972개 사건**으로, 개선 후 전처리가 **225.102초(3분 45초)** 안에 첫 모델 호출 지점에 도달했다. 기존 실행은 **1,256.131초(20분 56초)**가 지나도 PREPARING 단계였고 모델 호출 전에 중단했다.

이번 측정은 맥에서 실제 전처리 경로를 실행하고 **모델 클라이언트 호출 지점에서 모의 클라이언트로 중단한 오프라인 시험**이다. 학교 서버에 분석을 전송하거나 AI 결과를 생성하지 않았다. DB 조회·저장·요청 지문 생성·네트워크 대기·GPU 추론은 측정에 포함하지 않았다. 이전 값은 실제 작업 실행 중의 하한이고 당시 동시 부하도 달랐으므로, 엄밀한 동일 조건 속도 배율로 해석하지 않는다.

입력은 이전 시험의 `remeasure-input.json`이다. 앱에 저장된 7,975개 중 분석 접수 이후 도착한 3개는 원래 이 스냅샷에 포함되지 않았으며, 이번 최적화에서 새로 제외한 사건은 없다.

## 수정 내용

1. **토큰 수 계산에서 불필요한 결과 변환 제거**
   - 기존 DJL `encode()`는 토큰 ID 외에도 문자열·마스크·문자 위치 정보를 Java 객체로 가져왔다.
   - 같은 해시 고정 Qwen 토크나이저와 같은 native encoding을 사용하되 ID만 읽는다.
   - native encoding은 `finally`에서 해제한다. 문자 수로 토큰 수를 추정하지 않는다.
   - 스레드 중단이 요청되면 다음 토큰 계산 전에 멈춘다.

2. **압축 후보 중복 계산 제거**
   - `LosslessEventColumns`는 한 번 비교한 현재 최적 후보의 토큰 수를 같은 재귀 호출 안에서 재사용한다.
   - `MovementInputEncoder`도 같은 후보의 토큰 수를 다시 계산하지 않는다.
   - 후보 형식과 동률일 때의 선택 우선순위는 유지했다.

3. **구간 검색 범위 축소**
   - 기존에는 매 구간마다 남은 사건 전체의 절반부터 압축·검사를 시작했다.
   - 처음에는 작은 구간으로 시작하고, 이후에는 직전 구간 크기를 출발점으로 삼는다. 두 배씩 늘려 한도를 넘는 범위를 찾은 다음 이분 탐색한다.
   - 채택하는 구간은 실제 토큰 수로 검사하며, 재시도 문구·출력 예약·200토큰 여유를 유지한다.
   - 전체 사건의 순서와 정확히 한 번씩 포함되는 성질을 유지한다. 구간 경계는 기존 방식과 달라질 수 있다. 최대 크기의 구간이나 같은 AI 문장 출력을 보장하는 알고리즘은 아니다.

4. **분석 실행 안에서 이미 만든 입력 재사용**
   - 요청 지문을 위해 만든 전체 프롬프트와 사건 ID 별칭을 파이프라인에 전달한다.
   - 같은 전체 프롬프트를 다시 압축하거나 같은 별칭을 다시 만들지 않는다.
   - 사용자 간 공유 캐시를 추가하지 않았다.

5. **전처리 진행 표시**
   - 구간 준비가 끝날 때마다 PREPARING에 준비된 사건 수/전체 사건 수를 보고한다.
   - 앱은 준비 단계에서 ‘기록’, AI 관찰 단계에서 ‘구간’ 단위로 표시한다.
   - 이 수치는 준비 범위이며 전체 분석 완료율이나 예상 잔여 시간이 아니다.

행동 판단 규칙, AI 지시문, 안전 검증 기준은 바꾸지 않았다. 기존 전처리 정책에 더하여 원본 사건을 선별하거나 제거하지 않았다.

## 검증

- **실제 입력 오프라인 벤치마크 1건 통과:** 기존 기본 인코딩과 개선된 압축 입력을 복원하고 전체 JSON 필드를 비교했다. 첫 요청의 실제 입력+출력 예약도 한도 이내임을 확인했다.
- **분석·AI 관련 테스트:** 141개 통과, 27개 조건부 테스트 건너뜀, 실패 0개.
- **AI 게이트웨이 테스트:** 9개 통과. 게이트웨이도 같은 토큰 계산 소스를 공유하므로 Java 21에서 검사했다.
- **프론트엔드:** `npm run typecheck` 통과.
- 추가 회귀 검사: 기존 tokenizer 전체 encoding과 새 count-only 결과를 한국어·영문·결합문자·이모지·공백·특수 토큰·긴 입력·동시 호출에서 비교했다. 여러 세션과 길이가 다른 96개 사건에서 순서·모든 사건 객체·원본 불변성·재시도 포함 토큰 예산·진행 보고를 확인했다.
- **전체 백엔드 테스트의 별도 실패:** 221개 중 187개 통과, 33개 건너뜀, `QuestMigrationTest` 1개 실패. 수정하지 않은 `V37__create_analysis_jobs.sql`의 PostgreSQL `timestamptz`를 H2가 지원하지 않아 초기화가 실패했다. 전처리 테스트 실패가 아니며 DB 마이그레이션 파일은 변경하지 않았다.

## 재현

저장소 루트에서 Java 25를 사용한다. 실제 스냅샷은 개인정보를 포함할 수 있어 Git에 넣지 않는다.

```bash
PREPARATION_BENCHMARK_SNAPSHOT="$PWD/output/closed-loop-pilot-20260929/remeasure-input.json" \
PREPARATION_BENCHMARK_RESULT="$PWD/output/closed-loop-pilot-20260929/preparation-result.json" \
backend/gradlew -p backend test --tests '*AnalysisPreparationBenchmarkTest' --rerun-tasks
```

이번 실행 결과는 로컬 `output/closed-loop-pilot-20260929/preparation-after-v2.json`과 `preparation-after-v2.log`에 있다. 출력에는 원본 로그 내용이나 API 키를 넣지 않았다.

## 남은 범위

전처리가 끝나더라도 41개 관찰 구간의 추론과 후속 통합·검토가 남는다. 이번 시간은 전체 분석 완료 시간이 아니다. 실제 학교 API로 끝까지 실행한 시간과 분석 품질, 추천 퀘스트 반복 효과는 별도로 측정해야 한다.

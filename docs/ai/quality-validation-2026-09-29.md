# 기존 3회 실험 기반 검증 규약·분석 품질 보완

작성일: 2026-09-29. 실제 호출 결과를 보존하면서 갱신하는 기록이다. **형식 검사 통과와 분석 내용의 타당성은 별개**다.

## 범위와 기준

[기존 3회 실험](ai-recommended-three-rounds-2026-09-29.md)의 저장된 원본, 구간 관찰, 분석을 사용했다. 이번 시험은 같은 데이터를 이용한 **최종 검토 및 프로필 단계의 새 모델 호출**이다. 플레이·전체 구간 분석·추천 퀘스트 생성을 모두 다시 실행한 실험은 아니다. 시험 중 운영 DB와 기존 프로필을 덮어쓰지 않는다.

- 1회차: 목표는 우유 1개와 바나나 1송이. 제출은 `milk:1, banana-single:1`. 이전 AI는 성공으로 오판했다.
- 2·3회차: 제출은 `milk:1, banana:1`. 목표 규격·수량과 일치한다.
- 3회차 프로필: 이번 요청의 허용 근거는 R1~R17인데 이전 본문의 `(R17,R18)`을 복사해 두 번 실패했다.
- 모든 능력·성패·지원 판단은 AI가 한다. 위 목표 대조는 실험 결과를 평가하기 위한 기준이며 운영 코드의 성패 판정 규칙으로 넣지 않았다.

## 검증 규약 변경

1. 프로필 입력·출력의 설명문에 있는 단독 괄호형 E/R 인용만 제거한다. 구조화된 `evidenceEventIds`, 상품 ID, 수량은 보존한다. 사건 ID는 요청마다 새로 매핑하므로 이전 본문 번호를 복사하면 잘못된 인용이 된다. 원본 AI 응답은 감사 기록에 남는다.
2. 이번 요청에서 허용한 실제 사건 UUID는 별칭과 동등하게 수용한다. 존재하지 않는 사건, 다른 요청의 UUID, 세션 ID를 사건처럼 인용하는 경우는 계속 거절한다.
3. 프로필 finding당 근거 상한을 8→30개로 맞춘다. findings는 0~12개, uncertainties는 0~20개로 분석 단계와 맞춘다. 관찰이 없다면 불확실성과 관찰용 계획이 필요하며, 실제 finding의 근거를 비워 통과시킬 수는 없다.
4. 재시도에 오류 코드·경로·잘못된 ID를 전달하고 감사 기록에도 저장한다. 무관한 근거로 자동 교체하지 않으며 재시도 상한은 2회다.

5. 최종 검토 문장의 괄호형 인용이 그 문장의 `evidenceEventIds`에 이미 들어 있고 실제 원본에도 존재하면 본문의 중복 표기를 정리하여 수용한다. 다른 문장의 근거, 없는 번호, 근거 배열의 중복·역순은 계속 거절한다. 새 인용을 보충하지 않는다.

의료적 추측이나 근거 없는 능력 판단을 허용하는 변경이 아니다. 형식상 불필요한 거절을 줄이는 변경이며, 의미 오류는 별도로 평가한다.

## 분석 프롬프트 변경

- 목표의 `acceptedProductIds`, 규격, 수량과 실제 제출 값을 대조하도록 명시했다. 허용 대체 상품을 단순 이름·distractor 분류로 오답 처리하지 않도록 함께 명시했다.
- 첫 보완(v15)에서는 여전히 이전 성공 결론을 따라갔다. v16은 원본 목표·사건을 앞에 두고, 검토 입력에서 이전 성패·요약·능력 해석·연습 계획을 제외한다. 이전 관찰과 지원 제안은 검토 대상으로 남기고, 새 판정은 원본에서 독립적으로 작성한다. 이전 전체 응답은 저장 기록에서 보존된다.
- 구간별 미확인 사항은 `localLimitationsToRecheck`로 구분한다. 내용은 보존하며, 다른 구간에서 확인된 사실은 최종 미확인 사항으로 복사하지 않도록 한다. 남는 한계의 선택·통합은 AI가 한다.
- 고정된 짧은 글자 수에 맞춰 규격·수량·근거 관계를 빼도록 하던 지시를 제거했다. 중복 설명은 줄이되 필요한 정보를 유지하도록 한다.

**남은 의미 오류:** 화면을 열었다는 기록을 실제 확인·읽기로 확대하는 표현, 도움 요청 동기를 추정하는 표현, 시각적 마커 등 조절 항목 밖의 지원 제안이 남는다. `reviewNotes`에 고쳤다고 쓰고 실제 문장은 그대로인 사례도 있다. 규격 판정 정정이 분석 전체 품질 해결을 뜻하지 않는다.

수정 분석의 연습 목표는 단순 품목 수집에서 **송이·팩·낱개 등 상품 규격 구분**으로 바뀌었다. 실제 퀘스트 생성·반복 플레이와 교육 효과는 이번 시험 범위가 아니다.

## 출력 상한과 배포

처음 2,400토큰을 요청한 6건은 배포된 게이트웨이의 상한 1,800 때문에 HTTP 400으로 거절됐다. 모델 추론 실패로 계산하지 않는다. 당시 백엔드 기본값은 호환성을 위해 1,800으로 유지했다.

게이트웨이 상한을 2,400으로 늘리고 인증된 `/api/limits`로 상한을 확인할 수 있도록 준비했다. 인증, 모델 제한, 전체 컨텍스트 제한, 입력·출력 합계 검사, 큐 제한은 유지한다. 무인증 요청과 상한 초과 거절을 포함한 게이트웨이 자동 검사 10개가 통과했다.

사용자가 20:27 KST 업데이트를 실행했다. 백업은 `/opt/oneuldo-ai/oneuldo-ai-gateway.jar.before-output-limit-20260929-202742`다. 이후 인증된 `/api/limits` HTTP 200 및 `maxOutputTokens=2400`을 확인했다.

확인 후 학교 백엔드의 최종 출력 기본값과 이 맥의 학교용 `local.properties`를 2,400으로 변경했다. 팀원 설정 스크립트도 학교 2,400 / 노트북 1,800을 구분하도록 변경했다. 구간 관찰 출력은 1,800, 전체 요청 예산은 18,000으로 유지한다. 전체 예산 안에서 출력 예약 공간이 600토큰 늘어나는 것이므로 입력에 무조건 600토큰을 더 허용하는 변경이 아니다.

로컬 실험 백엔드(18080)는 최종 출력 2,400을 명시해 재시작했고 퀘스트 조회 HTTP 200을 확인했다. 기존 격리 DB와 수동 분석 설정을 유지한다. 팀원 백엔드는 이 코드 반영과 재시작이 별도로 필요하다.

**출력 잘림은 4건 모두 없었다. 첫 시도 구조·판정 검증 통과는 3/4건**이다. 2회차는 `/sessionAssessments/0/explanation/3/evidenceEventIds`에 `[E7997,E1]`을 적었다. 해당 원문은 보존하고 구체적인 오류 위치를 전달한 교정 요청을 별도로 실행했다. 교정 요청도 61.27초·1,656토큰으로 끝까지 생성됐으나 `/summary/1`에서 `[E6321,E6965,E6323]`을 사용하여 다시 거절됐다. 문장도 우유 선택 후 도움 요청이 있었다고 서술했지만 원본 도움 요청은 우유 선택보다 앞선다. 단순 인용 정렬로 통과시키면 실제 서술 오류를 숨기므로 정상 결과로 저장하지 않았다.

최초 4건과 별도 교정 1건 모두 **출력 잘림 0/5**, 최초 구조·판정 검증 **3/4 통과**, 교정은 **0/1 통과**다. 순서 실패를 제외하고 성공률을 계산하거나 모델 출력 자체를 자동 수정하지 않았다.

화면 열기→확인·이해 확대, 도움 동기 추측, 구현 범위 밖 지원 제안은 별도 의미 품질 문제로 남는다. 전체 새 분석→프로필→퀘스트 경로는 이번 재시험 범위에 포함하지 않는다.

## 자동 검사

백엔드 관련 48개 검사 통과: 분석 서비스 22, 검토 문장 출력 14, 프로필 재분석 3, 신규 프로필 회귀 5, 최종 입력 예산 2, 원본 대조 자료 보존 2. 새 검토 입력이 기존 SUCCESS/FAILURE 값만 바뀌어도 동일하고, 원본 목표와 사건은 보존되는지 확인했다. 이 검사는 모델의 의미 판단 정확도를 증명하지 않는다.

이번 상한 반영 후 출력 예약 1,800·2,400을 비교하는 예산 검사 3개, 학교/노트북 설정 분리와 기존 개인 설정 보존 등을 확인하는 Python 검사 6개도 통과했다.

## 900과 1,000에 대한 정정

기존 실행은 `Limit=1000 / Requested=1200` 오류를 받았고 당시 최대 출력 설정이 1,200이어서 출력 측 제한으로 추정했다. 하지만 그 로그만으로 **계정의 고정 출력 상한이 1,000이라고 확정할 수 없다.**

이번 동일 입력 기반 진단에서는 최대 출력 **1,200 요청도 HTTP 200으로 수락**됐다. 따라서 900은 현재 앱의 보수적인 출력 예산이지 모델 또는 계정의 확인된 고정 최대치가 아니다. 과거 오류가 발생한 정확한 원인은 당시 세부 오류와 계정 한도 화면이 없어 미확정이다. 이번에 원인이 해소됐다고 단정하지 않는다.

현재 실 API 응답 헤더:

| 항목 | 값 | 의미 |
|---|---:|---|
| `x-ratelimit-limit-tokens` | 8,000 | 분당 토큰 한도(TPM) |
| `x-ratelimit-limit-requests` | 1,000 | 하루 요청 한도(RPD), 분당 요청 한도가 아님 |

Groq 공식 문서는 일부 조직에 ITPM/OTPM이 별도로 적용될 수 있으며, 정확한 입력/출력 세부 한도는 계정 Limits 화면의 TPM 값에 마우스를 올려 확인하도록 안내한다. 이번 진단은 로그인된 계정 화면을 확인하지 않았고, 입력/출력별 수치는 확정하지 않았다. [공식 한도 문서](https://console.groq.com/docs/rate-limits), [계정 한도 화면](https://console.groq.com/settings/limits).

요금제·모델·결제 설정은 변경하지 않았다.

## 무엇을 바꿨나

프롬프트 버전: `behavior-analysis-v9-compact-reduce`.

OBSERVE의 원본 로그 입력, FINAL 출력 계약, 프론트 코드는 변경하지 않았다. **REDUCE 전용 출력 계약**을 추가했다.

| 항목 | 이전 | 현재 REDUCE |
|---|---|---|
| 출력 지시 | 핵심 관찰 1~3개, 짧게 작성 | 650토큰 이내 목표, 최대 출력 설정 900 유지 |
| 요약 | 구체적 길이 지시 없음 | 60자 이하 |
| 관찰 | 길이 지시 없음 | 최대 2개, 사실·가설 각각 60자 이하 |
| 다른 설명 | 구체적 분량 지시 없음 | 관찰마다 60자 이하 1개 |
| 근거 | 실제 원본 사건 여부 검사 | 관찰마다 1~8개, **직접 입력한 하위 해석에 인용된 사건**인지도 검사 |
| 불확실성 | 짧게 권장 | 1~2개, 각각 60자 이하 |

650은 프롬프트의 목표이며 토큰 수에 따른 서버의 내용 자르기는 없다. 개수·문자 수·참조 범위는 출력 형식 검사다. 서버는 문장을 잘라 붙이거나 사용자 성공/실패를 계산하지 않는다. 기존 JSON/참조 오류 1회 재시도 및 실패 시 중단 정책을 유지한다.

두 하위 AI 해석의 `chunkAnalyses`는 저장 요청과 JSON 값이 완전히 같은지 검사한 뒤 전송했다. 원본 244개 사건과 이동 표본 169개는 수정·삭제하지 않았다. 어느 관찰을 묶고 어떤 근거를 인용할지는 AI가 정한다.

주의: 원본 보존과 **중간 AI 요약의 정보 보존은 별개**다. 관찰 수·근거 수를 줄이면 중간 요약에서 세부 사항이 빠질 수 있다. 반증·상충·도움·자료 한계를 숨기지 말라고 지시했으나 의미 보존을 자동으로 증명한 것은 아니다.

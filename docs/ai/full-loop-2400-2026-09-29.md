## 이번에 수집한 문제

### 1. 추천 퀘스트가 분석 계획 및 시나리오 계약과 충돌 — 진행을 막은 직접 원인

AI 분석의 practicePlan은 `itemCount=3`, 난이도 2다. S01은 우유 1개와 바나나 1송이로 고정된 2품목 시나리오다.

| API 요청 | 내부 응답 | 생성 내용 | 실제 코드로 재현한 거절 사유 |
|---|---|---|---|
| 1차 | 1 | S01, 우유+바나나 2품목 | AI_PLAN_ITEM_COUNT_MISMATCH |
| 1차 | 2 | S01, 우유+바나나+사과 3품목 | 시나리오 콘텐츠 계약 |
| 추가 1회 | 1 | S01, 우유+바나나 2품목 | AI_PLAN_ITEM_COUNT_MISMATCH |
| 추가 1회 | 2 | S01, 우유+바나나+생수 3품목 | 시나리오 콘텐츠 계약 |

같은 실행 백엔드의 Java 클래스와 카탈로그를 읽기 전용 진단 프로그램으로 호출하여 위 오류를 재현했다. 기록상의 포괄적 오류명만 보고 추정한 것이 아니다. 검증기는 잘못된 설정을 올바르게 거절했다. 프롬프트에는 CUSTOM 사용 및 품목 수 일치 지시가 이미 있지만 모델이 이를 지키지 않았다.

**우선 개선안:** AI에게 연습 계획에 맞는 시나리오 선택 가능 조건을 명시하고, 3품목 구성처럼 기존 S01 계약으로 표현할 수 없는 경우 CUSTOM을 선택하도록 출력 구조/교정 메시지를 보완한다. AI의 능력 판단을 코드로 대신하거나 검증기를 꺼서 통과시키는 방향은 적절하지 않다. 회귀 사례는 이번 4개 원문을 사용한다.

### 2. 구매 결과 판정은 정정됐지만 원인 해석은 여전히 과도하다

이번에는 목표 `banana`와 실제 `banana-single` 차이를 정확히 읽어 FAILURE로 판단했다. 이전의 성공 오판이 이 새 입력에서는 재현되지 않았다. 다만 “규격을 오인하거나 구분하지 못한 것으로 보입니다”라는 해석은 한 번의 선택만으로 확인되지 않는다. 같은 응답의 uncertainties는 의도적 대체·시스템 표시 혼동 등 이유를 알 수 없다고 적어 내부 긴장이 있다. finding별 alternativeExplanations도 비어 있다.

퀘스트 초안은 이를 더 강하게 “바나나 규격을 혼동하여 실패했습니다”라고 적는다. **분석의 불확실성이 다음 생성 단계에서 확정 원인으로 바뀌는 문제**다.

### 3. 화면을 연 기록을 내용 확인으로 서술한다

분석 observation은 장바구니를 열어 “내용물을 확인했습니다”라고 쓴다. 기록으로 확인되는 UI 열기와 실제로 읽고 비교·이해한 행동을 분리해야 한다. 이것이 자동 검증 통과만으로 의미 타당성이 보장되지 않는 사례다.

### 4. 오류 원인에 대한 연습과 난이도 변경의 근거가 약하다

2품목 과제에서 규격 오류가 발생한 뒤 plan은 3품목·수량 복잡도 MEDIUM으로 바뀐다. 이것이 반드시 부적절하다고 단정할 수는 없지만, 왜 항목을 늘리는 것이 포장 단위 대조 연습에 필요한지 설명이 없다. 이후 성공률을 비교할 때도 과제 부담 변화와 친숙도 변화를 분리해야 한다.

### 5. 전체 파이프라인 지연 및 진단 정보 부족

10분 29초짜리 플레이에 전체 분석만 32분 39초가 걸렸다. 47개 응답의 입력 토큰 합계는 약 61.7만이며, 같은 콘텐츠/조건을 반복해서 보내는 입력도 포함한다. 최종 검토만 약 82초였으므로 마지막 출력 한도 조정만으로 전체 지연이 해결되지 않는다. 구간 입력 표현과 중복 정보 처리 비용을 우선 측정해야 한다.

퀘스트 audit에는 상세 원인 대신 `INVALID_AI_QUEST`만 저장된다. 이번에는 별도 Java 재검증으로 품목 수/시나리오 계약을 구분했다. 경로·기대값·실제값을 audit에 남기면 다음 진단 비용을 줄일 수 있다.

### 6. 사용자에게 보여주는 구매 단위

기준 과제의 설명은 “바나나 1송이”지만 목록은 “바나나 1개”였다. UI의 단위 일관성을 먼저 맞춰야 모델/가상 사용자 선택과 화면의 혼동을 분리해서 검증할 수 있다.

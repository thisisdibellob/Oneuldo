# 적응형 대기·묶음 통합·체크포인트 적용 결과

> 후속: [최종 입력 축소 보고서](./final-input-compaction-report-2026-09-05.md)에서 같은 요청을 약 28% 줄이고 최종 분석 READY를 확인했다. 맞춤 퀘스트는 별도의 고정 시나리오 예산 불일치로 아직 실패했다. 아래는 축소 전의 검증 기록이다.

## 결론

요청한 네 가지 변경은 구현했다. **하지만 최종 사용자 분석·맞춤 퀘스트까지 성공하지는 못했다.** 이제 중간 통합은 통과하지만, AI가 인용한 원본 사건을 최종 프롬프트에 다시 붙이면 출력 예약 포함 약 9,500토큰으로 로컬 7,000 예산을 초과한다. `FINAL_EVIDENCE_EXCEEDS_LIMIT`에서 중단하며 FINAL/QUEST 호출은 0회다.

원본 사건 244개와 이동 표본 169개를 삭제하거나, 서버가 사용자 성공/실패를 대신 판단하지 않았다. 무손실 추가 압축 방식도 시험했으나 최종 입력을 예산 안으로 줄이지 못해 해당 실험 코드는 제거했다. 필요한 원문을 몰래 빼서 성공 처리하지 않았다.

## 네 가지 변경

| 항목 | 이전 | 현재 |
|---|---|---|
| 대기 | 매 분석 호출마다 고정 61초 | 공통 HTTP 클라이언트에서 요청 토큰 예약·실사용량·응답 헤더·입력/출력별 한도에 따라 부족한 경우만 대기 |
| 통합 | 무조건 두 개씩 | 실제 입력/출력 예약 토큰을 계산해 시간순으로 들어가는 만큼 묶음 |
| 문장 길이 | REDUCE 60자 초과 시 실패 | 60자는 작성 권장치. 일반 크기 상한·JSON·참조 검증 유지 |
| 재개 | 성공한 중간 단계도 재호출 | 검증된 단계별 응답을 DB 체크포인트로 저장하고 같은 입력이면 다시 검증 후 재사용 |

분석 버전: `behavior-analysis-v10-resumable`.

### 토큰 기반 대기

`AnalysisCallPacer`를 `RestGroqChatClient`에서 사용하므로 분석과 퀘스트가 같은 프로세스의 한도 관리기를 공유한다. 입력과 최대 출력을 예약한 뒤 공급자 `usage`로 실제 입력/출력량을 정산한다. 한도에 걸릴 때만 예약의 만료 또는 공급자 리셋/Retry-After까지 기다린다. 61초는 보수적인 사용량 계산 창이며 모든 요청의 강제 간격이 아니다.

- `GROQ_TPM`: 기본 7,000, 로컬 보수적 분당 예산.
- `GROQ_RPM`: 기본 30.
- `GROQ_ITPM`, `GROQ_OTPM`: 미확인 기본값 0. 설정된 하위 한도와 실제 오류에서 관측한 ITPM/OTPM을 적용한다.
- 공급자 헤더의 요청 한도는 **일일 요청 수**이므로 RPM으로 잘못 쓰지 않는다.
- 2분보다 긴 대기가 필요하면 요청을 무한히 붙잡지 않고 한도 오류로 종료한다. 실패/통신 불명확한 요청의 예약은 보수적으로 유지한다.
- 다른 서버 프로세스·다른 API 키의 같은 조직 사용량까지 완벽히 예측하는 분산 한도 관리기는 아니다. 429가 절대 발생하지 않는다는 보장은 없다.

이번 오류에서 **`OTPM Limit=1000 Used=572 Requested=900`**을 실제 확인했다. 이전의 추정과 달리 출력 측 분당 제한이라는 문구가 명시됐다. 확인된 계정 값 1,000을 로컬 설정 `GROQ_OTPM`에 반영했다. 모델의 컨텍스트 크기나 고정 단건 출력 최대치가 1,000이라는 뜻은 아니다. [Groq 한도 설명](https://console.groq.com/docs/rate-limits).

### 묶음 통합과 검증

현재 실제 입력에서는 **17개 → 2개(15개 묶음 + 2개 묶음) → 1개**로 통합했다. 성공한 통합 AI 호출은 총 3회다. 최초 묶음의 입력 계산은 6,076토큰으로, 출력 예약까지 계산해 로컬 예산 내에서 전송했다.

문장 길이는 권장으로 바꿨지만 JSON 계약, 일반 최대 크기(문자열 2,000자 등), 원본의 실제 사건, 직접 제공한 하위 해석의 근거 참조는 검사한다. `finish_reason=length`는 불완전 출력으로 처리하고 서버에서 문장을 잘라 붙이지 않는다. 재시도에는 허용된 기술 오류 코드만 추가하며 개인 로그를 오류 문구로 반사하지 않는다. 상세 필드별 오류 안내는 아직 모든 일반 계약 검사에 구현한 것은 아니다.

### 체크포인트와 재개

신규 테이블: `ai_analysis_checkpoints`(마이그레이션 V33).

- 사용자·데이터셋·모델·정확한 시스템/입력 프롬프트·출력 예산·온도를 묶은 SHA-256 키로 조회한다.
- JSON 객체의 속성 순서만 정규화한다. 배열 순서, 관측 값, 프롬프트 버전, 구간 접미사는 유지한다.
- 검증에 통과한 응답만 저장한다. 실패 응답을 성공 체크포인트로 등록하지 않는다.
- 재사용할 때도 현재 데이터 범위와 현재 검증기를 다시 적용한다.
- 기존 분석 감사 기록은 덮어쓰지 않고 새 분석 기록을 남긴다. 시도 기록은 LIVE/CHECKPOINT/PREFLIGHT 출처와 시스템·출력 예산·종료 사유·토큰 사용량 등을 구분한다.
- 저장된 결과와 스냅샷은 소유자 범위로 제한한다. 삭제되는 회원/스냅샷의 체크포인트는 외래키 연쇄 삭제된다.

재개 API: `POST /api/behavior-analyses/{analysisId}/resume`. 인증·분석 소유권을 확인한 뒤 같은 불변 스냅샷을 사용한다. 기존 `/datasets/{datasetId}` 재요청도 해당 스냅샷의 체크포인트를 이용한다. 새로운 스냅샷을 만든 요청은 같은 캐시로 간주하지 않는다. 프론트 자동 재개 UI는 추가하지 않았다.

과거 v8/v9 실행을 운영 캐시로 자동 승격하지 않는다. 이번 진단에서 과거 OBSERVE 17개는 이전과 같이 실제 JSON 값과 구간 접미사를 대조한 명시적 재사용이다. 이후 현행 프롬프트로 검증된 결과를 체크포인트 테스트 저장소에 저장했다. 운영 DB의 사용자 분석을 덮어쓰지 않았다.

| `final-quest-1788607366078/report.json` | 9.324초 | 1회 | 한도 설정 반영 후 남은 통합 성공. 최종 입력 크기에서 중단 |
| `final-quest-1788607679055/report.json` | 4.869초 | 0회 | 체크포인트 20개 재사용. 추가 압축 시험 후에도 최종 입력 초과 |

경로는 모두 `backend/build/diagnostics/` 아래이며 버전 관리 제외 대상이다. 마지막 두 번은 실제 AI를 전혀 재호출하지 않았다. 속성이 직렬화되는 순서가 실행마다 달라 캐시를 못 찾던 문제도 발견해, 의미를 바꾸지 않는 JSON 객체 키 정렬로 수정했다.

이번 새 실 API 호출은 총 4회(성공 3, 한도 거절 1). 성공 응답은 각각 354 / 598 / 897 출력 토큰이며 정상 종료했다. 새 실 호출의 HTTP 왕복 합계는 6.445초다. 이 수치를 최종 분석·퀘스트 전체 완료 시간이라고 표시하지 않는다.

## 최종 입력이 아직 막히는 이유

마지막 통합 결과뿐 아니라 **그 결과가 인용한 원본 사건 전체**를 최종 분석에 붙이는 구조다. 요약을 하나로 합쳐도 원문 분량은 충분히 줄지 않았다.

출력 예약 포함 로컬 토큰 계산:

- 17개 구간 결과를 최종 입력으로 조립: 약 36,000.
- 두 묶음으로 통합 후: 약 9,597.
- 한 묶음으로 통합 후: 약 9,500.
- 현재 예산: 7,000.

이는 새 AI 호출 전의 로컬 검사 실패다. 최종 사용자 판정, 연습 목표, 맞춤 퀘스트 결과는 생성되지 않았다. 단순히 글자 수 제한을 풀거나 호출 속도를 높인 것으로 해결됐다고 볼 수 없다.

다음 작업에는 선택이 필요하다. 원문 검토를 별도 AI 단계로 분리하고 최종 분석에 검토 결과를 전달하는 구조를 설계하거나, 이 입력을 수용하는 실제 API 한도를 확보해야 한다. 전자는 단계 간 의미 손실과 근거 연결을 별도로 검증해야 하며, 후자는 계정/서비스 변경과 비용 검토가 필요하다. 이번 작업에서는 원문 생략이나 결제 변경을 임의로 하지 않았다.

## 퀘스트 입력의 추가 정리

퀘스트 생성 프롬프트는 같은 60상품 카탈로그를 `availableProducts`와 `contentContext.products`에 중복 전달하고 있어 한 부를 제거하고 기존 무손실 표 표현을 적용했다. 전체 상품과 속성은 유지한다. 버전은 `market-ai-quest-v4-lossless`다. 실제 최종 분석이 나오지 않았으므로 이 변경의 **실 API 퀘스트 생성 성공은 미검증**이다.

## 회귀 검사

토큰 예약/정산, 헤더 대소문자, OTPM·Retry-After·일일 한도 처리, 한 번에 6구간 통합, 중간 실패 뒤 성공 단계 재사용, DB 체크포인트 재조회, 타 사용자 재개 거부를 검사했다. 전체 테스트는 **101개 중 99개 통과, 실 API 재호출 테스트 2개 제외, 실패·오류 0개**다. 실제 스냅샷 읽기 진단을 포함했다. 회귀 검사 통과와 위 실 API 전체 분석 실패는 구분한다.

백엔드를 새 코드로 재시작했고 실제 PostgreSQL에 V33 추가 마이그레이션을 적용했다. 운영 체크포인트 테이블은 향후 검증된 호출부터 채워지며, 이번 로컬 진단의 20개 체크포인트를 운영 테이블에 임의로 가져오지는 않았다. 기존 244사건 스냅샷은 유지했다.

# AI 판단·검증 문제 관리

최종 갱신: 2026-09-30. 이 문서는 실제 실패와 코드 확인 결과를 관리한다. 각 항목의 상태와 후속 기록으로 적용 여부를 구분한다. 수정 방향에 적힌 전체 계획이 한 번에 완료된 것은 아니다.

## 현재 결론

2026-09-30 반복 규격 오류 보완: 선택 상품의 실제 규격·단위를 최종 검토에 보존하고, 최근 3개 고유 플레이의 과제·안내·구매를 프로필과 추천에 연결했다. 1품목 CUSTOM 연습을 허용했다. 저장 실패 기록에서는 바나나·우유 오류를 모두 바로잡았고 정상 기록은 성공으로 유지했다. 최종 추천은 난이도 1·우유 1품목·비교/제거/교체 안내로 변경됐다. 프로필의 인지 해석 과장·세션 별칭 표기와 H2의 PostgreSQL 시간 타입·부분 인덱스 미지원으로 인한 마이그레이션 테스트 실패는 남아 있다. **새 과제를 플레이한 학습 개선 결과는 아니다.** [수정·실서버 검증](adaptive-practice-fix-2026-09-30.md), [AI 원문](adaptive-practice-raw-2026-09-30.md).

2026-09-29에는 3회 반복 실험의 원본으로 검토·프로필 단계를 재시험했다. 오래된 프로필 인용 번호 복사로 인한 거절은 보완 후 2/2회 통과했으나, 목표와 다른 규격을 허용 상품으로 잘못 해석하는 문제와 출력 잘림이 재현됐다. 형식 통과를 의미 품질 개선으로 계산하지 않는다. [수정 및 시험 기록](quality-validation-2026-09-29.md).

2026-09-21 팀원 장애 대응에서는 NET-001 공개 연결 실패를 최우선으로 조사한다. AI-008 예산 설정·계산은 코드 수정과 실제 서버 분석 검증을 마쳤으며 팀원별 코드·설정 반영이 필요하다. [조사 및 적용 결과](connectivity-budget-fix-2026-09-21.md).

문제는 모델의 판단 오류와 검증 규약의 불일치가 함께 발생한다. **27B 또는 Q4라서 생기는 문제라고 확정할 비교 실험은 없다.** 모델 교체 전에 근거 표현 규약과 검증기의 불필요한 거부부터 고쳐야 한다.

현재 말하는 ‘안전 검증’은 주로 JSON 형식, 원본 사건 참조, 문장별 검토 누락, 게임 설정의 허용 범위를 확인하는 검사다. 통과했다고 문장의 사실성·인지 능력 판단·교육 효과가 입증되는 것은 아니다. 반대로 실패했다고 모든 분석 내용이 틀린 것도 아니다.

행동의 의미, 과제 수행 판단, 필요한 지원은 AI가 판단한다. 코드는 존재하는 사건인지, 참조가 일치하는지, 실행 가능한 설정인지 검사한다. 성공·실패나 능력을 규칙으로 계산하는 방식으로 바꾸지 않는다.

### AI-001 — 요약 근거 허용 범위가 과도하게 좁음

- **확인된 사례:** 검토 4회차 `/summary`의 E1·E2, 5회차 `/summary`의 E1이 거부됐다. E1은 세션 시작, E2는 미션 제시이며 모두 원본에 존재한다.
- **코드상 원인:** `ReviewEvidenceChecks`는 요약의 허용 근거를 findings와 sessionAssessments의 `evidenceEventIds` 합집합으로 제한한다. 원본에 있는 미션 맥락도 하위 항목에 인용되지 않으면 거부한다.
- **영향:** 올바른 맥락을 요약에 사용하는 경우에도 구조 검증에서 탈락할 수 있다. 다만 ID가 존재한다는 사실만으로 그 ID가 문장을 뒷받침한다는 뜻은 아니다.
- **수정 방향:** 요약 전용 근거를 명시하고 원본 존재 여부를 검사하도록 규약을 정리한다. 하위 관찰에 불필요한 사건을 억지로 넣어 통과시키지 않는다. 요약과 근거의 의미 일치는 AI 검토 대상으로 유지한다.
- **완료 기준:** 원본의 미션 사건만 인용한 정당한 요약은 통과하고, 존재하지 않는 ID는 거부한다. 이 실행의 요약 사례를 저장 응답 재생과 실제 모델 호출에서 확인한다. 이 조치만으로 AI-002가 해결됐다고 처리하지 않는다.
- **관련 코드:** [ReviewEvidenceChecks.java](../../backend/src/main/java/oneuldo/behaviorlog/analysis/service/ReviewEvidenceChecks.java), [AnalysisReviewPrompt.java](../../backend/src/main/java/oneuldo/behaviorlog/analysis/service/AnalysisReviewPrompt.java).
- **완료 근거:** `/summary`를 원본 사건 전체와 대조하도록 변경했다. 새 실제 응답은 하위 항목에 없는 E1을 요약 근거로 사용해 정상 통과했다. 알 수 없는 ID 거부 등 자동 검사도 통과했다. 의미의 정확성은 완료 범위에 포함하지 않는다.

### AI-002 — 검토표와 최종 근거가 동기화되지 않음

- **확인된 사례:** 검토 5회차 `/findings/0/observation`의 `claimChecks`는 E3·E4를 포함하지만, 해당 finding의 최종 근거는 E104~E109다. E3·E4는 안내 화면 넘기기 사건으로, 최종 관찰이 서술한 사과 수량 조절 사건과 다르다.
- **코드에서 확인한 부담:** 같은 근거를 관찰 본문의 E번호, `evidenceEventIds`, `claimChecks`에 반복 작성한다. 프롬프트 앞부분은 “먼저 … claimChecks를 쓰고 … analysis를 새로 작성”, 뒷부분은 “문장을 수정한 후 … claimChecks를 쓴다”고 지시한다.
- **원인 판단:** 작성 순서 충돌과 중복 표현은 확인됐다. 이것이 이번 출력 불일치에 각각 얼마나 기여했는지는 아직 실험하지 않았다.
- **수정 방향:** 최종 주장과 AI가 선택한 근거를 한 곳에서 표현하도록 계약을 단순화한다. 다른 형식이 필요하면 그 근거에서 기계적으로 파생한다. 모델이 낡은 검토표와 수정된 문장을 따로 내지 않도록 작성 순서도 통일한다. 스키마 변경 시 게이트웨이 허용 스키마와 기존 클라이언트 호환성을 함께 확인한다.
- **완료 기준:** 해당 불일치가 재현 검사에서 검출되며, 수정 출력은 최종 문장과 근거가 일치한다. 원본에 존재한다는 이유만으로 무관한 E3·E4를 자동 추가하거나 검사 전체를 끄지 않는다.
- **관련 코드:** [AnalysisReviewPrompt.java](../../backend/src/main/java/oneuldo/behaviorlog/analysis/service/AnalysisReviewPrompt.java), [ReviewEvidenceChecks.java](../../backend/src/main/java/oneuldo/behaviorlog/analysis/service/ReviewEvidenceChecks.java).
- **후속 반영:** `claim-evidence-v2`에서 각 문장의 `text`와 `evidenceEventIds`를 함께 작성한다. `claimChecks`와 AI가 별도로 작성하던 상위 근거 목록은 제거했다. [ReviewedClaimOutput.java](../../backend/src/main/java/oneuldo/behaviorlog/analysis/service/ReviewedClaimOutput.java)가 같은 문장 객체에서 화면 인용과 공개 근거 목록만 구성한다. 새 문장이나 근거를 추론해 보충하지 않는다. 예전 형식은 저장 응답 재현에만 사용하며 실제 분석에서 자동 대체하지 않는다.
- **완료 범위:** 최종 v13의 전체 분석은 첫 검토에서 통과했고 두 finding의 원본 근거·화면 인용·공개 근거 목록 일치를 확인했다. 근거를 선택한 AI의 의미 판단이 옳다는 보장은 이 항목에 포함하지 않는다.

### AI-003 — 구체적인 오류 정보 없이 전체 분석을 다시 씀

- **확인된 사례:** 실제 오류는 특정 경로의 인용 불일치인데 최종 상태는 `INVALID_AI_ANALYSIS`다. 현재 예외에는 경로와 어긋난 ID가 없으며, 재시도는 `REVIEW_EVIDENCE_NOT_CITED` 같은 코드만 전달받는다.
- **코드상 원인:** 파이프라인은 대부분의 내용 검증 실패를 일반 오류로 묶는다. 재시도 지침도 중복 축소·JSON 완결 같은 공통 지침과 짧은 오류 문자열로 구성된다.
- **영향:** 모델이 어디를 고칠지 특정하기 어렵고, 전체 재작성 중 다른 항목이 바뀔 수 있다. 이번 재검토는 70.783초와 53.590초를 사용하고도 실패했다.
- **수정 방향:** 내부 감사 기록에 `code`, `path`, `offendingIds`, `allowedIds`를 구조적으로 보존하고, 재시도에 오류 항목을 전달한다. 최종 사용자에게는 이해 가능한 실패 이유를 보여준다. API 키나 원본 개인정보를 오류 메시지에 노출하지 않는다.
- **완료 기준:** 두 종류의 실제 불일치가 정확한 경로·ID로 기록된다. 재시도 후에도 전체 규약을 검사하며, 두 번째 실패의 세부 원인도 원본 응답을 수동 재파싱하지 않고 확인할 수 있다.
- **관련 코드:** [TimelineAnalysisPipeline.java](../../backend/src/main/java/oneuldo/behaviorlog/analysis/service/TimelineAnalysisPipeline.java), [ReviewEvidenceChecks.java](../../backend/src/main/java/oneuldo/behaviorlog/analysis/service/ReviewEvidenceChecks.java).

### AI-004 — 관찰 가능한 조작을 심리·인지 상태로 확대함

- **최근 사례:** 검토 4회차 해석에 “사용자는 안내문을 읽은 후 목표 상품이 위치한 선반 영역으로 이동하여 체류했습니다.”가 남았다. E3·E4는 `SHOP.BRIEFING_ADVANCED`이며 화면 넘기기 기록만으로 읽었다는 사실을 확인할 수 없다.
- **이전 사례:** 9월 17일 구조 검사를 통과한 검토에도 “구매 의도의 최종 단계로 기록된다”는 표현이 남았다.
- **수정 후 실제 응답:** 관찰·해석에 “장바구니 … 확인”을 단정하면서 uncertainties에는 읽었는지 확인할 수 없다고 썼다. “우연한 입력” 가설도 불확실성에 남았다. 인용 검증 통과 후에도 이 항목은 미해결이다.

### NET-001 — 외부 연결 문제는 판단 오류와 별도로 관리

2026-09-21 재조사에서도 공개 연결 실패를 재현했다. 동시 시험 10건 중 실패 7건은 맥에서 SYN 각각 6회 송신·서버 관측 0회였고, 성공 3건은 양쪽 시퀀스가 일치했다. 서버 관측 지점 이전 경로 조사가 필요하며 정확한 장비는 미확정이다. 학교 기본 예산·검토 예산 계산·진단 도구를 수정했으며, 네트워크 장애와 분리해 검증한다. [조사·수정 기록](connectivity-budget-fix-2026-09-21.md)을 참고한다.

- **미확정 사항:** 학교 상위 장비, 경로 정책 등 정확한 원인은 미확정이다. 모델이 근거를 잘못 인용하는 원인으로 볼 증거도 없다.
- **다음 작업:** 팀원·다른 접속망의 시각을 맞춘 연결 시험과 서버 패킷/상위 장비 기록을 대조한다. 품질 실험에는 연결 재시도 시간과 모델 호출 시간을 별도로 남긴다.
- **완료 기준:** 여러 접속망의 반복 시험에서 안정성을 확인하고 관측 기간·성공/실패 수를 기록한다. 일회 성공이나 서버 내부 성공만으로 해결 처리하지 않는다.
- **관련 자료:** [학교 서버 연결](school-server-connection.md), [연결 검증 기록](validation-2026-09-18.md#미해결-외부-tcp-연결).

# 반복 오류에 맞춘 분석·추천 과제 수정

작성: 2026-09-30. 대상: `unit-support-loop-20260930`에서 실제 앱으로 수행한 가상 사용자 3회 기록. 실제 지적장애인의 학습 효과를 검증한 자료가 아니다.

## 문제와 원인

세 번 모두 우유 900mL 1개·바나나 1송이를 요구했지만, 실제 제출은 `milk-small`(200mL) 1개·`banana-single`(낱개) 1개였다. 전체 실패 판정은 맞았으나 분석은 바나나를 목표 충족으로 잘못 설명했다. 추천은 계속 2품목·난이도 2·표준 문자 지원이었고, 목표 규격 재진술을 넘어서는 비교·수정 절차가 부족했다.

원인은 모델 의미 판단 오류와 입력·실행 계약의 제약이 함께 있었다.

- 최종 검토의 읽기용 원본 사본에는 상품 ID와 장바구니가 있었지만, 실제 선택 상품의 이름·용량·판매 단위가 누락됐다. 상세 원본에는 있었으므로 데이터 전체가 없었던 것은 아니다.
- 프로필·추천 단계는 분석 요약 중심으로 입력을 받았다. 직전 과제의 요구·실제 안내·최종 구매를 최근 여러 회차에 걸쳐 직접 비교하기 어려웠다.
- 품목 수 최솟값이 2여서 모델이 한 가지 규격에 집중하는 1품목 과제를 선택할 수 없었다.
- 같은 품목을 반복하는 것 자체가 문제는 아니다. 같은 오류가 반복됐는데 요구와 안내를 모두 그대로 반복하는 것이 이번 사례의 문제다.

## 코드 변경

1. `SourceEventDetails`에 당시 기록된 상품의 `id/name/detail/salesUnit/attributes/price`를 보존했다. 현재 카탈로그로 과거 값을 덮지 않는다. 최종 검토에는 요구 조건·선택 상품 속성·제출 장바구니를 함께 제공하며, 모든 목표를 각각 대조하도록 요청한다. 코드가 정답 여부를 계산하지 않는다.
2. `PracticeHistoryService`를 추가했다. 회원 소유의 원본 스냅샷과 프로필 연결을 조회해 최근 최대 3개의 서로 다른 세션에서 실제 과제·안내·선택 상품·제출을 전달한다. 같은 세션 재분석은 새 플레이로 세지 않는다. 이전 AI 판정과 원본을 구분하며, 원본이 없으면 `sourceAvailable=false`로 남긴다. 이력의 사건 ID는 새 인용 허가로 사용하지 않는다.
3. 프로필 갱신과 퀘스트 생성에 해당 이력을 연결했다. AI가 어려워한 요구와 이미 제공된 지원을 비교해 초점 기술과 변경할 수행 조건을 선택하도록 했다.
4. 분석·프로필·추천의 품목 범위를 1~4개로 맞췄다. 1품목은 `CUSTOM`으로 실행하며 기존 S01/S02의 고정 목표·예산은 유지한다. 프론트 타입도 일치시켰다.
5. 단순 목표 반복 대신 무엇을 보고, 무엇과 비교하고, 다르면 어디서 어떻게 바꿀지 짧게 안내하도록 요청했다. 이전 실수를 이번에도 이미 했다고 단정하지 않도록 조건부 안내를 사용한다. 실제 게임에 없는 UI나 배치 변경을 약속하지 않는다.
6. 분석·검토·프로필·퀘스트 프롬프트 버전을 올렸다. 새 이력과 프롬프트가 퀘스트 재사용 키에 포함된다. 과거 저장 결과는 소급 수정하지 않는다.

실패 횟수 → 난이도, 장애명 → 능력, 특정 상품 → 성공/실패를 계산하는 규칙은 추가하지 않았다. 난이도·지원·목표는 AI가 선택하고, 검증기는 실행 범위와 참조·형식을 확인한다.

- 전체 이동 로그의 관측 단계를 다시 돌리거나 새 가상 플레이를 만든 시험은 아니다.

## 남은 문제와 해석 한계

- 수정 후에도 프로필 요약에 “장바구니를 열어 내용을 확인”이라는 표현이 남았다. 화면 열기만으로 실제 읽기·확인을 입증할 수 없다. 원본을 보강하고 지시를 추가해도 의미 오류가 완전히 없어지지는 않았다.
- 프로필 본문의 S1/S2/현재 세션·R 범위 표기가 남아 세션별 설명이 혼동될 수 있다. v1에 있었던 잘못된 현재 세션 UUID 표기는 v2에서 없어졌으나, 별칭을 본문에 나열하는 문제는 남았다.
- v2 `uncertainties`의 “허용 목록의 품목 ID만 매칭했을 가능성”은 사용자의 관측된 사고가 아니다. 가능성이라는 말만으로 근거가 생기지 않으며 수정 대상으로 남긴다.
- 다른 규격·수량·예산 문제에서도 항상 적절히 조절하는지는 이 두 기록으로 보장할 수 없다. 구조 검사 통과와 내용 정확성을 구분한다.
- 새 퀘스트로 가상 사용자가 실제 학습했는지, 지원 없이 새로운 과제에도 적용하는지는 이번에 시험하지 않았다. 목표 수·안내 조건이 바뀌므로 이후 성공하더라도 곧바로 일반 능력 향상으로 계산하지 않는다. 먼저 지원받은 수행 여부, 다음에 지원을 줄인 전이 과제를 분리해 확인해야 한다.

## 자동 검사와 적용 상태

- 관련 백엔드 검사 **30건 통과**: 실제 상품 단위 보존, 단일 품목 CUSTOM 허용과 고정 시나리오 보존, 회원별 이력 조회·재분석 중복 배제, 최종 프롬프트 토큰 예약, 프로필·추천 계약, 동시 요청·완료 결과 재사용, 예산 오류 재시도, 설정값 우선순위.
- 프론트 검사 **10건 통과**, TypeScript 검사 통과. 1품목 과제에서 작은 우유를 담았다가 수량을 0으로 바꾸고 목표 우유를 담아 제출하는 실제 컴포넌트 조작·로그를 검사했다. 이는 앱 실행 가능성 검사이며 가상 사용자의 학습 성공으로 세지 않는다.
- 전체 백엔드 검사는 총 251건 중 최초 2건 실패·40건 건너뜀. 한 건은 이미 사용 중인 최종 출력 2,400토큰을 여전히 1,800으로 기대하던 테스트를 수정하고 재검사했다. 다른 한 건은 기존 V37 마이그레이션의 PostgreSQL `TIMESTAMPTZ`를 H2가 지원하지 않는 `QuestMigrationTest` 실패로 남아 있다. 이번 변경에는 DB 스키마 수정이 없다. 전체 검사가 전부 통과했다고 보고하지 않는다.
- 로컬 테스트 백엔드 18080을 새 코드로 재시작하고 기동을 확인했다. 학교 모델·게이트웨이 재설치나 운영 DB 결과 수정은 하지 않았다. 운영 팀원 백엔드에서도 이 변경 코드를 실행해야 반영된다.
- 기존 결과는 보존되며 새 버전으로 수행하는 분석·추천에 적용된다. 테스트용 저장 결과를 사용자 프로필에 자동으로 덮어쓰지 않았다.

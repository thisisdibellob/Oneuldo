# 분석 시간 및 복구 개선 (2026-09-08)

## v13: 관찰 범위와 설명 복원

분석이 지나치게 간략하다는 피드백에 따라 다음 생성부터 관찰 지침을 변경했다. 근거가 충분한 구간은 서로 다른 관찰 3~5개, 최종 분석과 누적 프로필은 서로 다른 항목 2~3개를 목표로 한다. 근거가 부족하면 적게 작성하며 항목 수를 채우기 위해 행동을 만들지 않는다. 20~40자 고정 문장 제한을 없애고 실제 행동·해석 이유·실행 가능한 지원을 완결된 문장으로 작성한다. 재시도에서도 무조건 한 항목만 남기는 지시는 제거했다.

요청별 출력 상한 900토큰과 근거 검증은 유지한다. 분량 증가에 따른 실제 출력 잘림 빈도와 품질은 API 한도 회복 후 검증해야 한다. 프롬프트 버전을 변경해 이전의 짧은 분석을 새 요청의 캐시 결과로 재사용하지 않으며 기존 보고서는 소급 변경하지 않는다. 아래 v12 항목 수와 측정치는 변경 전 기록이다.

## 추가 변경: 실제 429 응답 후 재시도

아래 최초 검증 시간은 선제 대기가 있던 버전의 측정치다. 이후 요청별 토큰 예약량과 성공 응답의 잔여 한도로 61초를 미리 기다리던 동작을 제거했다. 입력 크기 제한과 구간 분할은 유지한다.

공유 HTTP 클라이언트가 먼저 전송하고 실제 HTTP 429가 오면 Retry-After, 오류 본문의 재시도 시간, reset 헤더 순으로 대기 시간을 정한다. 시간 안내가 없을 때만 61초를 사용한다. 대기 상태는 기존 작업 진행 표시로 전달하며 다른 요청도 이미 확인된 제한 해제 시각을 존중한다.

대기 후 거절된 요청의 동일 프롬프트·출력 상한으로 최대 3회 재시도한다(최초 포함 4회). 이미 성공한 구간은 재전송하지 않는다. 관찰, 최종 통합, 프로필 갱신 모두 적용된다. 2분을 넘는 긴 한도 대기는 워커를 계속 점유하지 않고 실패 처리하며, 기존 체크포인트와 프로필은 유지된다. 출력 잘림이나 입력 길이 초과는 429와 별개로 처리한다.

## 1. 최종 통합 입력 제한

구간별 관찰 결과와 그 결과가 인용한 이벤트의 ID·세션·상대 시간·종류만 최종 단계에 전달한다. 전체 원본 타임라인과 장면 데이터를 다시 붙이지 않는다. 최종 입력이 예산을 넘으면 최대 4개 구간 결과씩 재요약한다. 사실, 가설, 대안 설명, 불확실성을 분리하고 하위 결과에 없는 근거 인용을 거부한다.

최종 모델은 원본을 직접 재검토하지 않는다. 참조 검증은 존재 여부와 범위 검증이며, 해석의 정확성을 보증하지 않는다. 원본 스냅샷은 보관한다.

## 2. 구간 입력과 호출 수 축소

ObservationInputCompactor가 전송 시각, 앱 버전 등 분석에 반복되는 메타데이터를 제외하고 해당 구간·과제에서 참조한 상품 정보만 전달한다. 상대 시간, 이벤트 순서, 실제 행동 payload와 관련 장면 정보는 유지한다. 상품 정보의 생략 범위도 프롬프트에 명시한다.

분할은 실제 토크나이저로 비용을 계산하며 시간순으로 한 호출에 들어가는 최대 연속 구간을 선택한다. 출력 900토큰과 재시도 지시문 여유를 함께 예약한다. 900은 입력 구간 크기가 아니라 응답 상한이다.

이동 로그 개선 후 동일 입력으로 비교한 관찰 호출 수:

| 플레이 | 기존 분할 | 새 분할 |
| --- | ---: | ---: |
| 최근 (81 이벤트) | 5 | 3 |
| 이전 (179 이벤트) | 9 | 5 |

이 표에는 최종 통합 및 필요한 누적 프로필 호출이 포함되지 않는다.

## 3. 짧은 출력과 부분 복구

관찰 결과와 최종 결과는 짧은 키·배열 형태의 JSON으로 생성하고 서버에서 기존 도메인 형식으로 복원한다. 관찰은 최대 2개, 최종 결과와 프로필은 핵심 내용을 짧게 쓰도록 지시한다. 구조와 근거 ID 검증은 유지한다.

잘린 응답은 더 짧은 출력 지시로 재시도한다. 관찰 단계에서 계속 잘리면 실패 구간만 둘로 분할한다. 성공한 호출은 체크포인트로 재사용한다. 무한 재시도 대신 호출·분할 상한을 둔다. 작은 입력의 단일 호출 경로 및 최종/프로필 출력은 재시도 후에도 실패할 수 있다.

## 4. DB 작업 큐 및 앱 복원

- POST `/api/analysis-jobs/sessions/{sessionId}` 또는 `/latest`: 소유권 확인 후 고정 입력 스냅샷을 지정한 작업 접수, HTTP 202 반환.
- GET `/api/analysis-jobs/current` 또는 `/{id}`: 로그인한 사용자의 상태만 반환.
- 작업 상태: QUEUED → RUNNING → READY/FAILED. 관찰/재요약/최종/프로필 단계, 완료 구간 수, 한도 대기 종료 시각을 DB에 저장한다.
- 단일 워커로 기존 제공자 호출 한도를 공유한다. 동일 입력의 진행 중 작업과 같은 프롬프트 버전의 성공 작업은 중복 접수하지 않는다.
- 워커는 10초마다 45초 임대를 연장한다. 서버 중단 후 임대가 만료되면 같은 스냅샷으로 재개하고 성공 체크포인트를 재사용한다. 반복 중단은 3회 시작 후 실패 처리한다.
- 앱은 작업 접수 응답만 기다리고, 분석 탭에서 진행 중에는 3초 간격으로 상태를 조회한다. 앱 복귀 시 다시 조회한다. READY 조회 후 프로필을 읽어 완료 직전의 오래된 프로필 표시를 방지한다.
- 프로필 갱신 성공 전까지 기존 프로필을 유지한다. 앱 종료는 서버 작업을 취소하지 않는다. 서버가 꺼져 있는 동안에는 처리가 정지하며 다시 실행된 뒤 복구된다.

## 검증

- 프론트 전체 25개 스위트, 140개 테스트 통과. 이후 계정 변경 응답 경합 수정에 대한 분석 탭 6개 테스트 및 TypeScript 검사 통과.
- 백엔드 분석·프로필 78개 테스트 중 70개 실행 통과, 선택 실행 진단 8개 생략. 격리된 PostgreSQL 스키마에서 중복 접수, 사용자 소유권, 저장, 임대 만료 복구 검증 포함.
- 실제 이전 플레이: 관찰 5회와 최종 1회 후 성공. 최종 입력 2,849토큰, 작업 접수부터 프로필 준비까지 약 5분 31초. 과거 실패 입력과는 이동 로그 양도 달라 직접적인 속도 비율 비교는 하지 않는다.
- 실제 최근 플레이: 관찰 3회와 최종 1회, 분석 243,055ms(4분 3초). 최종 입력 2,109토큰. 누적 프로필 병합 1회 60,701ms 후 버전 2 READY. 앞 작업의 큐 대기를 제외하면 분석·프로필 처리 합계 약 5분 4초이며 재시도는 없었다.
- 실제 앱 종료·재실행 중에도 서버 작업이 계속 진행됐다. 인증 API 조회로 작업 진행 중 기존 READY 프로필 유지도 확인했다. 두 작업 모두 최종 READY 상태를 DB에서 확인했다.

무료 API의 분당 호출·토큰 제한으로 인한 대기는 남는다. 호출 수와 실패 재작업을 줄인 것이며 몇 초 내 완료를 보장하지 않는다.

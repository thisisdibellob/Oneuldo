# 가상 사용자 장보기 반복 검증 — 예비 실험

## 질문과 범위

동일한 가상 사용자 초기 조건에서 `앱 플레이 → 실제 AI 분석/프로필 → AI 추천 퀘스트 → 앱 플레이`가 연결되는지, 일반 과제 반복과 어떤 수행 차이가 생기는지 확인한다. 실제 지적장애인의 교육 효과, 진단 정확도 또는 임상적 타당성을 평가하는 실험은 아니다.

행동 생성은 `mild-intellectual-disability-adult` v5 / stochastic policy v5를 사용한다. 분석과 추천은 학교 서버의 기존 Qwen 모델/운영 프롬프트를 사용한다. 행동 생성 모드와 분석 AI를 혼동하지 않는다. 운영 모델 교체나 파인튜닝은 하지 않는다.

## 실행 전 고정 조건

- 별도 로컬 PostgreSQL DB `oneuldo_pilot_20260929`, 별도 JWT 키, 맞춤/비교 전용 계정 두 개.
- 앱 `127.0.0.1:18082`, 백엔드 `127.0.0.1:18080`, 재생 bridge `127.0.0.1:8765`.
- 최초 두 경로 모두 `S01`, 배치 seed `pilot-baseline-20260929`, actor seed `pilot-round-1`. 첫 방문, 이월 기억 없음.
- 경로별 3회: 1회차 공통 출발 과제, 2~3회차 맞춤 경로는 직전 분석에 연결된 AI 생성 과제, 비교 경로는 사전에 고정한 일반 과제 S02/S01.
- 대응 회차는 같은 actor seed `pilot-round-N`. 이는 반복실행 변동 통제이며 독립 표본 여러 명으로 세지 않는다.
- 향상 해석 전에는 두 경로 모두 같은 조건의 별도 최종 평가 과제가 필요하다. 훈련 과제의 성공률만으로 향상을 판정하지 않는다. 예비 3회가 완료되어도 최종 평가 없이는 교육 효과 결론을 내리지 않는다.
- 실패한 seed를 성공할 때까지 바꾸지 않는다. 생성 실패, UI 재생 실패, 전송 실패, 분석 실패, 추천 실패를 구분해서 남긴다.

## 경험과 분석의 분리

기존 `trace.attentionExperience`는 계획의 기억이다. 다음 회차에는 이를 그대로 넣지 않는다. `market-simulator/pilot-evidence.cjs`는 전체 step의 실제 완료, trace/snapshot 바인딩, 이동 검사, DB에 저장된 세션의 순번·중복·종료 기록을 확인한다. 그 후 실제 수행된 조작 종류와 실제 드래그한 상품 정보만 별도 경험으로 구성한다. 분석 결과, 다음 과제 정답, 계획상 보았을 뿐인 상품/공간 기억을 복사하지 않는다. 다른 계정의 기억 이월도 거부한다.

현재 actor는 안내 문장의 교육 내용을 이해해서 전략을 새로 습득하는 학습자가 아니다. 기존 정책의 첫 방문/재방문 차이와 친숙도 자체도 설계된 동작이다. 오류 확률이나 능력 파라미터를 회차에 따라 임의로 낮추지 않지만, 이 정책으로 관측한 변화는 **합성 정책의 적응**으로만 해석한다. 교육적 지원 문구의 효과는 현재 방식으로 검증할 수 없다.

## 증거와 측정

- 원본 앱 tracker/queue가 행동 로그를 기록·전송한다. 생성 trace를 BehaviorLog로 변환해 업로드하지 않는다.
- 제출 직전 앱의 실제 장바구니를 replay report에 복사한다. 계획의 마지막 장바구니를 실제 결과로 보고하지 않는다.
- 과제별 목표 품목/수량 차이, 목표 밖 구매, 예산 충족, 소요 시간, 목록·장바구니 확인·도움 요청 횟수를 기록한다.
- 도움 없이 수행했는지는 지원 종류와 함께 해석한다. 비어 있는 계산대에 직원 호출이 필요했던 상황을 인지적 도움 의존으로 단정하지 않는다.
- 시간 감소나 목록 확인 감소만을 개선으로 간주하지 않는다. 과제 난이도·물품 수·수량·지원 조건을 함께 제시한다.
- `QUEUED`/`RUNNING`을 분석 성공으로 보지 않는다. `READY`와 현재 세션의 analysisId, 그 분석에 연결된 `source=AI` 추천이 있어야 맞춤 다음 회차로 넘어간다. 정적 fallback은 맞춤 결과로 세지 않는다.

## 재현 도구

기존 `market-simulator/cli.cjs interactive`의 pair/generate/validate/play/status 도구를 사용한다. 상세 사용법은 [재생 안내](../../market-simulator/README.md)를 따른다. 실험 계정의 로그인 비밀번호/API 키/pairing 토큰은 문서에 기록하지 않는다.

개발용 재생 URL에 `marketPilotScenario=S01`을 추가하면 명시적으로 고정 기본 과제를 사용한다. AI 맞춤 회차에서는 이 옵션을 제거한다. `marketPilotLayout`은 매장 배치 재현용 seed다. 일반 앱/네이티브/운영 모드에서는 이 옵션을 적용하지 않는다.

재생이 완료되면 실제 DB 증거를 수집한다:

```sh
node market-simulator/scripts/record-pilot-round.cjs \
  output/closed-loop-pilot-20260929 matched-round-1.json \
  REPLAY_UUID oneuldo_pilot_20260929
```

출력: `.replay.json`, `.receipt.json`, `.measurement.json`, `.experience.json`, `.job.json`. 파일을 덮어쓰지 않는다. 다음 생성에는 experience의 `visit`, `previousLayoutKey`, `memory`만 전달하고 provenance는 실험 증거로 따로 보존한다.

실행 결과와 중단 사유는 이 문서의 후속 결과 절에 기록한다. 단위 테스트의 fixture는 실제 플레이 자료가 아니다.

## 첫 실행 중단 당시의 범위와 병목

**첫 실제 플레이만 완료됐으며, AI 분석·추천 및 3회×2경로 비교는 완료되지 않았다. 향상 여부는 판단할 수 없다.**

1. 학교 공개 API 연결이 불안정했다. `/healthz`는 일부 시도에서 HTTP 200이었지만, 마지막 성공도 TCP 연결까지 11.22초가 걸렸다. 인증을 포함한 `/api/tags`는 12초·12초·35초·15초 연결 시간 초과로 응답을 받지 못했다. 따라서 서버가 항상 꺼져 있다거나 키가 틀렸다고 판정할 수 없다. 상태 확인 한 번의 성공을 분석 가능 상태로 간주하지 않았다.
2. 로컬 분석 작업을 실제로 시작했으나 중단 직전까지 약 237초 동안 `PREPARING`이었다. 스레드에서 `LosslessEventColumns.smaller → QwenTokenCounter.count → TokenizersLibrary.getTokens`가 실행 중임을 확인했다. 원문을 무손실 형태로 압축하기 위한 반복 토큰 계산 단계다. 이 측정은 **전처리에 이미 소비한 시간**이며 전체 소요 시간이나 모델 추론 시간이 아니다. 모델 호출 단계에 도달하지 않아 분석 결과·안전 검증 결과·AI 추천 퀘스트는 없다.
3. 현재 stochastic actor는 교육 문구의 의미를 학습하지 않는다. 향후 실제 추천이 나와도 이 도구만으로 교육 내용의 효과를 검증할 수 없다. 별도의 학습자 상태 모델 검증과 실제 참여자 평가가 필요하다.

추가 결과를 만들지 않고 작업용 백엔드를 중단했다. 중단 전 작업 상태는 `RUNNING/PREPARING`, `analysis_id=null`이며 `FAILED`라고 바꿔 기록하지 않았다. 재시작 시 기존 lease 만료 작업을 복구하는 백엔드 로직으로 이어갈 수 있다. 실험용 앱/bridge/잠자기 방지 프로세스도 종료하고 DB·실행 증거는 보존한다. 운영 AI 서버와 기존 앱 서비스는 변경하지 않았다.

재개 순서:

1. 학교 공개 API의 **인증 요청**이 정상 응답하는지 먼저 확인한다. 원인 진단이 필요하면 그때 서버 SSH를 사용한다.
2. 동일 데이터로 전처리 비용을 측정하고, 무손실 압축의 반복 토큰 계산/중복 인코딩을 줄이는 개선을 별도 검증한다. 로그를 임의로 삭제해서 통과시키지 않는다.
3. 격리 백엔드의 분석 worker를 다시 켜고 저장된 1회차 세션으로 분석을 완료한다. `READY` 및 같은 analysisId의 AI 추천을 확인한 뒤에만 맞춤 2회차를 실행한다.
4. 비교 경로 및 공통 사후 평가까지 완료한 후 과제 조건과 함께 결과를 비교한다.

현재 체크포인트: 세션 `7711d319-dffe-4f95-b023-0f52d5da2341`, 분석 작업 `767424bc-d9ed-4875-9169-50d4e5c8379e`. 비밀 설정은 기존 `output/closed-loop-pilot-20260929/application-pilot.properties`에만 있다. 해당 파일과 `accounts.json`/pairing 설정은 공유하거나 Git에 추가하지 않는다.

## 재측정 결과 — 2026-09-29 13:59~14:20 KST

사용자의 재측정 요청에 따라 **전처리 코드·모델·토큰 한도를 변경하지 않고** 같은 격리 DB의 작업을 재개했다. 운영 서버에 설정 변경이나 배포는 하지 않았다.

### 연결과 분석 준비

| 검사 | 결과 |
|---|---|
| 인증 `/api/tags` 5회 | 성공 2회(0.348초, 2.065초), TCP 연결 시간 초과 3회(각 약 10초) |
| 실제 짧은 `/api/chat` 1회 | 성공, 응답 “연결 성공”, 전체 22.173초 |
| 위 짧은 호출의 모델 보고 시간 | 전체 16.941초, 그중 모델 로딩 16.583초. 본 분석 성능으로 일반화하지 않음 |
| 본 분석 준비 | 13:59:42.714 시작 → 14:20:38.845 마지막 확인, **1,256.131초(20분 56초)에도 미완료** |
| 중단 직전 상태 | `RUNNING / PREPARING`, `analysis_id=null`, 오류 코드 없음 |
| 중단 이유 | 재측정 도중 정한 전처리 20분 관찰 상한을 넘겨 수동 중단. 자연 완료나 시스템 오류 종료가 아님 |

**20분 56초는 전처리에 이미 소요된 시간의 하한이다. 완료 시간 또는 모델 추론 시간이 아니다.** 최종 입력 분할이 끝나지 않았고, 본 분석의 모델 호출·결과 검증·프로필·추천 퀘스트 단계에는 도달하지 않았다. 별도의 짧은 모델 호출은 성공했지만 반복된 TCP 시간 초과 때문에 공개 접속이 안정적이라고 판단할 수 없다.

입력 범위를 다시 대조했다. 전체 저장 로그는 7,975개지만, 앱이 구매 제출 시 생성한 고정 분석 스냅샷은 **7,972개 / JSON 31,908,859 bytes**다. 이후 생성된 `SHOP.CHECKOUT_PROXIMITY_EXITED`, `SHOP.MOVEMENT_STOPPED`, `SHOP.SESSION_ENDED` 3개가 해당 스냅샷에는 없다. 재측정 중 데이터를 잘라낸 것이 아니며, 이전 작업과 동일한 스냅샷을 재사용했다. “전체 저장 로그 수”와 “실제 분석 입력 수”를 구분해야 한다.

스레드 관찰에서 초반 원문 인코딩을 지나 `TimelineAnalysisPipeline.partition → observationCost → MovementInputEncoder → LosslessEventColumns/QwenTokenCounter`로 진행한 것을 확인했다. 구간 크기 이진 탐색 중 여러 후보를 다시 압축하고 토큰화한다. 토크나이저의 `encode`는 길이 계산에 사용하지 않는 토큰 문자열·타입·마스크·문자 위치도 가져온다. 이는 비용을 줄일 후보이며, 이번에는 변경하지 않았다. 반복적으로 동일한 메서드에 있었다는 사실만으로 무한 루프라고 단정하지 않는다.

시간은 개발 환경의 실제 경과 시간이다. 약 14:06부터 비교 경로의 웹앱 재생도 같은 Mac에서 병행했으므로, CPU를 독점한 순수 마이크로벤치마크로 해석하지 않는다. 분석 스레드가 실제 계산 중인 것과 모델 호출 전 단계인 것은 별도로 확인했다.

# 검증기 수정 및 실제 분석 확인 — 2026-09-18

## 결과

요약의 정상 근거를 거부하던 문제를 수정했다. 학교 모델로 합성 장보기 사건 208개를 새로 분석한 결과 **READY, 227.497초(약 3분 47초), 모델 호출 4회, 검증 재시도 0회**였다. 연결 재시도와 출력 잘림도 없었다.

백엔드의 실제 분석 파이프라인과 공개 학교 HTTPS를 사용했다. 저장된 모델 응답을 재사용하지 않았으며 DB·사용자 프로필에는 쓰지 않았다. 앱 로그인부터 누적 프로필·퀘스트 생성까지 전체를 검사한 결과는 아니다. 검증 통과 후에도 의미 판단 오류가 남아 있어 아래에 별도로 기록한다.

| 비교 | 수정 전 | 수정 후 |
|---|---|---|
| 입력 | 동일한 합성 장보기 사건 208개 | 동일 |
| 결과 | FAILED | READY |
| 전체 시간 | 335.227초 | 227.497초 |
| 모델 응답 수 | 5회 | 4회 |
| 검토 | 2회 모두 인용 검사 실패 | 첫 검토 통과 |
| 연결 | 첫 호출 연결 2회 실패 후 성공 | 연결 재시도 없음 |
| 출력 잘림 | 없음 | 없음 |

입력은 같지만 모델 출력과 연결 상황이 달랐다. 시간 차이 전체를 검증기 수정의 성능 효과로 해석하지 않는다. 실제 모델 검사는 1회이며 반복 안정성까지 입증한 것은 아니다.

## 무엇을 바꿨는가

1. **요약 근거를 독립적으로 검사한다.** 이전에는 하위 finding·sessionAssessment의 근거 합집합 안에 있어야 했다. 이제 `/summary`의 `claimChecks`는 제공된 원본 전체에서 선택할 수 있다. 미션이나 세션 시작처럼 하위 관찰에 없어도 필요한 맥락을 허용한다. 존재하지 않는 사건·중복·역순 검토 목록은 계속 거부한다.
2. **본문에 적은 관찰 근거를 검토표에서도 빠짐없이 확인한다.** 이전에는 본문에서 E1·E2를 인용하고 검토표에는 E1만 있어도 통과할 수 있었다. 이제 누락된 E2를 검출한다. 서버가 근거를 대신 채우지 않는다.
3. **재시도에 오류 위치를 알려준다.** 인용 불일치와 관찰 검토 누락에 대해 `validationFailure: {code, path, offendingIds}`를 감사 기록에 저장하고 재시도 입력에 전달한다. 재시도까지 실패한 경우에도 상세 정보를 남긴다. 이전 감사 JSON도 읽을 수 있다. 다른 모든 검증 오류를 상세화한 것은 아니다.
4. **프롬프트의 작성 순서를 통일한다.** 최종 analysis를 작성한 다음 그 문장을 기준으로 claimChecks를 작성한다. 서로 반대였던 두 지시를 정리했다. 같은 근거를 여러 필드에 작성하는 구조 자체는 아직 남아 있다.

버전은 `behavior-analysis-v24-source-summary` / `analysis-review-v11-source-summary`다. 작업·분석 재사용 시 이전 버전과 구분된다. 행동 성패·능력을 코드로 계산하는 규칙은 추가하지 않았다.

응답 스키마와 학교 게이트웨이는 변경하지 않았다. DB 마이그레이션도 필요하지 않다. 실행 중인 맥의 로컬 백엔드는 새 코드로 재시작했다. 다른 팀원의 백엔드에는 이 코드 반영과 재시작이 필요하다.

## 자동 검사와 저장 응답 재생

관련 테스트 118개 중 **98개 통과, 20개 조건부 건너뜀, 실패 0개**. 건너뛴 검사는 별도 환경변수·로컬 자료가 필요한 검사다. 이후 학교 모델 전체 분석 검사 1개도 별도로 통과했다. 저장 응답 재생은 네트워크를 쓰지 않는다.

- 하위 finding에 없는 정상 요약 근거 허용, 분석 객체와 근거 목록을 임의 변경하지 않음.
- 없는 사건, 세션 ID를 사건으로 사용, 중복·역순 인용, 다른 finding의 근거, 필수 검토 누락·중복 거부.
- 본문에 인용한 사건을 검토표에서 빼면 거부.
- 두 번 실패하면 분석 결과를 반환하지 않으며, 오류 경로·ID를 두 시도 모두 보존.
- 재시도에 오류 정보 전달, 새 감사 정보 직렬화·복원, 기존 감사 JSON 호환.

실제 이전 응답을 재생한 결과:

|---|---|---|

4회차 응답의 테스트용 복사본에 E194만 보충하면 구조 검사가 통과한다. 이는 검사 조건을 검증하기 위한 조작이며, 실제 모델 응답을 서버가 수정하거나 승인한 것이 아니다. 원본 응답은 그대로 보존했다.

재현 명령(Java 25, `backend` 디렉터리 기준):

```bash

AI_VALIDATOR_LIVE=true ./gradlew test --tests '*ValidatorSchoolPipelineLiveTest' --rerun-tasks
```

첫 명령의 저장 응답 검사는 로컬 `output/analysis-request-2026-09-18` 자료가 필요하다. 두 번째는 해당 입력과 `local.properties`의 API 키를 사용한다. 일반 CI에서는 조건부 검사가 건너뛰어지므로 기본 테스트 성공만으로 실제 모델 검사 성공을 주장하지 않는다.

## 추가로 남은 오류와 다음 작업

1. **확인 행동을 단정하고 다른 필드에서는 모른다고 쓴다 — AI-004.** 관찰에는 “장바구니를 열어 … 확인하고 닫았습니다”, 해석에는 “현재 상태를 확인한 후”라고 쓰지만, uncertainties에는 “실제 목록을 읽었는지 … 확인할 수 없습니다”라고 적었다. UI 조작을 인지 행동으로 확대하고 결과 내부에서도 일관되지 않다. 다음 수정의 우선 대상이다.
2. **의도 추측을 불확실성으로 옮겨 남긴다 — AI-004.** “목표 … 맞추기 위해”라는 목적을 해석에 넣었고, uncertainties에는 “우연한 입력인지”를 추가했다. 대안 배열을 비우는 것만으로 근거 없는 추측이 사라지지 않는다.
3. **품목 종류 수와 총 수량의 계획 표현이 모호하다 — AI-005.** 목표는 “과일 2개 및 음료 1개 구매”인데 `itemCount=3`이다. 이것이 과일 두 종류를 뜻하는지, 같은 과일 두 개를 뜻하는지 문장에 없다. 종류 수와 총 수량을 혼동했을 가능성이 있지만 이 결과만으로 단정하지 않는다. 생성 퀘스트까지 대조해야 한다. “한 번에 목표 수량 선택” 같은 제안도 실제 조작 기능과 대응 여부를 확인해야 한다.

관찰·해석·불확실성의 의미 일치는 AI 검토로 개선하고 원본과 별도 평가한다. 특정 단어를 금지하거나 성공 여부를 규칙으로 계산해서 의미 판단을 대체하지 않는다.

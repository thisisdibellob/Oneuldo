# AI 페이즈별 구현 계획

## 1. 목적과 기준

이 문서는 [AI 활용 및 온디바이스 시스템 설계](./ai-system-design.md)를 실제 개발 작업으로 나눈 구현 로드맵이다. 현재 저장소 상태를 기준으로 데이터 계층, Android 네이티브 런타임, React Native 연동, AI 기능, 개인화 순서로 진행한다.

핵심 구현 원칙은 다음과 같다.

- 첫 AI 기능은 **버스 또는 카페 퀘스트의 단계별 힌트 생성**으로 제한한다.
- 정답, 보상, 완료와 난이도는 규칙 엔진이 결정하고 LLM은 문장만 생성한다.
- 모든 AI 기능은 모델 없이도 정적 콘텐츠로 동작해야 한다.
- 기능 구현보다 먼저 Bllossom GGUF 모델 파일을 확정하고 프로젝트가 재현 가능한 방식으로 내려받을 수 있게 한다.
- 각 페이즈의 완료 조건을 통과한 뒤 다음 페이즈로 이동한다.

## 2. 전체 일정 요약

아래 기간은 개발자 1명이 AI 연동을 주 작업으로 진행할 때의 상대적인 추정치다. 모델 변환과 네이티브 빌드 문제에 따라 달라질 수 있다.

| 페이즈 | 목표 | 예상 기간 | 핵심 결과물 |
|---|---|---:|---|
| Phase 0 | Bllossom GGUF 모델 준비와 프로젝트 반입 | 1~2일 | 모델 파일, manifest, 다운로드 절차 |
| Phase 1 | 퀘스트 수행 데이터 기반 구축 | 1~2주 | 단계·선택지·세션·이벤트 API |
| Phase 2 | llama.cpp 네이티브 런타임 연결 | 1~2주 | Android Development Build에서 모델 실행 |
| Phase 3 | AI 공통 계층과 안전장치 구현 | 1주 | 오케스트레이터, 입출력 검증, fallback |
| Phase 4 | 첫 AI 상황 변형 적용 | 1주 | 퀘스트 1종의 온디바이스 문장 변형 |
| Phase 5 | 성과 기반 난이도 조정 | 1~2주 | 지표 계산, EASY↔NORMAL 자동 조정 |
| Phase 6 | 통제된 상황 변형 확장 | 1~2주 | 검토된 시나리오 변형 확대 |
| Phase 7 | 품질·배포 안정화 | 1~2주 | 저사양 최적화, 회귀 테스트, 배포 절차 |

MVP 범위는 Phase 0~4다. Phase 5부터는 첫 AI 상황 변형 기능이 MuMu Player와 Development Build에서 안정적으로 동작한 뒤 진행한다.

## 3. Phase 0 — Bllossom GGUF 모델 준비와 프로젝트 반입

### 목표

Korean-Bllossom-3B Q4_K_M GGUF 모델을 앱 전용 저장소에 내려받고, 팀원과 기기가 같은 모델 버전을 재현할 수 있도록 파일 위치와 버전 정보를 고정한다. 초기 Qwen/MNN 준비 구조는 모델 비교 후 Bllossom/llama.cpp 구조로 교체되었다.

### 작업

- [x] 사용할 Bllossom GGUF 모델 리비전과 라이선스를 확인한다.
- [x] `frontend/models/bllossom-3b-q4-k-m/`을 로컬 모델 보관 경로로 정한다.
- [x] GGUF 단일 모델 파일의 크기와 SHA-256을 manifest에 고정한다.
- [x] 대용량 모델 바이너리는 Git에 커밋되지 않도록 `.gitignore`에 등록한다.
- [x] 모델 ID, 리비전, 파일 목록, 크기와 체크섬을 담은 `model-manifest.json`을 작성한다.
- [x] 앱 첫 설치 과정에서 같은 파일을 받을 수 있도록 Android 다운로드 관리자를 만든다.
- [x] 누락 파일과 체크섬 불일치를 검사하는 검증 명령을 추가한다.
- [x] 초기 Development Build에는 텍스트 모델을 Android asset으로 포함하도록 확정한다.

### 프로젝트 반입 원칙

- Git에는 모델 바이너리 대신 manifest와 다운로드 스크립트만 커밋한다.
- 모델 파일은 앱 전용 저장소의 Bllossom 모델 디렉터리에서 관리한다.
- 개발자마다 임의의 모델 리비전을 사용하지 않도록 manifest의 리비전을 고정한다.
- 다운로드가 끝나면 파일 존재 여부와 체크섬을 자동 확인한다.
- 액세스 토큰이 필요하면 환경 변수로만 전달하고 저장소에 기록하지 않는다.

### 완료 조건

- 지정한 모델 파일이 로컬 모델 경로에 모두 존재한다.
- 다운로드를 다시 실행해도 같은 리비전과 체크섬을 재현한다.
- 모델 바이너리가 Git 변경 목록에 나타나지 않는다.
- 새 개발자가 문서의 명령만으로 모델을 내려받고 검증할 수 있다.

### 산출물

- 로컬 Korean-Bllossom-3B Q4_K_M GGUF 모델 파일
- `model-manifest.json`
- 모델 다운로드·검증 스크립트
- `.gitignore` 모델 제외 규칙
- Android asset 복사용 Expo config plugin
- 모델 설치 명령과 파일 구조 문서

## 4. Phase 1 — 퀘스트 수행 데이터 기반 구축

### 목표

AI가 참고할 단계별 수행 데이터를 먼저 정확히 수집한다. 현재 백엔드에 있는 카테고리·하위 카테고리·퀘스트 조회 기능을 단계, 선택지, 세션, 이벤트까지 확장한다.

### 백엔드 작업

- [x] `quest_steps`, `quest_choices` 마이그레이션과 초기 데이터를 추가한다.
- [x] `quest_sessions`, `quest_events` 마이그레이션을 추가한다.
- [x] 각 테이블의 Entity, Repository, Service, DTO를 구현한다.
- [x] 퀘스트 상세 조회 API에 단계와 선택지를 포함한다.
- [x] 세션 시작·완료·중단 API를 구현한다.
- [x] 선택 이벤트 기록 API를 구현한다.
- [x] 정답 여부는 서버의 `quest_choices.correct`를 기준으로 계산한다.
- [x] 인증된 사용자가 자신의 세션만 기록·조회하도록 권한을 검사한다.

### 프론트엔드 작업

- [x] `frontend/src/api/quest.ts`를 퀘스트 상세·세션 API까지 확장한다.
- [x] `QuestPracticeScreen`의 하드코딩된 단계를 API 데이터로 교체한다.
- [x] 단계 시작 시간, 선택 시간, 시도 횟수와 힌트 사용 여부를 수집한다.
- [x] 네트워크 실패 시 현재 퀘스트가 중단되지 않도록 이벤트 임시 큐를 둔다.

### 테스트

- 퀘스트 상세 응답의 단계 순서와 선택지 순서를 검증한다.
- 같은 선택을 반복해도 시도 번호와 응답 시간이 올바르게 기록되는지 검증한다.
- 클라이언트가 정답 값을 조작해도 서버 판정이 바뀌지 않는지 검증한다.
- 세션 완료와 중단 상태 전이를 검증한다.

### 완료 조건

- AI 없이도 퀘스트 시작부터 완료까지 수행할 수 있다.
- 각 선택이 누락 없이 `quest_events`에 기록된다.
- 정적 힌트와 피드백만으로 기존 훈련 흐름이 유지된다.

## 5. Phase 2 — llama.cpp 온디바이스 네이티브 런타임 연결

### 목표

Expo Go가 아닌 오늘도 Development Build에서 llama.cpp와 Korean-Bllossom-3B GGUF를 호출할 수 있게 한다.

### 네이티브 작업

- [x] llama.cpp Android 라이브러리와 필요한 C++ 의존성을 프로젝트에 연결한다.
- [x] Expo config plugin 또는 Expo Module 형태로 네이티브 모듈을 구성한다.
- [x] 모델 초기화, 생성, 취소, 해제 API를 Kotlin/Java 계층에 노출한다.
- [x] 추론은 UI 스레드 밖에서 실행한다.
- [x] 모델 중복 로딩과 동시에 여러 생성 요청이 실행되지 않도록 상태를 관리한다.
- [x] 앱 종료와 백그라운드 전환 시 메모리 해제 정책을 구현한다.

> Qwen/MNN 구현은 2026-08-16 완료했으며, 2026-08-17 Bllossom/llama.cpp로 교체했다. 두 ABI 빌드와 Debug APK는 통과했고 실제 `arm64-v8a` 및 MuMu `x86_64` 실행·성능·메모리 검증은 기기 연결 후 마무리한다. 최신 내용은 [Bllossom 전환 설계](./bllossom-3b-on-device-migration-plan.md)에 기록한다.

### TypeScript 인터페이스

초기 인터페이스는 기능별 API가 아니라 런타임 제어에 집중한다.

```ts
type GenerateRequest = {
  requestId: string;
  prompt: string;
  maxTokens: number;
  timeoutMs: number;
};

type GenerateResult = {
  requestId: string;
  text: string;
  latencyMs: number;
};
```

필요한 메서드는 `initializeModel`, `generate`, `cancel`, `releaseModel`, `getRuntimeStatus` 정도로 제한한다.

### 빌드와 테스트

- Android 네이티브 변경 후 Development Build를 새로 생성한다.
- MuMu Player에서는 모듈 로딩, 호출, 오류 처리만 확인한다.
- MuMu Player에서는 모듈 로딩, 모델 초기화, 생성과 오류 처리를 확인한다.
- 모델 파일 없음, 손상, 저장 공간 부족과 초기화 실패를 각각 테스트한다.

### 완료 조건

- React Native 화면에서 한국어 입력을 전달하고 결과를 받을 수 있다.
- 생성 도중 화면 이동 또는 취소가 발생해도 앱이 종료되지 않는다.
- 지원하지 않는 환경에서는 명확한 상태를 반환하고 정적 기능을 유지한다.

## 6. Phase 3 — AI 공통 계층과 안전장치 구현

### 목표

화면에서 네이티브 모듈을 직접 호출하지 않도록 AI 공통 계층을 만들고, 모든 출력에 같은 안전 정책과 fallback을 적용한다.

### 권장 프론트엔드 구조

```text
frontend/src/ai/
├─ contracts.ts          # 입력·출력 타입과 스키마 버전
├─ orchestrator.ts       # 작업별 프롬프트 구성과 실행 흐름
├─ nativeRuntime.ts      # llama.cpp 네이티브 모듈 어댑터
├─ policy.ts             # 길이·문장 수·금지 표현·새 숫자 검증
├─ fallback.ts           # 서버 원본 문장
├─ selectors/
│  └─ questVariationSelector.ts
├─ parsers/
│  └─ questVariationParser.ts
├─ prompts/
│  └─ questVariationPrompt.ts
└─ index.ts
```

### 작업

- [x] `quest-variation-input-v1`, `quest-variation-output-v1` TypeScript 계약을 정의한다.
- [x] 프롬프트에 실명, 이메일, 생년월일과 회원 ID가 들어가지 않도록 입력 선택기를 만든다.
- [x] 정확한 출력 필드, 문장 수, 글자 수, 금지 표현과 새 숫자를 검사한다.
- [x] JSON 파싱 실패, 시간 초과와 런타임 오류를 공통 실패 코드로 정리한다.
- [x] 모든 오류에서 서버 원본 퀘스트를 반환한다.
- [x] `modelVersion`, `promptVersion`, `policyVersion`, `latencyMs`, `fallbackUsed`를 기록한다.
- [x] 개발 모드 진단에는 메타데이터만 전달하고 모델 입력·출력 원문은 저장하지 않는다.

### 테스트

- 정상 JSON, 설명문이 섞인 JSON, 잘린 JSON, 빈 출력에 대한 파서 테스트
- 너무 긴 문장, 추가 필드, 새 숫자와 금지 표현에 대한 정책 테스트
- ID·선택지·정답과 개인정보가 프롬프트에 포함되지 않는지 구조 테스트
- 모델 미설치와 시간 초과에서 서버 원본 퀘스트가 반환되는지 테스트

### 완료 조건

- UI는 AI 결과와 fallback 결과를 같은 타입으로 받는다.
- 검증되지 않은 문자열이 사용자 화면에 직접 표시되지 않는다.
- 모델을 비활성화해도 전체 퀘스트 테스트가 통과한다.

> 2026-08-17 구현 완료. Phase 3 전용 입력 선택·파싱·정책·병합·fallback 테스트를 추가했으며, 화면 적용은 Phase 4에서 진행한다. 상세 내용은 [Phase 3 구현 요약](./phase3-implementation-summary.md)을 참고한다.

## 7. Phase 4 — 첫 AI 기능: 통제된 퀘스트 상황 변형

### 목표

버스 퀘스트 하나에서 서버 구조와 판정은 고정하고, 전체 단계의 상황·지시·힌트·선택지 표시 문장을 온디바이스 AI로 변형한다.

### 변경 경계

| 데이터 | 처리 |
|---|---|
| `questId`, `stepId`, 선택지 ID | 원본 유지 |
| 정답 boolean, 보상, 단계·선택지 순서와 개수 | 원본 유지 |
| `situation`, `instruction`, `hint`, 선택지 `label` | AI가 짧은 한국어 문장으로 변형 |
| 피드백 | 서버 원본 유지 |
| 파싱·정책·구조·정답 검사 실패 | 해당 단계 전체 원문 사용 |

### 작업

- [x] 첫 대상 퀘스트와 변경 가능한 두 필드를 확정한다.
- [x] 단계 진입 시 Phase 3 `generateQuestVariation()`을 호출한다.
- [x] 생성 중 로딩 표시와 중복 버튼 방지를 구현한다.
- [x] 같은 세션·단계에서는 검증된 결과를 재사용한다.
- [x] AI 결과와 원본 fallback을 기존 화면 컴포넌트에 연결한다.
- [x] 접근성 기준에 맞게 짧은 문장·한 행동·안정된 선택지 순서를 유지한다.

> 2026-08-18 코드 구현 완료. `TAKE_BUS_ALONE`에 앱 시작 모델 자동 준비, 전체 4단계 순차 사전 생성, 검토된 테마별 상황 설계안, 선택지 표시 문장 생성과 정답·핵심 의미·한국어 전용 검증을 연결했다. 자동 테스트는 7개 suite, 58개가 통과했다. MuMu 반복 안정성과 arm64-v8a 실기기 성능 검증은 남아 있다. 상세 내용과 시험 순서는 [Phase 4 구현 요약](./phase4-implementation-summary.md)을 참고한다.

### 사용자 평가

- AI 문장이 원래 퀘스트 목표와 정답 의미를 바꾸지 않는지 확인한다.
- 문장이 이해하기 쉽고 불안을 유발하지 않는지 보호자·전문가 검토를 받는다.
- 같은 입력의 반복 생성 결과가 허용 범위 안에 있는지 확인한다.

### 완료 조건

- 모델 다운로드가 끝난 기기에서 온라인 연결 없이 퀘스트 문장 변형이 동작한다.
- 실패 시 서버 원본 퀘스트로 자연스럽게 전환된다.
- 정답률과 보상은 AI 출력과 무관하게 동일한 규칙으로 계산된다.
- MuMu Player에서 반복 실행해도 앱 종료나 UI 멈춤 없이 fallback이 동작한다.

## 8. Phase 5 — 성과 기반 자동 난이도 조정

### 목표

퀘스트 세션과 선택 이벤트를 고정된 서버 규칙으로 계산해 사용자별·세부 분야별 권장 난이도를 EASY와 NORMAL 사이에서 안전하게 조정한다. AI는 난이도 판단에 사용하지 않는다.

### 범위

- [x] 사용자·세부 카테고리별 현재 난이도를 저장한다.
- [x] 완료율, 첫 시도 정답률, 힌트 사용률, 재시도율과 서로 다른 퀘스트 수를 계산한다.
- [x] `PROMOTE`, `MAINTAIN`, `LOWER`, `DATA_INSUFFICIENT`, `NO_CONTENT` 규칙을 버전으로 관리한다.
- [x] 최근 표본과 목표 난이도 콘텐츠 존재 여부를 검사한다.
- [x] 변경 이력에 당시 지표, 판단, 사유 코드와 규칙 버전을 저장한다.
- [x] 로그인 사용자의 현재 난이도에 가까운 퀘스트를 목록 앞에 배치한다.
- [x] 같은 세부 분야의 원본 견본은 카드 하나 안에서 순환하고 목록에 여러 카드로 노출하지 않는다.
- [x] 대중교통 원본 견본을 EASY 5개와 NORMAL 5개로 구성한다.
- [x] 선택된 대중교통 견본 전체에 AI 표현 변형을 적용한다.
- [x] 보호자 대시보드와 실전 퀘스트는 이번 범위에서 제외한다.

### 초기 규칙

- 모든 세부 분야는 EASY에서 시작한다.
- 승급은 최근 3회, 12단계 이상, 완료율 100%, 첫 시도 정답률 85% 이상, 힌트·재시도율 각각 20% 이하, 서로 다른 퀘스트 2개 이상일 때만 허용한다.
- 하향은 완료율 60% 미만, 첫 시도 정답률 50% 미만, 힌트 70% 이상과 재시도 50% 이상이 동시에 발생하거나 2회 연속 중단했을 때 적용한다.
- 한 번에 한 단계만 바꾸고 변경 뒤 24시간 동안 다시 바꾸지 않는다.
- 목표 난이도의 활성 콘텐츠가 없으면 현재 난이도를 유지한다.
- 응답 시간은 접근성·기기 성능 영향을 받으므로 초기 판정에서 제외한다.
- AI는 난이도를 결정하지 않는다. EASY는 한 단서·한 행동, NORMAL은 복수 확인 조건과 행동 순서가 있는 검토된 원본을 먼저 선택한 뒤 표현만 바꾼다.

### 완료 조건

- 같은 세션·이벤트와 규칙 버전이면 같은 결정을 재현할 수 있다.
- AI와 온디바이스 모델을 꺼도 난이도 결정이 동일하다.
- 난이도가 바뀌어도 기존 콘텐츠를 잠그지 않고 권장 순서만 달라진다.
- 자동 테스트와 실제 반복 수행으로 승급·유지·하향 경계를 확인한다.

> 2026-08-18 코드 구현과 자동 테스트 완료. 실제 사용자 반복 수행 검증은 남아 있다. 상세 구조와 시험 방법은 [Phase 5 구현 요약](./phase5-implementation-summary.md)을 참고한다.

## 9. Phase 6 — 통제된 상황 변형 확장

### 목표

Phase 4에서 한 퀘스트에 적용한 상황 변형을 여러 검토된 퀘스트로 확대한다. 보호자 대시보드와 실전 퀘스트는 만들지 않는다.

### 작업

- [ ] 퀘스트별 승인된 상황 테마와 변경 금지 정보를 정의한다.
- [x] 대중교통 EASY·NORMAL 원본 10개에 공통 생성·검증·fallback 흐름을 적용한다.
- [x] 선택지 ID, 정답, 보상, 단계 순서와 핵심 의미를 계속 고정한다.
- [x] 대중교통 견본 전체에 한국어 전용 출력과 핵심 의미 검증을 적용한다.
- [ ] 각 퀘스트에 모델 없이 쓸 수 있는 검토된 정적 변형을 준비한다.

### 완료 조건

- 대상 퀘스트가 늘어나도 원본 정답과 판정은 달라지지 않는다.
- 영어 혼입, 구조 변경과 핵심 의미 훼손이 정책에서 차단된다.
- 모델 실패 시 각 퀘스트의 서버 원본 또는 검토된 정적 변형으로 복구된다.

## 10. Phase 7 — 품질·배포 안정화

### 목표

지원 Android 환경에서 장시간 안정적으로 사용할 수 있는 배포 수준으로 마무리한다.

### 작업

- [ ] 지원 Android 버전과 ABI별 모델 로딩·생성 회귀 테스트를 자동화하거나 체크리스트화한다.
- [ ] 앱 업데이트와 모델 업데이트를 분리하고 모델 버전·해시를 검증한다.
- [ ] Wi-Fi 다운로드, 중단 재개, 저장 공간 부족과 손상 복구를 구현한다.
- [ ] 모델·프롬프트·정책 버전별 품질 회귀 테스트를 실행한다.
- [ ] 30분 이상 반복 훈련에서 메모리 누수와 발열을 확인한다.
- [ ] AI 기능 비활성화 원격 설정 또는 앱 내 안전 스위치를 준비한다.
- [ ] 동의 철회, 데이터 보관 기간과 삭제 절차를 구현한다.
- [ ] 장애 상황과 fallback 비율을 개인정보 없이 관찰할 운영 지표를 정의한다.

### 완료 조건

- 지원 Android 환경에서 크래시, 메모리 누수와 심각한 UI 멈춤이 없다.
- 모델 다운로드 실패나 손상 후 복구할 수 있다.
- 모델 버전 변경 전후의 한국어 품질과 안전성 차이를 확인할 수 있다.
- AI를 비활성화해도 핵심 퀘스트가 정상 동작한다.

## 11. 페이즈 간 의존 관계

| 선행 작업 | 후속 작업 | 이유 |
|---|---|---|
| Phase 0 | Phase 2~5 | 고정된 모델 파일과 버전 정보가 있어야 네이티브 연결과 품질 검증을 재현할 수 있음 |
| Phase 1 | Phase 4, 6 | 힌트와 개인화에 신뢰할 수 있는 단계·세션 데이터가 필요함 |
| Phase 2 | Phase 3 | 실제 런타임 오류와 상태를 알아야 공통 어댑터를 설계할 수 있음 |
| Phase 3 | Phase 4, 5 | 안전 검증과 fallback 없이 생성 문장을 화면에 노출할 수 없음 |
| Phase 1 | Phase 5 | 난이도 계산에 신뢰할 수 있는 세션·선택 이벤트가 필요함 |
| Phase 4 | Phase 6 | 단일 기능에서 품질과 성능을 검증한 뒤 생성 범위를 넓혀야 함 |

Phase 0과 Phase 1은 병행할 수 있다. Phase 2를 시작하기 전에는 Phase 0에서 고정한 모델 파일, manifest와 체크섬 검증이 준비되어야 한다.

## 12. 다음 검증 작업

1. arm64-v8a 실제 Android 기기에서 Bllossom 초기화·생성 시간과 메모리를 측정한다.

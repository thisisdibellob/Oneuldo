# 최종 분석 요청 축소 결과 (2026-09-05)

## 변경 목적과 범위

최종 요청의 참고자료 관리 정보, 중복 출력 설명, 반복 원문 표현을 줄였다. 원본 행동 기록을 삭제하거나 AI 인용 근거를 서버 기준으로 다시 고르지 않는다. 사용자 성패·지원 필요성·난이도는 계속 AI가 판단하며 서버는 구조·참조·게임 실행 제약을 검사한다.

이번 변경은 단계별 분석 뒤의 FINAL 조립에 적용한다. OBSERVE/REDUCE 프롬프트와 체크포인트는 유지한다. 기존 `behavior-analysis-v10-resumable`에 FINAL 입력 변경 식별자 `final-input-v2`를 추가했다. 정확한 시스템/입력 문자열이 체크포인트 키에 포함되므로 이전 최종 결과를 새 요청의 결과로 재사용하지 않는다. 작은 입력을 바로 분석하는 기존 단일 호출 경로는 변경하지 않았다.

## 1. 참고자료: 해석에 필요한 내용과 관리 기록 분리

- 카드 ID, 제목, 출처 URL, 기관·연도, 적용 대상, 핵심 지침, 자료 성격, 원문 위치, 주의사항, 연구 한계, 실제 읽은 범위, 전문가 미검증·추가 학습 미승인 표시, 비공식 요약 고지는 유지한다.
- 두 카드의 동일 속성은 `evidenceCardDefaults`에 한 번 저장하고 각 카드에 합쳐 읽게 한다.
- 수집일, 분류용 태그, 관리용 ID와 권리 관리 기록 전체는 서버의 원래 EvidenceIndex 파일에 그대로 보존한다. 모델에 전달하는 축약본이 원본을 덮지 않는다.
- 카드 선정·권리 상태·인용 허용 검증은 기존대로 적용한다. 미검토 카드를 새로 허용하지 않았다.

## 2. 출력 설명: 중복 예시와 장문 유도 줄이기

긴 JSON 예시를 필드 정의로 바꾸고 FINAL 시스템 지시의 중복을 정리했다. 관찰/가설/대안/근거/불확실성, 세션별 AI 판단, 연습 계획 필드는 유지한다. 의료 진단·능력 점수·개인정보·위험 행동 금지 및 자료의 제한된 용도도 유지한다.

최대 출력은 여전히 **900토큰**이다. 650토큰 내 완결, 핵심 finding 1개, 짧은 문장을 권장하지만 이는 서버의 문장 절단이나 강제 1개 제한이 아니다. 근거와 한계가 더 필요하면 유지하도록 지시하며 기존 최대 finding 12개 검증도 그대로다.

## 3. 반복 원문: 가역적인 공통 값·열 표현

새 `LosslessEventColumns`는 원본 JSON의 반복 표현만 바꾼다.

| 표현 | 읽는 방법 |
|---|---|
| `index` | 각 행에 사건 ID와 실제 eventCode를 나란히 표시 |
| `same` | 모든 해당 행에서 정확히 같은 값 |
| `values` | 원본 순서의 행별 값 |
| `fields` + `rest` | 공통 속성 열과 각 행의 나머지 속성을 합침 |
| `dictionary` + `refs` | 동일 상품·문맥 등 반복 값을 한 번 저장하고 0기준 인덱스로 참조 |
| `groups` + `positions` | 속성 구성이 같은 행을 묶되 원래 위치를 보존 |
| `prefix` + `suffixes` | 시각 등 문자열의 같은 앞부분을 한 번 저장하고 그대로 이어 붙임 |

날짜를 반올림하거나 좌표를 줄이지 않는다. null/누락/0/false/빈 값, 서로 다른 상품 가격, 배열 순서, 사건 수를 구별한다. 같은 상품 ID라도 속성이 달라지면 같은 값으로 합치지 않는다. 제어 키처럼 생긴 원문도 데이터로 복원한다. UUID 별칭 처리를 먼저 적용하고 그 다음 열 표현을 만든다.

기존 표현, 전체 객체의 표 표현, 새 열 표현을 실제 로컬 토큰으로 비교해 더 작은 것을 사용한다. 모두 커도 원문을 잘라 맞추지 않고 기존 크기 오류를 유지한다. AI가 근거를 추가 조회하는 별도 구조(제안 4번)는 구현하지 않았다.

## 동일 요청의 크기 비교

비교 대상은 기존 `final-quest-1788607901682/report.json`의 마지막 PREFLIGHT 요청이다. 원본 244사건을 구간 AI가 읽은 뒤, AI가 인용한 26사건과 마지막 통합 결과가 붙은 요청이다.

| 조건 | 로컬 토큰 수 |
|---|---:|
| 변경 전 입력 + 출력 예약 900 | 9,484 |
| 참고자료·출력 계약 정리만 적용 | 8,911 |
| 새 원문 표현·FINAL 시스템 지시까지 적용 | **6,825** |
| 변경 후 기본 재시도 안내까지 예약 | **6,841** |

같은 조건에서 2,659토큰(약 28%) 감소했다. 표의 숫자는 글자 수가 아니라 로컬 Qwen 토크나이저 계산이며 메시지 여유 64토큰과 최대 출력 예약을 포함한다. 공급자의 실제 usage와는 조금 다를 수 있다. 설정된 요청 예산 7,000과 출력 최대 900은 올리지 않았다.

진단 테스트는 26사건의 값·순서를 변경 전 요청과 정확히 비교하고 과제·통합 분석·전체 범위가 동일한지도 확인한다. 원본 DB 전체 행을 운영 결과로 덮어쓰지 않는다.

## 실제 API 검증

기존과 같은 244사건 스냅샷으로 검증된 구간·통합 체크포인트를 재사용했다. 따라서 아래 시간은 원문 244개를 처음부터 다시 분석하는 시간이 아니다. 실제 API를 쓰되 분석/퀘스트 저장소는 테스트 경계로 대체하여 앱 DB에 진단 결과를 게시하지 않는다.

첫 실행 `final-quest-1788610128752/report.json`은 입력 제한을 통과했지만 FINAL 응답 두 번 모두 `finish_reason=length`였다. 900토큰에서 JSON이 끊겨 실패 처리했고 퀘스트는 호출하지 않았다. 총 68.131초이며 두 API 응답은 2.665초/2.636초, 재시도 대기는 58.258초였다. 출력에서 일부 사건 ID 연결 오류도 확인했다.

그 뒤 사건 ID와 행동 코드를 나란히 표시하고, FINAL 출력의 간결한 작성 지시를 보강했다. 두 번째 실행 `final-quest-1788610421796/report.json`에서 최종 분석은 **READY**, 정상 종료(`stop`), 입력 5,974·출력 495토큰으로 응답했다. HTTP 왕복은 2.039초, 캐시 재사용·조립을 포함한 분석 단계는 7.787초였다. 이 실행은 통합 2묶음 상태에서 이미 FINAL 입력이 예산 내로 들어와 마지막 추가 통합이 필요 없었다.

실제 AI가 제안한 연습 목표: **결제 전 목록 확인 습관 강화**. 난이도 2, 두 품목, 낮은 수량 복잡도·예산 압박, 표준 텍스트 지원을 제안했다. 서버가 이 목표나 난이도를 계산한 것은 아니다.

### 품질상 주의

정상 JSON과 참조 검사를 통과했다고 전문가 수준의 해석 정확성이 입증되는 것은 아니다. 두 번째 분석에도 다음 문제가 남았다.

- 한국어 문장에 `核对`라는 중국어 단어가 섞였다.
- AI는 SUCCESS를 선택하면서도 결제 후 최종 승인 여부는 직접 확인되지 않는다고 적었다. 제출·승인·수행 완료를 어떻게 구분했는지 해석의 일관성 검토가 필요하다.
- 도움 요청을 확인 전략으로 해석하는 것은 가설이다. 해당 게임 기록만으로 생활 능력이나 지원 필요성을 확정할 수 없다.

이 결과를 서버 규칙으로 교정하거나 성공으로 덮어쓰지 않았다. 입력 크기 해결, 생성 파이프라인 통과, 전문가 검토가 필요한 문장 품질은 구분한다.

AI는 두 번 모두 S01(우유 1개·바나나 1송이)을 선택하고 `budget:5800`을 출력했다. 현재 S01 실행 계약의 고정 예산은 **7,000원**이다. 상품 총액 5,800원과 과제 예산을 혼동한 것으로 보이며, 서버는 기존 `시나리오 콘텐츠 계약` 검사에서 거절했다. 이는 사용자의 성공/실패 판정이 아니라 앱이 실행할 퀘스트의 데이터 계약 검사다. 고정 과제 예산을 서버가 덮어쓰거나 검증을 풀지 않았다.

생성됐지만 채택되지 않은 문장 예시:

> 오늘은 아침에 먹을 우유와 바나나를 사요. 장바구니에 담은 물건을 다시 한번 확인하세요. 목록과 맞는지 확인한 후 결제하세요.

따라서 **입력 축소 및 최종 사용자 분석 성공 / 맞춤 퀘스트 최종 채택 실패**가 이번의 정확한 결과다. 퀘스트의 시나리오별 예산 안내와 구체적인 기술 오류 재시도 안내는 별도 개선 대상이다. 추가 API 호출·검증 완화·유료 한도 변경은 하지 않았다.

## 회귀 검사와 서버 반영

전체 백엔드 회귀 검사는 **106개 중 104개 통과, 실 API 재호출 테스트 2개 제외, 실패·오류 0개**다. 실행 명령은 `AI_TOKEN_DIAGNOSTIC=true AI_CHAIN_AUDIT_DIAGNOSTIC=true` 환경에서 `gradlew test --rerun-tasks`이며, 로컬 스냅샷/저장 응답 읽기 진단을 포함한다. 실제 API 전체 체인의 실패와 회귀 테스트 통과는 별개의 결과다.

추가 검사는 다중 세션·빈 세션, 모든 사건 순서, 시각 정밀도, null/누락/0/false/빈 값, Unicode·예약 키, 같은 상품의 속성 변경, 손상된 참조, 사건 ID/행동 인덱스, 기존 표 인코딩과의 왕복 복원을 다룬다. 카드의 출처·적용 한계도 축약 후 정확히 남는지 비교했다.

저장된 두 퀘스트 응답은 실제 검증기로 다시 확인했다. 진단 메모리 안에서 예산 필드만 7,000으로 바꿨을 때 나머지 검사가 통과하여 실패 원인을 좁혔다. 이 가상 수정본은 AI 결과로 저장하거나 앱에 반영하지 않았다.

`git diff --check`는 통과했다. 기존 사용자 변경은 보존했고 커밋은 만들지 않았다. 백엔드를 21:19 KST에 새 코드로 재시작했다(PID 29184, 8080 포트). DB 마이그레이션 V33은 변경 없이 정상 확인됐고 인증 없는 분석 조회가 예상대로 HTTP 401을 반환했다. 원래 스냅샷의 사건 수 244도 다시 확인했다. MuMu/프론트 재설치나 사용자 데이터 초기화는 하지 않았다.

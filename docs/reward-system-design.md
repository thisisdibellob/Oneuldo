# 보상 체계 설계안

작성: 2026-11-27 · 상태: **제안 (팀 합의 전)** · 범위: 자녀용 앱(`frontend/`), 서버 저장은 별도 합의 후

> 이 문서는 아직 구현하지 않은 설계안이다. 현재 코드의 보상 상태는 1장에 정리했다. 2026-09-05 [3~6페이즈 변경 보고서](ai/phase-3-6-change-report.md)에서 정한 "앱이 성공·실패를 판정하지 않는다"는 방향을 유지하는 것을 전제로 한다.

## 2. 설계 원칙

1. **결과가 아니라 참여에 보상한다.** 정답 여부, 속도, 실수 횟수로 보상을 바꾸지 않는다. 앱이 성공·실패를 판정하지 않는다는 기존 결정과 맞춘다.
2. **잃는 보상은 없다.** 감점, 벌칙, 연속 기록이 끊겼을 때의 손실 표시를 두지 않는다. 연속 기록이 끊기면 조용히 새로 시작한다.
3. **도움 요청은 칭찬할 행동이다.** 혼자 하기 어려울 때 도움을 청하는 것도 훈련 목표다. 도움을 받았다고 보상을 줄이지 않는다.
4. **왜 받았는지 보인다.** 보상마다 짧은 이유("장보기를 끝까지 했어요")를 함께 보여 준다. 숫자만 오르게 하지 않는다.
5. **예측 가능하다.** 무작위 상자, 확률 보상, 한정 시간 압박은 쓰지 않는다. 같은 행동에는 같은 보상을 준다.
6. **보상과 능력 평가를 섞지 않는다.** XP·레벨은 참여량이다. 보호자 앱과 분석 화면에서 능력 점수처럼 보여 주지 않는다.
7. **게임 속 돈은 보상이 아니다.** 소지금은 장보기 예산 연습 도구로 분리한다(6장).

## 3. 보상 종류와 지급 규칙

### 3.1 경험치(XP)

| 근거 | XP | 지급 시점 | 데이터 근거 |
|---|---:|---|---|
| 장보기 끝까지 하기 | 30 | 계산을 마쳐 활동 기록이 저장될 때 | 활동 앨범 `shopping` |
| 도서관 업무 끝까지 하기 | 30 | 사서에게 보고를 마칠 때 | `library` |
| 카페 근무 끝까지 하기 | 30 | 근무를 마칠 때 | `cafe` |
| 버스로 목적지 도착 | 20 | 목적지에서 내릴 때 | `bus` |
| 빨래 정리 끝까지 하기 | 20 | 옷장 정리까지 마칠 때 | `laundry` |
| 수상한 연락 확인하기 | 20 | 이야기를 끝까지 마칠 때 | `safety` |
| 물품 전달 | 10 | 받는 사람에게 건넬 때 | `delivery` |
| 마을 일일 퀘스트 완료 | 정의된 값(10~30) | 퀘스트 완료 시 | `dailyQuests.ts`의 `rewardXp` |
| 퀘스트 연습 끝까지 제출 | 퀘스트의 `rewardPoints` | 마지막 단계까지 선택을 제출할 때 | 서버 퀘스트 |
| 오늘의 첫 활동 | +10 | 그날 첫 보상이 생길 때 | 지급 기록 날짜 |
| 도움 요청을 써 본 활동 | +5 (활동당 1번) | 해당 활동 완료 시 | 활동 지표의 도움 요청·도움받은 주문 |

**반복 제한:** 같은 종류의 활동은 하루 3번까지만 XP를 준다. 4번째부터는 기록은 남기되 XP는 0이며 "오늘은 충분히 연습했어요"라고 보여 준다. 같은 행동을 기계적으로 반복하게 만들지 않기 위해서다.

**중복 방지:** 지급 기록마다 근거 ID(예: `activity:shopping:<세션ID>`)를 키로 두고, 같은 키는 한 번만 지급한다.

### 3.2 레벨

- 레벨마다 **100 XP 고정**. `레벨 = floor(누적 XP / 100) + 1`
- 레벨이 갈수록 어려워지는 곡선은 쓰지 않는다. "다음 레벨까지 40 XP"처럼 남은 양이 늘 비슷해야 이해하기 쉽다.
- 하루 평균 2~3개 활동이면 약 이틀에 1레벨 오른다.

### 3.3 연속 학습

- 퀘스트 탭 달력의 연속 일수(`countActivityStreak`)를 그대로 쓴다.
- 3일, 7일, 14일, 30일에 도달하면 뱃지와 +20 XP를 한 번 준다.
- 끊기면 0부터 다시 센다. "연속 기록이 끊겼어요" 같은 손실 알림은 띄우지 않는다.

### 3.4 뱃지

활동 기록만으로 판단할 수 있는 것만 둔다. 실력이나 정확도 기준 뱃지는 만들지 않는다.

| 뱃지 | 조건 |
|---|---|
| 첫 장보기 | 장보기 1회 완료 |
| 버스 박사 | 버스 도착 5회 |
| 카페 단골 직원 | 카페 근무 3회 |
| 책 정리 도우미 | 도서관 업무 3회 |
| 빨래 척척 | 빨래 정리 3회 |
| 연락 지킴이 | 수상한 연락 확인 3회 |
| 마을 한 바퀴 | 7가지 활동을 모두 1회 이상 |
| 도움 요청 첫걸음 | 도움 요청을 처음 사용 |
| 3일·7일·14일·30일 연속 | 연속 학습 도달 |

### 3.5 보상을 쓰는 곳

- **꾸미기 해금(1순위):** 레벨에 따라 캐릭터 옷, 집 소품을 하나씩 연다. 돈처럼 쓰고 사라지는 방식이 아니라, 모은 만큼 열리고 잃지 않는다.
- **상점은 나중에 검토:** 화폐를 쓰는 상점은 잃는 경험이 생겨서 1차에서는 만들지 않는다.

## 4. 화면 배치

| 화면 | 보여 줄 것 |
|---|---|
| 활동 완료 화면 | `보상 미지급` 대신 받은 XP와 이유 목록. 예: "+30 XP 장보기를 끝까지 했어요", "+5 XP 도움을 요청했어요" |
| 게임 HUD | 활동 완료 때 짧은 XP 알림. 레벨이 오르면 한 번 더 알림 |
| 홈 탭 | 윗줄의 고정 문구 "연속 학습 117일!"을 실제 연속 일수로 바꾸고, 레벨과 다음 레벨까지 남은 XP 막대 |
| 퀘스트 탭 | 통계에 "이번 주 XP" 추가 |
| 사용자(프로필) 탭 | 레벨, 받은 뱃지, 해금한 꾸미기 |
| 보호자 앱 | 참여 횟수와 연속 일수만. XP·레벨을 능력 점수처럼 비교하지 않음 |

모션 감소 설정이 켜져 있으면 XP 알림 애니메이션을 줄인다. 글자 크기와 짧은 문장 규칙은 기존 화면을 따른다.

## 5. 데이터 구조

### 5.1 1단계: 앱 안의 지급 기록

`frontend/src/game/rewardLedger.ts` (새 파일, 활동 앨범과 같은 저장 방식)

```ts
type RewardSource = 'activity' | 'daily-quest' | 'practice' | 'first-of-day' | 'help' | 'streak' | 'badge';

type RewardEntry = {
  id: string;          // 근거 키. 같은 키는 한 번만 지급
  source: RewardSource;
  sourceId: string;    // 활동 세션 ID, 일일 퀘스트 ID 등
  xp: number;
  reason: string;      // 화면에 보여 줄 짧은 이유
  earnedAt: number;
};
```

- 누적 XP, 레벨, 이번 주 XP, 뱃지는 지급 기록에서 계산한다. 따로 저장하지 않는다.
- 활동 앨범에 기록이 추가될 때 보상 규칙을 실행하는 방식으로 연결한다. 각 게임 화면에 보상 코드를 흩어 두지 않는다.
- 저장 한계: 웹은 브라우저 저장, 휴대폰 앱은 활동 앨범처럼 실행 중에만 유지된다. 휴대폰에서도 남기려면 앨범과 함께 기기 저장소(예: AsyncStorage) 도입이나 2단계 서버 저장이 필요하다.

### 5.2 2단계: 서버 저장 (백엔드 합의 필요)

- 새 테이블 `member_rewards (id, member_id, source, source_key UNIQUE, xp, reason, earned_at)`
- `POST /api/rewards/claims`: 앱이 근거 키를 보내면, **서버가 자기 기록(완료된 `quest_sessions`, 행동 로그)으로 확인한 뒤** XP를 정해 지급한다. 앱이 보낸 XP 숫자는 믿지 않는다.
- `GET /api/rewards/summary`: 누적 XP, 레벨, 뱃지, 최근 지급 내역
- 퀘스트 연습: 마지막 단계까지 제출된 세션에 `QuestSession.complete(quest.rewardPoints)`를 호출한다. 정답 수와 무관하게 끝까지 참여했으면 지급한다.
- 기존 `quest_sessions` 기록은 소급 지급하거나 재계산하지 않는다(3~6페이즈 보고서의 원칙 유지).

## 6. 게임 소지금 정리

- 소지금은 XP와 관계없는 **미션 예산**이다. 장보기를 시작할 때 미션 예산을 받고, 계산한 만큼 줄고, 미션이 끝나면 초기화한다.
- HUD와 가방은 같은 값(현재 미션의 남은 예산)을 보여 준다. 미션 밖에서는 지갑 표시를 숨기거나 "장보기할 때 받아요"로 안내한다.
- 현재 `30,000`과 `12,000` 고정 숫자는 1단계에서 제거한다.

## 7. 단계별 계획

| 단계 | 내용 | 담당 | 규모 |
|---|---|---|---|
| 1 | 지급 기록 저장소, 활동·일일 퀘스트 XP, 레벨, 완료 화면 표시, 홈·퀘스트 탭 표시, 소지금 고정값 정리 | 프론트 | 약 1주 |
| 2 | 뱃지, 연속 학습 보상, 프로필 탭 | 프론트 | 3~4일 |
| 3 | 서버 저장과 퀘스트 연습 보상 지급, 앱 동기화 | 백엔드 + 프론트 | 백엔드 합의 후 |
| 4 | 꾸미기 해금 | 프론트 + 아트 | 아트 준비에 따라 |

### 검증 기준

- 같은 활동 기록이 두 번 저장 신호를 보내도 XP는 한 번만 오른다.
- 정답을 틀리거나 도움을 받아도 끝까지 하면 같은 기본 XP를 받는다.
- 같은 종류 4번째 활동부터 XP가 0이고, 안내 문구가 나온다.
- 레벨 경계(99→100 XP)에서 레벨과 남은 XP가 맞게 바뀐다.
- 저장소를 쓸 수 없는 환경에서도 게임 완료가 막히지 않는다.

## 8. 팀이 정할 것

1. **보상을 다시 켜는 데 동의하는가?** 9월에 성공 보상을 끈 이유(AI 분석 방향)와 이 설계(참여 보상)가 충돌하지 않는지 박재현 학생 확인이 필요하다.
2. **XP 값과 하루 3회 제한이 적절한가?** 전문가 자문이나 실제 사용자 반응을 보고 조정할 수 있다.
3. **서버 저장을 언제 할 것인가?** 1·2단계는 앱만으로 가능하지만, 기기를 바꾸면 기록이 사라진다.
4. **보호자 앱에 무엇을 보여 줄 것인가?** 참여 횟수만 보여 줄지, 레벨도 보여 줄지.
5. **꾸미기 아트를 준비할 수 있는가?** 없으면 4단계는 뱃지까지만 하고 미룬다.

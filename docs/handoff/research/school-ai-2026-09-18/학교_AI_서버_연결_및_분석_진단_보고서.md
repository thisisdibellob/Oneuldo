## 3 연결 수립 단계의 간헐적 실패

### 3.1 직접 측정한 HTTPS 연결 결과

2026-09-18 15:50 KST부터 `/healthz`와 `/api/tags`를 번갈아 검사했다. 아래 시간 단위는 초다. `/api/tags`는 인증 헤더를 넣지 않은 검사이므로 HTTP 401은 네트워크와 HTTP 응답 도달을 확인하는 정상적인 관측 결과다.

| 순서 | 경로 | HTTP | curl 종료 코드 | DNS 완료 | TCP 연결 완료 | 전체 경과 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | /healthz | 000 | 28 | 0.240430 | 0.000000 | 6.015230 |
| 2 | /api/tags | 401 | 0 | 0.209945 | 3.103321 | 3.205594 |

실패 3건은 TLS 연결 완료 시간도 0이었고 HTTP 응답을 받지 못했다. 성공 응답의 원격 IP는 모두 [당시 공개 서버 IPv4]이었다. 관측 범위에서 DNS 조회 실패는 없었으며, TCP 연결 완료 전 시간 초과와 부합한다.

`time_connect`는 요청 시작부터 TCP 연결 완료까지의 누적 시간으로 DNS 시간도 포함한다. 따라서 위 값 3.103321초를 순수 TCP 구간 지연으로 그대로 해석하면 안 된다. 해당 건의 DNS 이후 연결 완료까지 차이는 약 2.893초다. 이는 연결 구간 지연의 관측값이며 원인 장비나 패킷 손실을 확정한 값은 아니다.

### 3.2 실제 백엔드 요청에서 확인한 연결 실패

| 조건 | 실패 구간 KST | 코드와 단계 | 시도 수 | 클라이언트 경과 |
| --- | --- | --- | --- | --- |
| 기본 8K 분석 | 15:57:33~15:58:22 | AI_CONNECT_TIMEOUT / CONNECT | 3회 | 48,220ms |
| 18K 설정 분석 | 16:02:02~16:02:50 | AI_CONNECT_TIMEOUT / CONNECT | 3회 | 48,219ms |

두 건 모두 `httpStatus=null`, 원인 체인의 마지막 예외는 `ConnectException`으로 기록됐다. 클라이언트는 원인 체인에 포함된 `HttpConnectTimeoutException`을 우선 분류하므로 최종 코드가 `AI_CONNECT_TIMEOUT`인 것과 모순되지 않는다.

실행 설정은 연결 제한 15초, 연결 재시도 2회로 최초 시도 포함 최대 3회다. 재시도 대기는 1초, 2초다. 위 약 48.2초는 시도와 대기 및 가능한 클라이언트 큐 대기를 포함한 경과시간이며 단일 TCP 연결 시간은 아니다. 응답 대기 설정은 별도로 30분이었다. 응답 대기를 늘리는 것만으로 연결 단계 실패가 해결되지는 않는다.

실패 요청 식별자는 다음과 같다.

- 기본 8K: `[시험 식별자 생략]`
- 18K 설정: `[시험 식별자 생략]`

HTTP 이전에 실패한 요청은 `X-Request-ID` 헤더가 서버에 도달하지 않을 수 있다. 서버 접근 로그에 해당 ID가 없다는 사실만으로 장애 위치를 판정하면 안 된다.

### 3.3 다른 팀원이 전달한 관측과 해석 범위

추가로 전달된 보고에는 동일 도메인이 [당시 공개 서버 IPv4]으로 해석되고, 실패 시 `time_connect=0.000000`, 성공 시에도 연결까지 2~3초 이상 걸리는 경우가 있으며, 백엔드와 같은 형식의 요청에서 60초 동안 연결되지 않았다는 내용이 있다. **이는 팀원이 제공한 관측이며 위 직접 측정 표의 6건에 포함하지 않았다.**

두 환경의 결과는 연결 수립 단계 불안정이라는 설명을 지지한다. 다만 `time_connect=0`만으로 SYN 송신 또는 SYN-ACK 미수신을 패킷 수준에서 입증할 수는 없다. 프록시 사용 여부, 실제 접속 IP와 포트, curl 오류 문구 및 양쪽 패킷 캡처를 함께 확인해야 한다. 학교 방화벽, NAT, 서버 호스트 또는 중간 회선 중 어느 지점이 원인인지는 현재 미확정이다.

## 4 최종 분석 토큰 예산 초과

### 4.1 기본 설정에서 재현한 실패

원래 합성 기록은 사건 9개와 장면 상품 24개를 포함한다. 같은 기록의 두 번째 실행에서는 실제 AI 호출 3회가 모두 정상 종료했다. 관찰 2회와 통합 1회 이후 최종 분석 조립 단계의 로컬 사전검사에서 중단됐다.

```text
AI final assembly: groups=2, reservedTokens=9933, limit=7800
AI final assembly: groups=1, reservedTokens=9485, limit=7800
errorCode=FINAL_EVIDENCE_EXCEEDS_LIMIT
source=PREFLIGHT
analysis status=INPUT_TOO_LARGE
```

**AI 서버가 최종 요청을 거절한 사례가 아니다.** 최종 요청을 보내기 전에 로컬 `TimelineAnalysisPipeline`이 한도 초과를 판정했다. 앞선 정상 호출의 서버 집계 입력/출력 토큰은 각각 5,601/395, 4,420/632, 2,272/631이었다.

### 4.2 입력을 줄여도 한도가 남는 구조

근거 검토가 켜져 있으면 최종 분석 사전검사는 다음 예약량을 사용한다.

```text
finalReserve = finalOutputTokens
             + finalOutputTokens + 1500

기본 finalOutputTokens 1800 → 예약량 5100
성공 시험 finalOutputTokens 1200 → 예약량 3900
```

9,485와 7,548은 순수 입력 토큰 수가 아니라 **입력과 재시도 문구, 후속 검토를 위한 예약량을 더한 사전예산**이다. 실제 개별 HTTP 요청은 해당 단계의 입력과 출력 상한으로 다시 검사한다.

물건 2개·사건 3개로 줄인 데이터도 기본 출력 상한 1,800을 유지하면, AI 관찰 결과를 비워 둔 오프라인 계산에서 해당 최종 합성 사전예산이 8,504토큰으로 계산됐다. 이 수치는 실제 모델 호출 결과가 아닌 낙관적인 사전 계산이며, 기록 개수만 줄여서는 기본 예산을 만족하지 못할 수 있음을 보여준다.

18K 시험은 컨텍스트 18,432와 요청 예산 18,000으로 실행했으나 연결 시간 초과로 종료됐다. 18K에서 전체 분석이 성공하는지는 검증하지 못했다. 이 설정은 코드상 전체 원본을 직접 분석하는 경로도 선택할 수 있으므로 동일 요청에 컨텍스트만 더한 완전한 대조 시험으로 보아서는 안 된다.

### 4.3 출력 상한을 과하게 줄인 별도 실패

물건 2개·사건 3개, 관찰 출력 상한 400, 최종 출력 상한 1,200 조건에서는 모든 실제 호출이 7,800토큰 이하였다. 그러나 여러 응답이 정확히 400토큰에서 `finishReason=length`로 끊겼다. 자동 분할과 재시도 후 `CHUNK_ANALYSIS_FAILED`로 종료됐고 프로필은 생성되지 않았다.

이 실패는 낮춘 출력 상한 때문에 분석 JSON을 끝까지 생성하지 못한 사례다. 입력 초과, TCP 연결 실패와 구분해야 한다. 따라서 출력 상한을 일괄적으로 낮추는 방식도 안전한 일반 해결책으로 확인된 것은 아니다.

| 단계 | 로컬 입력 | 출력 상한 | 입력과 상한 합계 | 서버 입력 / 실제 출력 | 결과 |

로컬 수치는 프로젝트의 Qwen BPE 토크나이저로 실제 저장 요청을 재계산한 값이다. 메시지 포장 여유 64토큰을 포함한다. 서버 집계와의 수치 차이는 계산 범위 차이로 보아야 하며, 문자 수를 임의로 토큰으로 환산한 값이 아니다.

세 호출 모두 실제 학교 서버 응답이며 체크포인트 재사용이 아니었다. 모두 `finishReason=stop`, 오류 없이 끝났다. 호출별 경과시간은 20,101ms, 22,378ms, 37,410ms였고, **전체 분석 시간은 84,746ms**였다. 전체 시간은 TCP 연결 시간이나 단일 모델 호출 시간이 아니다.

16:26:19 KST에 분석 작업과 분석 결과가 `READY`가 됐으며, 현재 프로필 API는 HTTP 200과 `READY`를 반환했다. 첫 프로필은 검토가 완료된 분석을 초기 프로필로 저장한 것이다. 기존 프로필과 새 분석을 통합하는 별도 AI 호출을 시험한 것은 아니다.

분석 결과는 제출한 우유의 품목·수량과 예산이 목표에 맞는다고 판단했다. 또한 상품을 찾거나 추가하는 세부 조작과 사용자의 인지 상태는 이 기록에 없으므로 확인할 수 없다고 명시했다.

## 6 권장 진단 순서와 조치 대상

### 6.1 우선순위 1 연결 경로 확인

서버 담당자는 실패 시각, 클라이언트 공인 IP, 접속 대상 IP와 포트, 프록시 및 IP 버전을 맞춘 상태에서 클라이언트와 서버 또는 학교 경계 장비의 패킷을 대조해야 한다. HTTP 이전 장애는 웹 접근 로그만으로 판별하기 어렵다.

| 패킷 관측 | 우선 확인할 범위 |
| --- | --- |
| 클라이언트에서 SYN 송신이 확인되지 않음 | 로컬 방화벽, 프록시, 클라이언트 경로 |
| 클라이언트는 SYN 송신, 서버 관측 지점에는 도달하지 않음 | 중간 경로, 학교 경계 방화벽, NAT 또는 포트포워딩 |
| 서버에 SYN 도달, SYN-ACK 송신이 관측되지 않음 | 서버 방화벽, 443 리스너, 자원과 연결 대기열 |
| 서버가 SYN-ACK 송신, 클라이언트가 수신하지 못함 | 반환 경로, NAT, 양측 방화벽 |
| 양쪽에서 연결 완료가 확인됨 | TLS와 HTTP, 게이트웨이, 모델 처리 단계로 조사 범위 이동 |

각 행은 조사 우선순위이며 원인 확정표가 아니다. 패킷을 캡처한 위치와 NIC 선택도 확인해야 한다. 같은 시각의 Caddy 및 게이트웨이 로그, 방화벽 드롭 기록, NAT/conntrack 상태를 함께 대조한다. 서로 다른 외부 네트워크에서도 같은 조건으로 비교하면 특정 경로 또는 IP 제한 여부를 좁히는 데 도움이 된다.

네트워크 검사에는 인증 정보와 추론 부하가 없는 작은 경로를 사용한다. 다음은 재현용 예시이며, 본 보고서 작성 중 추가 실행한 결과는 아니다.

```powershell
curl.exe --connect-timeout 15 --max-time 20 -sS -o NUL `
  -w "http=%{http_code} ip=%{remote_ip} dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n" `
  https://oneuldo.duckdns.org/healthz
```

이 예시는 Windows PowerShell용이다. 실행 시각과 curl 종료 코드도 함께 기록한다. `/healthz` 성공은 연결과 해당 HTTP 경로의 응답만 확인하며, 모델 추론 성공을 대신하지 않는다.

### 6.2 우선순위 2 분석 예산과 출력 길이 검토

백엔드 담당자는 대표적인 짧은·보통·긴 기록을 고정하고 다음 값을 단계별로 함께 남기는 것이 필요하다.

- 실제 입력 토큰, 출력 상한, 실제 출력 토큰과 `finishReason`.
- 최종 합성 예약량 및 다음 근거 검토 요청의 실제 크기.
- 오류 단계와 코드, 로컬 사전 차단인지 서버 응답 오류인지 여부.
- 컨텍스트·요청 예산·품질 검토·출력 상한·모델·커밋.

`finalReserve`와 반복되는 지시문 및 장면 정보를 우선 검토하되, 목표·장바구니·근거 사건을 임의로 누락하는 축약은 피해야 한다. 출력 상한 조정은 관찰 JSON, 최종 분석, 근거 검토 각각의 완결성을 확인하면서 적용해야 한다. 본 소량 성공 설정을 전체 사용자용 설정으로 즉시 확정할 근거는 부족하다.

클라이언트는 이미 연결 실패만 제한적으로 재시도한다. 응답 시간 초과나 연결 중단은 서버에서 추론이 시작됐을 수 있으므로, 원인 구분 없이 재시도를 추가하면 중복 실행이 생길 수 있다.

### 6.3 완료 판정 기준

연결과 분석을 별도로 판정한다. 합의한 반복 검사 구간과 둘 이상의 외부 네트워크에서 연결 결과를 기록하고, 시간 초과가 재발하면 양쪽 패킷으로 실패 위치를 확인한다. 분석은 대표 기록별로 관찰·합성·검토·저장이 완료되고, 입력 한도 초과나 출력 잘림 없이 근거를 유지하는지 확인한다. 한 번의 성공을 장기 안정성 확보로 처리하지 않는다.

## 7 인수인계 범위

당시 검증은 최신 코드 확인, 인증, 실제 모델 호출, 합성 기록 저장, 소량 기록 분석·근거 검토 및 첫 프로필 저장까지다. 실제 모바일 전체 플레이, 기존 프로필 누적 갱신, 맞춤 퀘스트 생성, 대량 실제 기록과 장기 연결 안정성은 검증 범위에 포함되지 않았다.

이 Git 보관본은 수신자·수행자 이름, 공개 서버 IP, 합성 시험의 요청·분석·작업·데이터셋 ID와 로컬 로그 경로를 제외했다. 원본 보고서의 위치는 상위 인수인계 자료 목록에 남겼다. 이 문서를 현재 서버 상태나 백엔드 변경 권한으로 해석하지 않는다.

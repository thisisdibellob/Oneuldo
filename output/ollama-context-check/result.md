# 16K / 8K 실제 분석 비교 — 2026-09-10

동일한 합성 이벤트 85건(이동 80건 + 시작·수량 변경·제출·종료 5건)을 사용했다.
전체 분석 지시문을 포함한 로컬 예상 입력은 9,243토큰이었다.
오늘도의 실제 프롬프트, 입력 인코딩, 토큰 예산, 분석 파이프라인과 검증기를 사용했다.
DB는 이전 합성 입력을 읽기만 했으며, 이번 결과는 운영 DB에 저장하지 않았다.

| 컨텍스트 | 요청 예산 | 호출 수 | 전체 시간 | 누적 입력 토큰 | 누적 출력 토큰 | Ollama 전체 할당 | GPU 할당 |
|---|---|---|---|---|---|---|---|
| 16,384 | 14,000 | 1 | 488.543초 | 9,195 | 1,388 | 16.723GiB | 5.572GiB |
| 8,192 | 7,000 | 2 | 342.392초 | 6,962 | 1,170 | 16.239GiB | 5.643GiB |

두 실행 모두 READY이며 재시도 없이 종료했다. 16K는 전체 입력 9,195토큰을 실제로 받아
한 번의 최종 분석으로 처리했다. 8K는 관찰 호출 1회(187.615초)와 최종 호출 1회
(153.559초)를 사용했다. 이번 입력은 관찰 프롬프트로는 한 구간에 들어갔으므로,
8K 실행을 여러 원시 로그 구간으로 나눈 시험이라고 해석해서는 안 된다.

이번 사례에서 16K는 8K보다 146.2초,
약 42.7% 오래 걸렸다.

## 내용 차이

- 16K: 이동 기록 80건/2초 간격과 수량 수정에 대해 별도 finding 2개를 작성했다.
  합성 데이터라는 한계도 명시했다. 최종 출력 1,388토큰.
- 8K: 수량 변경과 구매 제출을 중심으로 finding 1개를 작성하고, 이동 해석은 요약과
  불확실성에 남겼다. 최종 출력 607토큰(관찰 출력 563토큰 별도).
- 두 결과 모두 구매 제출을 구매 완료로 표현하는 부분이 있다. 구조 및 참조 검증 통과가
  해석의 사실성이나 실제 사용자에 대한 판단 품질을 보장하지 않는다.

## 한계와 결론

16K에서 9K 이상의 긴 입력을 한 번에 분석하는 것은 이 노트북에서 가능했다.
하지만 이번 사례에서는 더 빠르지 않았으며 최종 응답 길이와 세부 관찰 수도 달랐다.
동일한 양의 결과를 생성하는 순수 처리량 비교가 아니고, 16K→8K 순서로 각 1회만 실행했다.
시간에는 컨텍스트 변경에 따른 로딩/캐시 효과가 포함된다. 최대 16K 입력, 여러 사용자,
여러 세션, 실제 로그 전반의 품질이나 안정성을 검증한 것은 아니다.

메모리 수치는 /api/ps의 size/size_vram이며 OS 전체 RAM 사용량이나 실제 피크 RSS가 아니다.
SSH 비밀번호 없는 접속이 불가능해서 RAM available, swap, 온도는 측정하지 못했다.

운영 설정은 변경하지 않았다. 테스트 후 실제 로드 컨텍스트도 8,192로 복원했다.
따라서 현재 설정을 유지하면서 정보 보존이 더 필요한 사례에 한해 16K를 추가 검증하는
것이 이번 측정에 맞는 판단이다.

## 결과 파일과 재실행

- report.json: 입력, 요청별 응답, 검증 결과, 시간 및 메모리 스냅샷
- memory.jsonl: 15초 간격 Ollama 메모리 보고값
- source.json: 이전 테스트에서 만든 짧은 합성 입력(확장 전)
- test.log: Gradle 실행 결과

SSH 터널이 열린 상태에서 backend 폴더에서 실행한다. 합성 source.json 파일이 필요하다.

```sh
OLLAMA_CONTEXT_BENCHMARK=true \
JAVA_HOME=/opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk/Contents/Home \
./gradlew test --tests '*OllamaContextBenchmarkTest'
```

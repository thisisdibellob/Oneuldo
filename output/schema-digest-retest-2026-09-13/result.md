# JSON Schema 적용 후 동일 구간 재시험

## 결과
- 운영 모델이 있는 서버의 내부 전용 임시 게이트웨이에서 검증했다. 운영 서비스 교체는 아직 하지 않았다.
- 이전과 동일한 E112–E154, 43개 사건을 보냈다. 전체 556개 사건 재분석은 아니다.
- HTTP 200, finish_reason=stop, 실제 호출 219.214초(3분 39초).
- 입력 5807토큰, 출력 724토큰. 응답 잘림 없음.
- 명명된 필드로 출력했고, 배열 자료형과 모든 근거 ID의 해당 구간 소속 검사를 통과했다.
- 응답 상한 1800토큰, 문맥 8192, temperature 0.2 유지.
- 전 시험은 259.808초에 802토큰, 이번은 219.214초에 724토큰이다. 출력량과 모델 로딩 상태가 달라 속도 개선 효과로 단정할 수 없다.

## 해결된 문제
근거 ID 칸에 설명 문장을 출력하던 문제가 이번 호출에서는 재발하지 않았다. 생성 스키마와 후속 입력 참조 검사를 모두 거쳤다. 정해진 스키마만 게이트웨이에서 허용하며, 최종 분석·퀘스트 생성 계약은 이번 변경 대상이 아니다.

## 남은 품질 문제
- ITEM_SEARCH_STARTED는 이동 시작 때 자동 발생한다. 모델은 여전히 검색 기능 사용이라고 오해했다.
- E135→E136 간격은 19185−18626=559ms(0.559초)인데 약 2초라고 설명했다.
- 생수의 categoryId는 drink인데 fresh 구역에 있는 것으로 추정했다.
- produce를 “생산품”으로 표현했다.
- 형식 통과는 해석의 정확도 통과가 아니다. 다음 단계로 이벤트 발생 조건 및 검증 가능한 시간·상품 위치 정보를 제공해야 한다.

## 구현과 검증 범위
최종 검증 묶음: 백엔드 11개(실제 모델 호출 1개 포함), 게이트웨이 8개, 합계 19개 통과. 추가로 앞선 관련 분석 회귀 테스트 묶음도 통과했다. 전체 프로젝트 테스트를 수행한 것은 아니다.
구간 관찰, 중간 요약, 추가 이동 상세 요청에서 completeDigest를 사용해 고정 JSON Schema를 Ollama format으로 전달한다. 기존 단일 문자열 보정과 원본 ID 소속 검사는 유지한다.
초기 maxLength=2000 스키마는 서버의 문법 복잡도 한도 오류를 일으켰다. 생성 단계의 maxLength만 제거했고, 백엔드의 글자 수 검사는 그대로 유지했다. 해당 실패 원문은 grammar-limit-failure.json에 보관했다.
